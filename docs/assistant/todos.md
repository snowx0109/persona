# To-dos (Todos)

Record something to do, hand it to one or several Agents, and see in To-dos which Agents are working on it, what each is doing and how far the overall task has progressed; Agents can also be grouped by to-do on the Agents page.

## Why this is needed

One task often needs several Agents (different computers, workspaces and tabs). An Agents list arranged by project, state or computer does not show which ones are working on the same task, its overall progress, where it is blocked or who it is waiting for. To-dos collect scattered Agents under one goal for progress tracking and coordination.

## Who owns what (since 2026-11-04)

To-dos belong to the assistant (`todos.go`, `todo_decisions.go`, `todo_sessions.go`, `tasks_close.go` in `server/internal/assistant`; formerly in hub, see `docs/assistant/assistant.md`, "Boundary with hub"):

- **Assistant**: storage (the four tables below, still in the hub's Postgres, no migration, read/written only by the assistant process), every to-do API in "API overview" below, automatic project linking and following spawned sessions, reconciliation of herdr markers, snapshots of Agent titles/start errors, decision records, automatic completion and closing Agents for completed tasks.
  When hub receives a computer's session list it emits `sessions.changed`; when the user handles a card it emits `interaction.resolved`. These behaviors come from those two events.
- **Hub**: only forwards to-do APIs (`assistantwire.Routes`, carrying caller role; read-only roles still get 403), and uses the assistant's snapshot report for App session lists, question cards and pushes (`todos`: which unfinished to-do each Agent works on and which Agents are quiet, `hub/assistant_todos.go`; quiet reports only cover Agents of unfinished quiet tasks or those completed less than 7 days ago (`quietKeep`), keeping the report small; Agents from older tasks still push normally if they work again);
  `POST /api/v1/sessions` and `POST /api/v1/sessions/{mid}/{sid}/messages` with `todo_id` first ask the assistant (`assistant.todo_handoff`): does the to-do exist, is it done (if handoff is disallowed, it supplies 404/409 and the message, echoed by hub), prepend decisions to the Agent's message and project context for new Agents, all in one call. After handoff, ask assistant to link it (`assistant.todo_link`; assistant determines both linked title and to-do title); workspace renames through hub notify assistant (`todos.space_renamed`). Protocol in `docs/protocol/protocol.md`, "Bus".
- **When assistant is disconnected** (hub just started, assistant process restarting): to-do APIs return `503 assistant_offline`, "The assistant is temporarily unavailable. Try again later"; create/send with `todo_id` also return 503 (to-do existence unknown). Session-list to-do/quiet markers keep hub's last report (absent in the first second or two after hub starts before assistant reports). Hub emits no events during this period, so automatic linking, marker reconciliation and decision records wait for the next session list or answer after reconnection; workspaces renamed through hub are not migrated.

Completed ownership is display-only (#5929): `TodoReport.completed` names the most recently completed, non-dismissed
to-do for each session without an active link. Session lists expose it as `completed_todo: {id,title}`, separate from
the existing active `todo`. The Web chat menu labels it Completed and opens the to-do; it offers no fresh-link prompt.
Active task routing, supervision, counts and the existing quiet grace period still read only their original active
links/quiet report. Unknown optional fields are ignored by older clients; native menus are not changed by this fix.

## Permission of a planned task

A writable task that `task_plan` leaves without a `permission` gets one on the hub before the plan is saved, so the
plan card shows the mode the Agent runs in (#1897, #3026), in this order: the manager's default permission mode
(Settings › Assistant, `default_permission_mode`), then `permissions.defaultMode` in Claude Code's settings on the
computer the task lands on (Settings › Claude Code › Default permission mode, read with `claude.settings`), then
`default` (Ask every step). The last two cover the common case: someone who set Claude Code to start in Auto gets
Auto for the Agents the assistant starts, as for the ones started from the Agents page with no mode picked. A plan
saved before this, or a task that reaches the start with no mode, is settled the same way on the computer it starts
on. A computer that is offline, an older node, or a mode Persona does not know (such as `dontAsk`) gives `default`.
The card names Auto (`auto` is one of `task_plan`'s modes, and Edit offers it on every client); a Codex launcher still
takes only `plan` from it (`assistant/tasks_permission.go`). None of this reaches a launcher whose Agents run with Allow all
(Claude Code, and a Paseo provider whose approval is Auto Accept, #8141): its card says Allow all, the mode that runs
("Read-only planned tasks" below).

## Read-only planned tasks

`task_plan` treats `readonly: true` as task metadata and a first-prompt constraint. Claude-family launchers save and start with
`permission: bypassPermissions`, whether the task is read-only or writable, and so do Paseo providers whose approval is
Auto Accept (their launcher says `auto_accept`; Grok and Paseo's other ACP providers, OpenCode): they start with it on,
as the owner decided (#8141, `docs/integrations/paseo.md` "Agents Persona starts"). A read-only task's first message adds
`本任务只读：不改项目文件、不提交、不对外写入` after its own prompt, without changing the saved prompt or duplicating the
constraint on retries. With the default `assistant.readonly_mode: sandbox`, Codex read-only tasks keep `permission: plan`
and the hard read-only sandbox. traex and omp take no permission mode or effort, so their tasks start with neither
and a read-only one has only the first-message constraint (#7559); one the call names is refused. pi, cursor and agy
start a writable task the same way, but one the call names is dropped rather than refused, as the node ignores it for
them (#8151); a read-only task for them is refused (below). Planning, card edits,
legacy plans, retries, and the final dispatch all resolve the launcher before applying this rule; a permission change is
saved with the resolved launcher and model.

A read-only task whose launcher starts pi, the Cursor CLI or the Antigravity CLI in a terminal is refused when it is
planned (#8316, `assistant/tasks_placement.go` `readonlyLauncherRefusal`): these agents have no read-only mode, so
`task_plan` answers `readonly_unsupported` with the launchers on that computer that do take a read-only task (Claude
Code's and Codex's), and nothing is saved or started. The model may plan the task writable or on one of those; no other
launcher is put in its place. The same check runs again before a start (a card edited to one of them, a plan saved
before this). A launcher whose agent the computer's list does not say keeps the selected protection mode, as above, and the
node refuses a plan-mode start it cannot hold read-only (below); a start an engine runtime runs is the runtime's to refuse.

Advanced users can choose **Settings > Assistant > Read-only task protection > Instructions only**, or use
`persona_settings` with key `assistant.readonly_mode` and value `prompt`. Agent-initiated changes require the owner's
confirmation on the phone. The confirmation explains the scope and rollback; denial, dismissal or an Agent answering
for the owner saves nothing. `sandbox` is the default and restores the existing behavior.

`prompt` keeps `readonly: true` and the first-message constraint, but starts Codex with `permission: default` rather than
forcing `plan`. The node leaves the launcher's permission arguments and Codex configuration alone; it does not add
`--sandbox read-only` or a bypass flag. Claude-family tasks and Auto Accept providers retain their existing
`bypassPermissions` behavior.
**Instructions only is not a security boundary**: the runtime's normal permissions still apply, including any sandbox
the owner configured there. The setting is per assistant, independent of the model, and is rechecked on new starts and
retries (including waiting or older saved plans). It does not restart or change running Agents. Ordinary explicit plan
starts and helpers preserving their caller's permissions are unchanged.

`persona_settings` list/get/set exposes the effective value. `GET /api/v1/assistant` returns `readonly_mode` as `sandbox`
or `prompt`, including the default when unset; `PUT /api/v1/assistant` accepts the same values. Writes require a full-role
caller and an explicit matching manager header or query parameter, as for `default_permission_mode`; other values and
`null` are rejected without changing settings. The existing Web Settings selection is a direct owner edit. Switch back
to `sandbox` in Settings or through an owner-confirmed `persona_settings` change to restore the default for future starts.

Ordinary plan-mode starts keep their existing behavior. In `sandbox` mode, for Codex read-only tasks the node must honor `plan` or refuse
the start. Terminal starts and supported terminal resumes use `--sandbox read-only
--ask-for-approval never`: no approval can escalate past the sandbox. The node retains that constraint for later
resumes, including a message that reopens the session. The terminal policy uses `never` because Codex 0.167 no
longer accepts `untrusted` on its CLI; the separate thread API policy is unchanged.

A Codex launcher with its own `-s` / `--sandbox`, `-a` / `--ask-for-approval`, `--full-auto`, dangerous bypass
(including `--yolo`), or `--approve-for-me` is refused with `readonly_unsupported` and `delivered: none` instead
of guessing which permission wins. Managed launcher arguments are checked too. A launcher argument separator
that would turn the added flags into prompt text is also refused. Non-plan launches retain their original arguments.
An already running Codex cannot receive new CLI flags, so it cannot be adopted by a read-only start.
pi, the Cursor CLI and the Antigravity CLI have no such mapping either: a read-only task for one of them is refused when it is planned (above), and the node refuses a plan-mode start of theirs that still reaches it, before a pane opens (`docs/integrations/launchers.md`, "Work agents").

External runtime starts fail closed unless the runtime declares `caps.readonly` (`docs/integrations/runtimes.md`):
without it a runtime may ignore the mode or fall back to a different provider at dispatch. The Paseo bridge declares it
(#3238): a plan start runs on a Paseo provider that runs Claude Code, in Paseo's `plan` mode; a non-Claude provider, no
such provider, an agent Paseo reports in another mode (archived at once), or a takeover are refused.
Update both the assistant and nodes for this behavior. This is the runtime's plan restriction on task work, not a
promise that the runtime writes no session metadata or plan files, and it does not prevent a later explicit mode
change by the user.

Health-space plans and mixed plans still wait for Start. Clients show the Read-only requested label on a waiting plan and
collapse a started plan to "Started N tasks". The saved task's `permission` is the actual launch mode:
`bypassPermissions` for Claude and an Auto Accept provider, and, by default, `plan` for Codex read-only tasks
(`default` in `prompt` mode).

## Data model

Server state is stored in the hub's Postgres database (read/written by the assistant, above):

### 1. todos table
- `id` (text, PK): opaque string identifier (e.g. `todo_3f2a1b9c`).
- `title` (text, NOT NULL): to-do title.
- `notes` (text, NOT NULL, DEFAULT ''): detailed description and requirements, sent as context when handed to an Agent.
- `done_at` (timestamptz): completion time; `NULL` while unfinished.
- `created_at` (timestamptz, NOT NULL): creation time.
- `updated_at` (timestamptz, NOT NULL): last modification time.
- `origin` (text, NOT NULL, DEFAULT ''): assistant chat that created the task (session id); empty for manual creation ([unified-entry.md](unified-entry.md)).
- `plan_id` (text, NOT NULL, DEFAULT ''): plan that created it (`task_plans.id`).
- `done_by` (text, NOT NULL, DEFAULT ''): who marked it done: empty = user tapped (or launch failed, see `start_error`), `auto` = assistant automatically completed it after judging it finished ("Automatic completion"), `review` = supervisor completed it after acceptance (#3124), `cancelled` = supervisor cancelled it (#1851). The API continues to send `done_by = review` for cancellations so existing clients retain their review labels and reasons; supervised cancellations also keep `supervision.state = cancelled`.
- `done_reason` (text, NOT NULL, DEFAULT ''): judgment model's reason for automatic completion (e.g. "PR merged and TestFlight released"), cleared when user marks done or reopens.
- `reopened_at` (timestamptz): last time user reopened a completed to-do; assistant only judges automatic completion again after a new turn of work follows it.
- `thread` (jsonb, NULL): the chat thread the to-do is bound to, `{"channel", "chat_id", "thread_id", "title"}` (#5279, "Chat thread" below); `NULL` while it has none. A `CHECK` requires all three keys, and a unique index `todos_thread` over `(thread->>'channel', thread->>'chat_id', thread->>'thread_id') WHERE thread IS NOT NULL` lets a thread belong to one to-do only. One value, read and written as a unit, hence a jsonb column like the ledger's `reviews` rather than four more columns on every to-do read; the binding goes with the row when the to-do is deleted.
- `source` (jsonb, NULL): where the to-do was asked for when that is another chat, `{"channel", "chat_id", "message_id", "anchor"?, "handoff"?, "no_report"?, "reported_at"?, "report_text"?, "report_due_at"?, "report_full_reply"?, "attempts"?}` (#6146, "Where it came from" below); `NULL` for any other to-do. Migration `0429` (manager side; first numbered 0428, which #6188 also took, so `db.go` renumbers it); a `CHECK` requires the three ids. Not unique (several to-dos may come from one message); one value read and written as a unit, hence jsonb like `thread`. Deleting the to-do deletes it.
- `due_at` (timestamptz) / `due_date` (date): when it is due, a moment or a whole day in the user's time zone; at most one (`CHECK todos_due_one`). `remind_at` (timestamptz): when the phone is pushed about it; `reminded_at` (timestamptz): when that was claimed, cleared whenever `remind_at` changes. `priority` (text, NOT NULL, DEFAULT ''): `''` normal, `high`, `low` (`CHECK`). Migration `0442` (manager side, #1683, "Due date, reminder, priority" below).
- `inbox_item` (text, NOT NULL, DEFAULT ''): the Inbox row it was made from (#6480, `docs/assistant/inbox.md` "Merge rows and Add to to-dos"), `''` for any other to-do. Migration `0512` (manager side). The to-do's page opens the row from it; the row links back through its chain.
- `project` (text, NOT NULL, DEFAULT ''): the slug of the knowledge-base project the to-do belongs to, `''` for none. Migration `0461` (manager side, #2581, "Project" below). Not a foreign key: projects live in the knowledge base's files.
- `kind` (text, NOT NULL, DEFAULT ''): `''` for a to-do or a task, `concern` for one of the owner's concerns (#3561, "Concerns" below). Set when it is made, never changed. Migration `0487` (manager side). `done_by` gains `reported` for a concern closed by its report.
- `part_of` (text, NOT NULL, DEFAULT '') / `after_ids` (text[], NOT NULL, DEFAULT '{}'): the to-do whose request this one is a piece of, `''` for none, and the pieces of that request it waits for (JSON `part_of`, `after`; "Requests in pieces" below). Migration `0542` (manager side). Not foreign keys: the manager checks them when they are written, and a deleted to-do leaves an id the readers skip.
- `restored_at` (timestamptz): when the owner last brought the to-do back from Inactive; `someday_until` (timestamptz): when a to-do the owner put off to Someday comes back, `NULL` while it is not put off, `9999-12-31` for Someday with no date. Neither is an edit: `updated_at` stays. Migration `0552` (manager side, #10226, "Restores and Someday" below).
- (Not in the table) `stage`, `stage_kind`, `pr_url`, `pr_status`, `delivery`: stage strip, task kind, change link, observed PR facts and delivery-card location, stored in settings `assistant.todo_stages`, merged when reading to-dos ("Delivery"); `stage_done` is worked out from them when the to-do is listed (below). `pr_url` comes from the full PR or merge request link in an Agent's reply; a PR named by number alone ("PR #7350", or "#7350" in a reply that speaks of a PR) becomes a full GitHub URL when its repository is known without guessing: the task's own PRs, the one repository the reply or the to-do's title or notes link, or the repository earlier full links from the same repository root on that computer showed (settings `assistant.repo_roots`, `assistant/pr_number_ref.go`, #7921). Anything ambiguous records nothing.
  Number-only references are recorded only after GitHub confirms a pull request, normally through the issue response's non-null `pull_request` field (#8248). An issue URL alone is not a delivery PR. If acceptance encounters a stale PR record and verification fails, it removes that record only after confirming an ordinary issue or a missing item with readable PR access; remaining PRs still pass the same delivery gate. A 404 from an inaccessible repository, permission failures, rate limits and transient errors do not discard the record. Item-level 404/422 responses do not pause unrelated PR checks.
  A complete final closeout's explicit `artifact: pr` outranks incidental PR numbers or URL artifacts elsewhere in that reply; full PR links, `#N`, `N` and `owner/repo#N` are supported. The reference must be the artifact itself, not a URL embedded in an annotation, quote, fenced example, document or ordinary reference. A closeout without a PR artifact does not fall back to incidental PR prose. Before accepting, the hub reads only the active linked agents' latest full turns, rejects peer, side-conversation, injected and unrelated-request evidence, and applies the normal merge/deployment gate to a recovered explicit PR even when the stored link is a different, valid PR. It never promotes an unproven link from saved reference history. If every active agent's own final record says `status="done"`, `merged="n/a"` and `deployed="n/a"` with a non-PR artifact, the task has no PR delivery: remove the contaminated current/history links and stale delivery hold, then check the original task criteria. Missing or duplicate applicability fields, unreadable or unrelated turns, malformed artifacts, and conflicting explicit deliveries cannot establish that exception. Legacy progress without a closeout keeps its existing link detection; normal polling still never fetches a transcript for a clipped preview. A recognizable full PR URL in `task_review.link` is checked ahead of the stored link and remains subject to the gate; an issue URL or number alone is not a PR override.
  `stage_kind` is `code` or `general` (#3380, #11590; `assistant/task_stage_kind.go`), evidence first. A linked GitHub PR or an HTTPS merge request on any host, a closeout's `artifact: pr|commit|branch`, or a delivery held at a PR or a merge makes a task `code`. A task handed out read-only stays `general` until then (plan permission alone is not read-only: code tasks start in plan mode to get a plan approved). Its stage record keeps `readonly` from the latest start and `change` once a change was seen without a PR link, so every recompute (an `agent_supervise` rescope, an adoption, a task without a kind) reads the same.
  Otherwise its goal (the brief's, else the title) and its criteria in effect are read for a code change asked for outright: fix, implement, PR, MR, merge into main, commit, refactor, unit tests or CI, with Chinese and Japanese equivalents (PR, MR and CI as written, so "Mr" names a person). A conditional sentence ("if …", "若…", "…则…", "otherwise", "whether") or a negated change ("don't change the code", "不改代码") counts for nothing, and in each clause the first kind of work named decides: "verify the fix" checks, "find the cause, then fix it" changes. Words that only name what is read, used or shipped (code, test, deploy, release, feature, bug) count for nothing either. With none of that, criteria or not, the task is `general`: a strip drawn for work that changes no code stays on Develop for good, while a code task read as `general` only goes without a strip until its change shows up. Repository or issue associations alone are no evidence (research runs in repositories too). Older clients ignore the field; every client (web, iOS, Android and the Feishu cards) omits the strip for general tasks and keeps the existing task status.
  `stage_done` (#11590) is worked out when the to-do is listed and never stored: the to-do is closed as done (not cancelled, not a failed start), its kind is not `general`, its stage is short of deploy, and nothing waits to ship (no delivery held at a PR, a merge or a switch; with a PR, only a delivery that says nothing ships). The clients then end the strip with Done after the steps it went through ("Plan ✓ — Develop ✓ — Done ✓") instead of leaving a current step. Work that went out keeps Deploy, or Verified once a check confirmed it (#3240): acceptance alone is no check of a deployment, so it never shows Verified, and a step the work never took is not ticked. Older clients ignore it and show the stored stage.
  Mid-task replies (session lists, full followed items and supervisor progress reports) and final handoffs update the same forward-only progress. List snippets ending in an ellipsis and followed items marked with `FullSize` are skipped, without fetching transcripts from the session-list handler. GitHub `/pull/N` and any host's `/merge_requests/N` or `/-/merge_requests/N` links count; bare `MR !N` does not. Web links use `PR #N` or `MR !N` respectively.
  A pending `IxPlan` approval temporarily shows `plan` before review; answering it restores the stored stage, without recording a backwards progress change. Agent-link changes recompute pending plans for both the old and new task. Other permissions and questions never imply plan approval.
  `pr_status` is additive forge evidence, not another task state: `url`, `head_oid` (the PR head commit), `state` (`open`, `merged`, `closed`), `draft`, `review`, `checks`, `conflicts`, and `checked_at`. The existing minute deployment pass reads GitHub PRs at most once per ten minutes per open to-do, independently of whether the running hub reports its commit, after its deploy checks and on a deadline of its own (one minute), so slow forge reads never delay a deploy. Failed reads never refresh old facts. After the current task/stage PR facts are saved, an open PR with merge conflicts and a known head emits an urgent, actionable `pr_conflict` supervision event, even with no running Agent. Pending conflict signals recheck the task/stage URL, head, open state and conflict before being rendered, so a resolved or replaced conflict is dropped. A digest containing a conflict stays in the existing pending-signal queue while its supervisor is busy or dispatch fails; it is never folded into a rendered relay, which cannot refresh the facts before draining. Other entries batched with that conflict wait with it until dispatch can revalidate the batch. The existing `assistant.supervision_dedup` setting keeps one permanent fingerprint per task/PR URL/head, independent of Agent text and the ordinary thirty-minute expiry; a new head can notify once, but returning to an already-told head cannot. Deferred or failed dispatch releases the existing reservation. Web uses matching facts no older than fifteen minutes and no active Agent or owner decision to show **Waiting for merge**, outside **In progress** but still open, with the existing PR link and blocker labels. A known open PR becoming merged or closed returns an external-event/someone-else hold to the same supervisor's `pending_review`; merging alone never accepts or closes it. Only that hold wakes: a to-do at work, in rework or under review keeps its state. A typed wait must record `merge_review`, `ready` and the matching GitHub PR object in `evidence.url`; its reason is not an observation binding. A different typed source or kind never falls back to prose. Only legacy parks without evidence match a reason containing a PR link or `#N` (`parkWaitsOnPR`). The park identity comes from the task snapshot before the forge request and is rechecked when its ledger changes, so an old response cannot end a park created or replaced during that request. The stage's PR is checked under the stage lock first, so a PR replaced while it was read changes neither the facts nor the supervision. Older `checked_at` observations cannot replace newer facts. Typed terminal waits reconcile again if a supervision write failed after saving PR facts, including after restart; they do not require another open-to-terminal transition. The existing review signal is queued after the ledger commits, not a new delivery outbox. A merged observation moves the stage to merge only while the open to-do and its stage still name that PR, checked under the stage lock (`setTaskStageOn`). A personal priority/date hold or an unrelated post-deployment hold is not disturbed. Work that spans several PRs (#7935): the pass also reads up to four of the to-do's earlier PRs (`PRs`, newest first, skipping ones already known merged or closed), kept per PR in the stage record (`prs_status`) and published as `other_prs` (the same fields, newest first). The to-do waits for merge while any of its PRs is fresh, open and non-draft, and each open one shows with its own blockers; only the current PR raises `pr_conflict`. A PR becoming merged or closed wakes the supervisor only once no other PR it follows is open or still unread, and only a park whose reason names one of its PRs. Older clients ignore these facts.

  Terminal-PR binding reuses the existing supervisor-review handoff; it does not directly send the Agent an acceptance instruction. The bound source can be an earlier, already terminal PR when the last other followed PR resolves. A terminal fact from before the active park cannot resolve its typed source indirectly: the source is rechecked, so a reopened source is not mistaken for an ended wait. The existing current-PR plus four-earlier-PR sample stays intact; a bound source outside it adds at most one read per existing poll interval, rather than displacing another open or unknown PR. New GitHub comments/reviews still use the existing task-linked Inbox path and its opt-in `assistant.inbox_signals`; this change neither enables that switch nor adds participant-specific reply, CI/run, deployed-version or GitLab observers. Aggregate review/check labels alone have no event identity or submission time and are not treated as fresh wake events.

  A fresh current-head change request can also end a typed merge wait (#9570). The same PR observer records optional `changes_requested_at` from an active review's provider `submitted_at`, only with a known reviewer and a `commit_id` matching the observed PR head. Later approval or dismissal by that reviewer supersedes the request; a saturated 100-review page supplies no automatic-wake timestamp. The exact recorded `merge_review` source must match, and the provider time must be strictly after this park and no later than `checked_at`; missing or ambiguous same-second times do not prove a new event. The captured park, current task/stage and latest saved facts are rechecked before changing the existing state to `pending_review`. This actionable review need not wait for other PRs to become terminal. Its provider time persists with PR facts, so a failed ledger write can reconcile after reload without another review-state edge. It preserves the original review/history and supervisor, queues the existing review signal, and never accepts/closes the task, fabricates an owner answer or sends an Agent instruction itself. Poll cadence and Inbox switches are unchanged; this does not add ordinary-comment, participant-reply, CI, GitLab or version observers.

   Review notifications ask the supervisor to check each current acceptance criterion; they are not completion verdicts (#8373). The shared message retains the actual PR event or judge's reason and any recorded criterion evidence. A prerequisite PR merging or closing, or receiving a change request, does not prove the delivery criteria passed. A judged-done result is still a review candidate, not acceptance. Review state, acceptance gates and task display grouping are unchanged.

### 2. todo_spaces table
Records project workspaces (herdr workspaces) linked as a whole to a to-do:
- `todo_id` (text, NOT NULL, FK → `todos(id)` ON DELETE CASCADE): linked to-do ID.
- `machine_id` (text, NOT NULL): machine ID.
- `space` (text, NOT NULL): project name (session `space_name`, or `space_id` if absent).
- `linked_at` (timestamptz, NOT NULL): link time.
- Constraints:
  - Primary key: `(todo_id, machine_id, space)`.
  - Unique index: `UNIQUE (machine_id, space)`, ensuring a project follows only one to-do at a time.

### 3. todo_agents table
Records associations between to-dos and Agent sessions:
- `todo_id` (text, NOT NULL, FK → `todos(id)` ON DELETE CASCADE): linked to-do ID.
- `machine_id` (text, NOT NULL): machine ID.
- `session_id` (text, NOT NULL): session ID.
- `linked_at` (timestamptz, NOT NULL): link time.
- `released_at` (timestamptz): time active association was released; `NULL` while active.
- `title` (text, NOT NULL, DEFAULT ''): session-title snapshot (still displayable beyond the session-list time window).
- `cwd` (text, NOT NULL, DEFAULT ''): session working-directory snapshot.
- `agent` (text, NOT NULL, DEFAULT ''): Agent-kind snapshot (`claude` / `codex`, etc.) written by manual, adoption/dispatch, workspace/automatic, planned, spawned, quiet `agent_start`, launcher-repair, successor and independent-review links from the session or start answer's `session.agent`. Planned, spawned and quiet `agent_start` tasks fall back to the explicitly resolved launcher kind when the answer (or the adopted session after a lost answer) omits it. A repair uses only its own start answer. Empty means unknown, and a later link with an empty value keeps the stored kind.
- `start_error` (text, NOT NULL, DEFAULT ''): asynchronous creation failure reason (viewable/removable in To-dos).
- `source` (text, NOT NULL, DEFAULT 'manual'): association source:
  - `manual`: manually linked or handed to an existing Agent;
  - `space`: linked with the entire workspace project;
  - `spawned`: spawned by a parent Agent linked to the to-do.
  - `leader`: the Agent of a task handed out with `task_plan` role `leader` (#3656, [unified-entry.md](unified-entry.md), "Task leaders");
  - `worker`: an Agent a task leader handed out with its own `task_plan`; `via` is the leader's to-do id (not a session): the worker's `supervision.supervisor` is that task's leader Agent session;
  - `review`: an independent reviewer's session (kept released, hidden from the lists).
- `via` (text, NOT NULL, DEFAULT ''): association path:
  - For source `space`, project key `<machine_id>/<space>`;
  - For source `spawned`, parent Agent identifier `<machine_id>/<session_id>`;
  - For source `worker`, the leader's to-do id.
- `dismissed_at` (timestamptz): manual removal timestamp. Removal sets both `released_at` and `dismissed_at`. APIs exclude removed records, and subsequent session updates do not automatically relink them.
- Constraints:
  - Primary key: `(todo_id, machine_id, session_id)`.
  - Partial unique index: `UNIQUE (machine_id, session_id) WHERE released_at IS NULL`, ensuring an Agent actively works for only one to-do at a time.

### 4. todo_decisions table
Decisions the user has made for this task ("Decision records"):
- `id` (text, PK): opaque identifier starting with `dec_`.
- `todo_id` (text, NOT NULL, FK → `todos(id)` ON DELETE CASCADE).
- `question` / `choice` / `reason` (text): question, selected choice, reason (reason may be empty).
- `source` (text, NOT NULL, DEFAULT 'manual'): `manual`, recorded manually in the to-do; `card`, recorded automatically when user answers an Agent question card; `outcome`, conclusions, decisions and lessons extracted from the Agent's last reply when the task finishes ("Record conclusions on completion" below); `agent`, noted by an Agent on the to-do while it works (`todo_decision_add`, below); `thread`, said by the user in the chat thread the to-do is bound to ("Chat thread" below); `reported`, what the main conversation told the owner of a concern's outcome (written only together with the concern's close, "Concerns" below).
- `source_machine` / `source_session` / `source_message` (text): provenance; for `card`, the asking Agent and card (interaction id), empty for manual records.
- `supersedes_id` (text, FK → `todo_decisions(id)` ON DELETE SET NULL): earlier decision this one supersedes.
- `created_at` (timestamptz, NOT NULL).
- Constraint: partial unique index `(todo_id, source_message, question) WHERE source_message <> ''`, recording each question on the same card only once.

### 5. todo_supervision table
Ledger for tasks supervised by the main chat (#3124, `docs/assistant/unified-entry.md`, "Supervision"), one row each; unsupervised to-dos have no row:
- `todo_id` (text, PK, FK → `todos(id)` ON DELETE CASCADE).
- `supervisor` (text, NOT NULL): supervisor, the chat that created it. With Agent tasks on (#3617, `docs/assistant/unified-entry.md` "Agent tasks") a to-do another chat or the user opened can have one too: the main chat or a leader, with `done_when` empty unless given. The background supervisor (#4927) is never stored here: a task it follows up keeps the main chat as `supervisor` (`docs/assistant/unified-entry.md` "Background supervisor").
- `done_when` (jsonb, NOT NULL, DEFAULT '[]'): acceptance criteria (string array); `expect_minutes` (integer, NOT NULL, DEFAULT 0): expected minutes.
- `state` (text, NOT NULL, DEFAULT ''): `''` in progress, `pending_review`, `rework`, `needs_user`, `accepted`, `cancelled`; `round` (integer): rework round.
- `reviews` (jsonb, NOT NULL, DEFAULT '[]'): each review (`verdict`, per-item `checks`, `note`), at most 20 kept; `updated_at` (timestamptz).
- `pending_since` (timestamptz, NULL): when the task entered `pending_review`; kept by every write while the review waits, NULL in every other state. Android and Apple read it to tell a supervisor's review under way from one that is overdue; the web lists every review alike (`docs/assistant/unified-entry.md` "Needs you and In progress: each thing once (#3387)"). Rows already waiting when the column was added started from `updated_at`.

### 6. task_briefs and task_brief_todos tables
A task's brief (#3822, `docs/assistant/unified-entry.md`, "Briefs"): what was asked when the work was handed out.
- `task_briefs`: `id` (text, PK), `brief` (jsonb, written once: the owner's message, who started it, goal, `done_when`,
  `expect_minutes`, `estimate_source`, `estimate_evidence`, `out_of_bounds`), `state` (jsonb: the log of dispatches, scope changes,
  completions, estimate_due and overdue marks, the result), `created_at`, `updated_at`. Nothing rewrites `brief`;
  `done_when` in effect is the brief's as its logged scope changes left it, and a supervised task's
  `todo_supervision.done_when` carries the same list. Pre-feature records with no estimate source stay outside the automatic clock.
- `task_brief_todos`: `todo_id` (text, PK, FK → `todos(id)` ON DELETE CASCADE), `brief_id` (FK → `task_briefs(id)`),
  `continues` (the to-do it took the work over from), `reason`, `linked_at`. A brief's rows in `linked_at` order are its
  lineage.
- `task_estimate_rounds`: one row per new supervised plan dispatch, keyed by `round_id` with to-do and brief links.
  Its machine, repository, task kind, mode, role and tier are immutable. A durable Agent link that matches that
  cohort marks admission. The accepted review stores the first recorded completion's elapsed minutes, once. Rows
  count only while their exact accepted closure still stands. The estimator reconciles a bounded batch of recent
  completed rounds after an interrupted sample write. The manager keeps this table private.

`GET /api/v1/todos` carries both on a to-do that has a brief: `brief` (the record, its `log`, `criteria` and
`expect_minutes_now` in effect, `estimate_source_now`, `estimate_evidence_now`, `estimate_clock_at`, `estimate_due_at`,
`estimate_due_told_at`, the latest `actual_minutes` and `completion_reported_at`, `clock_at`, `due_at`, `overdue_at`,
`result`) and `lineage`. A task from before briefs gets a reconstructed one lazily.

### 7. todo_imports table
To-dos imported from another app (#4009, "Imported from Reminders" below). Migration `0499` (manager side).
- `source` (text, `CHECK` `'reminders'`) and `external_id` (text, nonempty): the item in that app; together the PK.
- `todo_id` (text, NULL, FK → `todos(id)` ON DELETE SET NULL, unique while set): the to-do it became; `NULL` once that
  to-do was deleted in Persona, which keeps the item from being imported again.
- `fingerprint` (text): short hashes of the title, notes and due date last taken from the item, one per field.
- `created_at`, `updated_at` (timestamptz).

### 8. todo_images table
Images attached when a to-do is created (#11084), in their selection order. A timestamped manager migration keeps them apart from the to-do row so ordinary list reads never carry image bytes.
- `id` (text, PK): the client-supplied UUID of the image.
- `todo_id` (text, NOT NULL, FK → `todos(id)` ON DELETE CASCADE) and `position` (integer, NOT NULL): its to-do and place in the selection; unique together.
- `name` (text, NOT NULL, DEFAULT `''`): the optional original filename, shown as a label only, never used as storage or Agent content.
- `mime` (text): `image/jpeg` or `image/png`, checked against a complete decode of `data`; `width` and `height` (integer): the decoded dimensions.
- `data` (bytea): the image itself, at most 1 MiB before base64 encoding. A create takes at most 50 images and rejects a truncated, falsely labelled, invalid or oversized image before writing anything. The to-do, its repository bindings and all its images commit in one transaction; there are no temporary uploads to reclaim.

Link/release semantics:
- When an Agent is linked to a new to-do and is active on another, the same transaction marks the original association `released` (records `released_at`); the old to-do shows it as "Previously involved".
- If an Agent previously involved in this to-do is manually linked back, clear `released_at`/`dismissed_at`, and refresh `linked_at` and snapshot information.
- When the user removes an Agent from a to-do, set that row's `released_at`/`dismissed_at` (soft removal, excluded from API results).

### Session decoration fields
In session lists (`GET /api/v1/sessions` and WebSocket `sessions` pushes), hub injects to-do fields using the assistant snapshot's report (`todos.links`):
```jsonc
"todo": {
  "id": "todo_weather",
  "title": "Release weather App 1.3"
}
```
Only present when the session is currently associated (`released_at` and `dismissed_at` both `NULL`) and the to-do is unfinished. On release, transfer or completion, the field automatically clears; clients need no frontend join.
The internal `spawn_from` field carried in session reports is stripped before hub pushes to clients.

### Live WebSocket pushes
- `{"type":"todos"}`: broadcast on to-do creation, edit, deletion, whole-project link/unlink, Agent association changes, a change of its chat thread, or when its `ask` comes up, is taken or ends ("Waiting for the owner"); clients refetch `GET /api/v1/todos`. The manager sends one per write: the changes made within 100 ms of the first (`todosSettle`; one step of a task writes its to-do from several places) go out as one event, and a change made after it went out sends another, so the last read of every change starts after it (#5995). Separate writes still come in bursts: the App (`TodoStore`) and the web (`todosPushed` in `web/src/lib/store.ts`) keep one such read out at a time, and a push that lands while it is out asks for a single read after it.
  The same push also goes out when what a row's `view` files it under changes with no write to its to-do (#10226, `server/internal/assistant/todo_view_push.go`): its phase, section, reason, ask ids and the card each is answered by (`interaction`, #10465), the Inactive, Can wait and seen marks or its steps' count, but never its line's arguments, `since`, `next_change_at` or `rank` alone, so a working Agent's steps send nothing (the list's bytes still carry its latest line when a client reads). The one exception is the seen mark: the first step after the owner looked at a working row clears it and pushes once. The manager keeps what each to-do was filed under as first worked out after the last push. Three things work views out and compare: every list read; a change of the sessions on a computer where an open to-do has a run (its node's list, a card, a turn seen), after one second for the rest, recomputing only the open to-dos with a run there, the to-do each is a step of and its steps; and a timer at the earliest `next_change_at` (Just finished's 24 hours, 48 hours to the Inactive mark), recomputing only the to-dos whose moment passed, never more than once a minute and never sleeping more than an hour. The last two never copy the whole list: a failed start among them is held superseded from each to-do's title, PR, plan and close alone. A difference from the recheck or the timer sends one settled push. One a list read finds waits a second first, and a push meanwhile tells it, so changes coming one after another go out as one. Views worked out from to-dos read before a push change nothing. What the apps were told lives in the manager's memory only, so the first views worked out after it starts push once: a run may have come to ask while it was away. Old clients, which work rows out themselves, just read more often when it matters.
- Session-change push: when to-do/association changes affect sessions, assistant reports a new snapshot; hub compares which computer's sessions changed and re-pushes that computer's `sessions` event.

### Status codes and roles
- Missing title or malformed parameters: 400 Bad Request.
- Missing to-do: 404 Not Found. Old hubs without to-do APIs return 404; clients hide the entry point without an error popup.
- Linking to a completed to-do: 409 Conflict. Binding a chat thread another to-do holds: 409 Conflict.
- Assistant disconnected: 503 `assistant_offline` (to-do APIs and create/send with `todo_id`).
- Read-only role (e.g. paired Apple Watch, `role: "answer"`): every to-do write API (POST / PATCH / DELETE / PUT), plus create/send with `todo_id`, returns 403 Forbidden.

## Whole-project linking and automatic linking

### Whole-project linking
A herdr workspace can be linked as a whole to an unfinished to-do:
- On linking, batch-link every currently online Agent in the project (state not offline), `source = "space"`, `via = "<machine_id>/<space>"`.
- If the project is already linked elsewhere, unlink it first (remove the old to-do's space-linked Agents belonging to this project), then transfer to the new to-do.
- If an Agent in the to-do was dismissed, whole-project linking clears that dismissed state too.
- Unlinking deletes the workspace association and physically deletes Agent rows under this to-do with `source = "space"` and this project's `via` (manual/spawned Agents remain).
- Workspace writes (link, move, unlink, rename and task deletion) commit and publish their ownership changes in the same order. Session lookup happens outside that write boundary; a superseded request cannot later attach Agents to its former owner. Pending automatic Agent writes recheck current workspace ownership before persistence.

### Automatic linking with a project
When assistant receives a computer's session list (`sessions.changed`), it checks online Agents in whole-linked projects:
1. Agent currently has no other active to-do association (automatic rules do not take Agents away from other to-dos);
2. Target to-do has never had any record of this Agent (active, previously involved or manually removed all count as previously present, so no automatic relinking);
When both hold, automatically link to the to-do (`source = "space"`).
Automatic linking first updates assistant memory and reports to hub immediately (hub pushes that computer's session list again); database writes happen in background and roll back if they fail.
Previously hub linked it itself and included the association in that same session-list push; now it waits for the next push after assistant reports back (one bus round trip).
Automatic linking stops when a to-do is completed and resumes when reopened.

For renames through hub (shared with pin/mute's rename API), hub tells assistant (`todos.space_renamed`), migrating the space name in `todo_spaces` and corresponding `via` in `todo_agents` together. Assistant writes database first, then memory and broadcasts `{"type":"todos"}`. If the new name is already linked to another to-do (unique-index conflict), this project's old to-do link is invalidated and cleaned up, with a log entry. No migration if assistant is disconnected (same as "Known limitations", item 1).

## Following spawned Agents

For a supervised Agent's explicit handoff to a separate session, prefer `task_spawn` (or
`personad tool task_spawn` from its terminal; the same entry runs the Agent's other own tools, such as its to-do's
`todo_decisions`, #12096). The manager records the child on the caller's existing to-do with the
same supervisor before returning; the Agent never reads a hub credential or chooses a to-do ID. See
[Separate sessions within a supervised task](unified-entry.md#separate-sessions-within-a-supervised-task-5751).
Native Codex sidecar ancestry and UI folding alone do not create a to-do link. A standalone runtime
`create_thread` without parent metadata is not a supported supervised handoff.

Child Agents spawned by a linked Agent automatically join the same to-do, tracking their parent hierarchy:
1. **Parent marker**: an active Agent on an unfinished to-do has a `persona_todo_ref` marker on its herdr pane, value `<todo_id>@<machine_id>/<session_id>`.
2. **Dispatcher passes the marker**: after launching a child, the dispatcher reads its own pane marker and writes the value to the child's pane as `persona_from`.
3. **node reports, assistant associates**: when discovering sessions, node copies `persona_from` into `spawn_from` and reports to hub; hub passes the session list unchanged to assistant (`sessions.changed`). Assistant parses to-do ID/parent Agent; if unfinished, child has no active association and no history in that to-do, automatically link it (`source = "spawned"`, `via = "<parent_machine>/<parent_session>"`). Following does not depend on parent being online or on the same computer.
4. **Grandchildren follow**: after the child joins, node also sets `persona_todo_ref` on its pane; further generations follow the same mechanism.
5. **Consume the marker**: after child gets an active association, node's periodic reconciliation automatically clears its pane's `persona_from`, preventing mistaken relinking later.

### Dispatcher contract and example command
After launching a child Agent (on the same or another machine), the dispatch script should copy the marker as follows:
```sh
REF=$(herdr pane get "$HERDR_PANE_ID" | jq -r '.result.pane.tokens.persona_todo_ref // .result.pane.tokens.persona_from // empty')
[ -n "$REF" ] && herdr pane report-metadata "$CHILD_PANE" --source persona --token "persona_from=$REF"
```
Note: for a child on another machine, read the parent pane marker locally, then send the command that writes `$CHILD_PANE` to the target machine's herdr.

### botmux following
botmux sessions have no herdr pane or `persona_from`. node reads each session's Lark group (`raw.chatId`) and thread-root message (`raw.rootMessageId`) from `botmux observe --include-raw`, then reads `orchestrate-dispatch.json` in the botmux data directory (`SESSION_DATA_DIR`, otherwise the directory referenced by `~/.botmux/.data-dir`, otherwise `~/.botmux/data`): keyed by dispatched thread-root messages, with `orchSessionId` identifying the dispatching session (`botmux dispatch --session-id`). These three values report to hub with the session (`chat`, `topic`, `dispatched`) and are stripped before pushing to clients. After the first two rules, assistant tries two more, only for Agents with no active to-do and no previous record in the target to-do:
1. **Follow dispatch**: if the session's thread was dispatched with `botmux dispatch` by a session (on any computer; offline counts if still in its computer's list, i.e. offline no longer than `offlineWindow`) linked to an unfinished to-do, join that same to-do (`source = "spawned"`, `via = "<machine>/<session>"`).
2. **Follow the group**: among unfinished to-dos linked by other online botmux Agents in the same Lark group, if the largest count is at least twice the runner-up (automatic when only one to-do exists), join it (`source = "chat"`, `via` is group id; client shows **Same Group**). Ties or insufficient margin do not link; wrong links can be changed manually. Agents linked by this rule do not vote (otherwise one Agent could spread a to-do across the entire group), nor do Agents on computers with no list report for 10 minutes.

## herdr markers and reconciliation

Under herdr, to-do associations map to pane markers (shown in the sidebar):
- **Written markers**: for Agents linked to unfinished to-dos, node maintains two metadata tokens on their pane:
  - `persona_todo`: to-do title;
  - `persona_todo_ref`: `<todo_id>@<machine_id>/<session_id>`.
- **Clearing markers**: when a to-do completes, is deleted or an Agent is unlinked, node clears its `persona_todo` and `persona_todo_ref`.
- **Source/namespace protection**: all writes/cleanup use `--source persona`. Reconciliation only touches `persona_todo`, `persona_todo_ref` and `persona_from`, never user or other plugin metadata.
- **Periodic reconciliation**: assistant sends expected markers by session ID (node RPC `todo.sync_session_tokens`, via `device.call`): immediately for computers whose associations changed, no resend otherwise; on a new node/hub connection (`connected` in `sessions.changed` changes: node may have restarted, do not touch markers until received), resend all with the first session list on that connection, like hub's former immediate resend after node reconnect. node resolves live panes dynamically only from currently living sessions and host-reported current Agent sessions, compares herdr's markers with expectations, fills missing and removes surplus markers. If two sessions map to one pane, only the live one counts. node reconciles every 30 seconds; after herdr restart, pane-ID change or hot handoff, markers restore on the correct new pane without old exited sessions contaminating it.

## State calculation rules

Clients calculate to-do runtime state live from linked active Agents; it is not persisted. Use the first matching state in this priority order:

| Priority | State | Condition |
| :--- | :--- | :--- |
| 0 | Didn't Start | Agent for a task created from chat failed to launch; assistant ends the to-do (`done_at` + `start_error`, #1077); client shows failure/removal, not active. It still waits on the owner: the To-dos SOP counts it open while rule 1 keeps it in Waiting on you, and so do the assistant's snapshot (marked "（没开起来）" in its open index) and `todo_get` (#10365). A supervised task whose new tab is kept by its computer (`shell_waiting`, `agent_start_stalled`) is first remedied, still "starting" to clients ("Remedying a start" below) |
| 1 | Done | User marked done, or assistant judged a dispatched task complete (`done_at != null`; client shows **Auto-completed** for `done_by = "auto"`) |
| 1.5 | Timed out | `supervision.state == "timed_out"`: an unattended stalled terminal Agent was stopped after `max(60 minutes, expect_minutes × 3)` without supervisor action or real progress. The to-do stays open and retains the original session and workspace; **Continue** resumes that session through `POST /api/v1/todos/{id}/retry`, and a new turn clears the timeout. Runtime-owned sessions do not get this state (#4784; `docs/assistant/unified-entry.md` "Supervision") |
| 2 | Needs You | A linked active Agent is `needs_you` (waiting for question, plan approval or authorization) |
| 2.5 | Interrupted | A linked active Agent is stopped (`unread` / `idle`) with `turn_error`, no other participant is working or waiting to resume, and the task is not parked: a model-service failure interrupted the turn, or the hub reports a task turn with no output (`turn_error_kind` `no_output`, or `stopped` when Persona's Stop interrupted it, #10187, "Automatic completion" below), unfinished (#10399). **Continue** is only for recoverable errors or these silent turns. Account-sealed compaction marks the conversation invalid and directs the owner to a new conversation; it gets no retry. Closed tasks remain Done. A subscription usage limit is not this (the next row) |
| 2.6 | Usage limit | A linked active Agent is stopped with `turn_error_kind` `usage_limit`, and the reset is not known or not more than 10 minutes past. Not red and not Interrupted: "Usage limit · resumes <time>" when the CLI or the hub will continue it, "Usage limit · resets <time>" when nothing will. An older hub that does not send the kind stays Interrupted |
| 3 | Unread | A linked active Agent is `unread` (task finished, not viewed yet) |
| 4 | Active | A linked active Agent is `working` (working or starting) and not waiting (next row) |
| 4.5 | Waiting | A linked active Agent ended its turn but something brings it back (#3274): only background commands, subagents, Monitors or workflows it started still run (`background_working`), or the hub waits out another agent, a deploy / CI / a time, or a moment's model failure for it and wakes it (`work.phase` `blocked`, `work.on` `agent` / `external` / `transient`). A wait only the agent's own process ends (background work, a /loop) is dropped once the node lists the agent as cut off (`interrupted`): its process is gone, so the task reads Follow up and, when nothing else brings it back, Nobody is working on this (#5124). Shown with what it waits for (`work.line` / `work.wait`), its label naming what it waits on (web, #11090; `waitReason` in `web/src/lib/todo-wait-reason.ts`, first that holds): **Waiting on you** (等你) in the attention color when it waits on the owner by the sidebar badge's predicate (`waitsOnOwner`, "Sidebar and main navigation" below), so the label and the badge agree; otherwise, in a neutral color, **Waiting on background work**, **Waiting to retry**, **Waiting on a prerequisite** (another Agent, or its `prerequisite_blockers`), **Waiting to merge / deploy** (its `delivery` held by others, a fresh open PR, a park on a merge review, an `undelivered` check), **Waiting on something external** (what its Agent named in `work.wait`, a park on a person, an event or a date, a `waiting` check), else **Paused (nothing needed from you)**, never the attention color; iOS and Android still say 等待中 and follow; under way like Active in the dock, the board, Today and the brief. The hub's `taskState` sends `waiting` on task cards. On a hub with bounded lists the web reads a task's agents from the list's rows (the Agents window, and `taskRows`: the list's deltas and one exact lookup for an open task's agent outside it), not only from opened chats |
| 5 | Follow up | All linked active Agents are stalled (`idle` seen, `offline` not running, or launch failed) with nothing to bring them back |
| 6 | Not started | No linked active Agents |

- **Nobody is working on this** is not a row of this table: the hub works it out, since it needs to know whether the Agents' computers are connected and whether a wake is pending, and sends it as `orphaned` on the to-do ("Nobody is working on this"). A client that shows it puts it ahead of Interrupted and Follow up; one that does not shows the row above as before.
- **Own draft PRs** (#9426): the PR observer compares the draft author's login with the authenticated GitHub account
  (`GET /user` through the same forge). Matching open drafts carry `own: true` in their PR facts and emit `draft_pr`
  for the supervisor, even when the task is parked and no Agent is running. Other authors and unavailable identity
  never emit it; ready PR reads do not need the identity lookup. Each followed PR has its own pending signal.
  Before dispatch, the signal must still name fresh, open, own-draft facts at the same head and a PR the task and
  stage still follow. Busy supervisors keep raw signals pending, not rendered relays. The existing permanent
  task/PR/head fingerprint prevents repeated notices; a deferred delivery does not consume it. Handling lives in
  the canonical supervision instructions: check readiness or record why draft is intentional, without granting
  new ready/merge/deploy/contact authority. The observer does not accept, unpark or change the PR. Existing
  non-draft merge-wait classification is unchanged; this is not proof of a historical task's silence.
- To-do list ordering: unfinished first (same state by `created_at` descending), completed collapsed at bottom.
- Completion means the task is over: its Agents' sessions no longer say they currently work for it; **Reopen** to continue. A chat-dispatched task the hub completed also reopens when one of its Agents starts a turn again: an auto-completed one on any new turn (sent more with `agent_send`, or by the user; see "Stop Agents of completed tasks", #5892), since nobody accepted that close. A task accepted by a review (its supervisor's `task_review`, or the judge's own spot check, "Spot-check reviews" below) reopens only when its own conversation sent that Agent more after the acceptance (`agent_send` or `agent_interrupt` with `then` from the task's conversation, its supervisor or the background supervisor that follows it up for the main chat, or the owner's message on its card), whoever started the Agent (`task_plan`, `agent_supervise`, `agent_send` with a task, an Agent that became a task by itself, one linked by hand, `agent_start`). The background supervisor counts only for tasks whose ledger names the main chat, not for a task a side chat supervises. Such a send is noted before it goes and kept in the assistant's settings (`assistant.sends_out`), so a manager restart does not lose it (#7539); when the note cannot be saved, the send is not made and says so (try again). It reopens the task as soon as the Agent's computer takes it; a send that definitely failed (refused, or it never left the manager) reopens nothing; one whose answer never came, was lost with a manager restart, or that the computer could not confirm (its error says `delivered: unknown`, for example a Claude inbox holding the text for approval) reopens the task on the Agent's next turn, however late the Agent reads the text (a week at most), unless the task opened or was accepted again meanwhile or the Agent went to another task. A turn of the Agent that starts while the send is still out waits for its answer: when the send definitely failed (and no other send for the task is out), that turn was other work and the task stays closed; otherwise the turn and its end are the task's. A bare `/exit` or `/quit` asks for no work (the Agent's computer closes the Agent) and reopens nothing, and a message on a task's card reopens that task only. Accepting the task again, even while it is still closed, ends every send of more before it. `docs/assistant/todo-status-sop.md` ("Accepted tasks") has the details and the gaps that remain. Its Agent's other turns (its own timers and wakeups, other conversations, messages from other sessions, the owner typing in its session) leave the task closed, and their ends get no receipt, judgment or supervision signal: no new "judged done, waiting for your review" for a task already accepted (#6726, #7539). A judgment of work from before the acceptance that lands after it is dropped too: no check, delivery, stage or supervision signal from it. So is anything past the receipt of a turn whose end was being read when the task closed. **Reopen** and `todo_reopen` reopen any of them. Cancelled tasks stay closed when their Agent works again; only an explicit **Reopen** resumes their task tracking and supervision (#1851).
- **A hub restart during startup** (#3251, `assistant/tasks_recover.go`): a task start keeps the assistant busy from before its goroutine is launched until linking, failure bookkeeping or entering a retained-tab remedy has finished. The built-in manager therefore waits for it before switching binaries, subject to its existing 30-minute maximum (`docs/assistant/managers.md`). After a forced restart or crash, before its background loops begin, the assistant reads saved to-dos and plans. A started plan updated within `taskStartTimeout` (5 minutes) before this service was created, with an open task that has no agent, start error or recorded start remedy, is marked failed with an explicit restart reason. This includes read-only / plan-mode tasks and reused topic to-dos, whose plan relationship is saved in `ReuseTodo` instead of the to-do’s `PlanID`. The plan keeps the error, the conversation gets a failed receipt, and the supervisor receives an urgent failed-start signal (other tasks use the ordinary failure notification). Completed or cancelled tasks, any task with an agent, recorded remedies, older plans and starts admitted by the new service are left alone. The window uses the plan's saved update time, so approving an old draft or retrying a failed start can still qualify; historical dangling work is not replayed on deployment.
  The hub never resends these starts automatically: a node, especially a runtime bridge, may finish the previous request after its connection drops, and the saved plan has neither a start idempotency key nor a session / pane identity to adopt safely. The reason asks the supervisor or user to wait for the computer to reconnect and inspect its sessions before retrying. An offline computer does not delay recording the failure. No kept tab is invented for `beginRemedy`; existing remedies retain their normal expiry handling. Recovery requires the plan’s saved `TodoID`: it does not guess a task association if the process stopped before that link was saved.
- **Remedying a start** (#2570, `assistant/start_remedy.go`): when the new tab's shell stopped on a startup question (`shell_waiting`) or Claude's own screen stopped before its input box (`agent_start_stalled`), the computer keeps the tab for 10 minutes (`node/shellsettle.go`). For a supervised task the hub records this on the plan task (`start`: `state` remedying / started / failed, `attempt`, `by`, `machine`, `pane`, `until`, `code`, `reason`) instead of failing the to-do, and the supervision message carries the question, the tab's last lines and the retries left. The main conversation, or the task's current configured leader, may read the tab (`task_start_screen`), type into it (`task_start_keys`: any text up to 32 characters and keys, with a reason; the node takes them only into that kept tab while no agent runs there) and start again in it (`task_retry`, which also reopens a start that failed for good, in a new tab); at most 3 retries per task, and the hub never retries by itself. Each step is a `start_remedy` feed item. A retry that starts sends the supervisor a `started` signal. The start fails for good (`done_at` + `start_error`, the failed receipt, the bot's report) when the supervision turn that saw it ends with no retry running (the turn of the conversation that message went to, not another supervising conversation's, #4927), when the kept tab expires (checked on the supervisor's tick, so a restart catches up), or when a retry fails without a kept tab. If that turn never told the user (no `notify_user`, task review card or visible finish), the hub writes "Didn't start: <task>. <reason>" into the conversation and pushes it.
- User marks done while Agent is still launching (can take minutes on a busy machine; `done_at` written first): not **Didn't Start**, to-do stays done with no `start_error`; Agents that do launch join this completed to-do and are stopped by "Stop Agents of completed tasks" under existing rules (only after idle long enough) (#2954).

### Retrying on another launcher

A start can fail because of its launcher on that computer: the new terminal tab's shell cannot run it (`launcher_missing`
with `where: "terminal"`, for example a Persona-managed launcher whose `personad` the terminal's environment cannot see),
its health record keeps it off a fixed computer, or its error reads as its key, its model route or its subscription's
limit. Retrying the same task then fails the same way, and the health record of a terminal failure stays for 6 hours.
Since #10365 (`assistant/start_retry_launcher.go`):

- **Suggested, never swapped by itself**: such a failure fills the plan task's `retry_with`: the other launchers of the
  same computer it may start with, plain `claude` first when the computer has Claude Code, then the computer's own and
  the Persona-managed ones, only those running the same agent as the failed one, never the failed one or one its health
  record says cannot run there now, and no managed launcher while the terminal could not run `personad` itself (every
  managed launcher starts through it). The supervision message's failed entry lists them, and the task notice names the
  first. Any other failure (offline, a dropped link, a stalled tab) suggests none.
- **Asked for**: `task_retry` with `launcher` (and `model`), or the apps' **Use <launcher> instead** (`POST
  /api/v1/todos/{id}/retry` with `{"launcher","model"?}`, hello feature `task_retry_launcher`). The launcher is checked
  before anything is reopened: it must be on that computer, usable there now, and hold a read-only task read-only. A
  managed one asked for by name is taken even after `personad` was missing (only the suggestions leave it out): the
  terminal may have been fixed since. The task keeps its computer, directory and workspace (the checkout its
  first start made is used again), takes that launcher's default model unless one is given (a gateway's model id never
  carries over to another launcher), drops its tier, and its `why` says what changed. Its permission mode stays when the
  launcher runs the same agent as the one that failed (a Codex task in plan mode stays in plan mode on another Codex
  launcher), and is settled again for another agent, or when it was what Allow all gave the last one. The step is a
  `start_remedy` feed item with `launcher_from` / `launcher_to`.
- **From the launcher that ran**: a tier, a start-defaults policy or the `agent.new` binding may have chosen the failed
  start's launcher, which the plan does not keep (it keeps what the task named). The hub records the one that ran as the
  failed plan task's `error_args.launcher` (the node's coded refusal already names it for `launcher_missing`; the hub adds
  it otherwise, also with no `error_code`), and a retry compares with that: asking for another launcher pins it on the
  task and drops the tier, so the policy or the tier does not pick the failed one again; `launcher_from` and
  `task_retry`'s answer name the one that ran. Only the launcher the task names itself, with no tier and no model, is
  "the same" and changes nothing.
- **Nothing started, said so**: when another start of the task is on its way (the owner's Retry, `task_retry`, a plan
  taking the to-do over) or it started since, a retry asked for on a launcher starts nothing on it: the route answers 409
  with why (`assistant-tasks.retry_launcher_not_started`) rather than 200, and `task_retry` answers an error, records no
  move and takes its own remedy mark back. A plain Retry still answers the to-do as it is (a double tap starts one Agent).
- **The same launcher's tab**: a plain Retry of a start whose shell stopped on a question goes back to the tab its
  computer still keeps (`in_pane`, until `kept_until`), so an answer typed there is not lost to a new tab that asks
  again; once the tab is gone, a new one. A retry on another launcher always opens a new tab.
- **The words**: `launcher_missing` with `where: "terminal"` answers `action: switch_launcher` and a short `summary`
  (`docs/protocol/protocol.md`, "Errors"). The web's failed rows, the task panel and the to-do page read a failed plan
  task's code before its text (`lib/start-failure.ts`): a short line for a launcher the terminal cannot run or a
  workspace left in the way (`worktree_path_taken`), the hub's whole sentence under the details. Their buttons are
  **Use <launcher> instead** (when the hub suggests one and lists the feature), **Retry** and **Remove**; Retry no longer
  needs the to-do's `plan_id`. Apple and Android still offer Retry and Remove only.

### Answering a failed start's question

A planned task's start whose new tab's shell stopped on a startup question (`shell_waiting`: oh-my-zsh's update
question where the tab's environment could not turn it off, compinit's insecure directories, a passphrase) fails with
its tab kept by the computer for 10 minutes. Its plan task's `error_args` carry the question as the node listed it
(`line`, `screen`, `pane`, `kept_until`, `kind`, `choices`, `line_mode`, `secret`, `default`; `docs/protocol/protocol.md`
"Answering a start's question"). Since #10365 (`assistant/start_answer.go`) the owner answers it from the app instead
of going to the computer:

- **The route**: `POST /api/v1/todos/{id}/start/answer {"choice"}` (hello feature `todo_start_answer`), full devices
  only (403 `read_only` for a read-only or answer-only device and an extension's token). Only a failed start (done with
  `start_error`) whose last start stopped with `shell_waiting`, whose tab is still kept (`kept_until` ahead) and whose
  question offered that choice is answered; otherwise 409 `start_not_waiting`, `start_tab_gone` or `choice_not_offered`,
  nothing typed and nothing changed. A start the assistant is still remedying, or one starting again, has no question
  to answer here.
- **The node types it** (`start.answer {pane, line, choice}`, capability `start_answer`; an older node answers 409
  `node_outdated`, worded "update Persona on <computer>"): with `start.continue`'s guards, only an answer the question
  offers, only while that question is still the tab's last line, Ctrl-C alone into a password prompt, never "yes" to
  an ssh host key, Enter after a key a line-reading question echoes (never after a key a one-key question read). A
  question no longer on the last line (answered at the computer) gets nothing typed, and the task starts in the tab
  all the same. The node's reply says which (`{ok, typed}`; a reply without `typed`, from the first `start.answer`,
  counts as typed).
- **Then the task starts again in that tab**, as its Retry does there (`retryTaskWith` with `in_pane`): the same to-do
  reopened, no new tab. The node marks the tab typed (as `task_start_keys` does), so that start waits out the
  question's line, which stays the last one written until the shell draws its prompt, instead of refusing at once as a
  plain Retry into a tab whose question is still open does. A question after that one fails the start again with its own answers. The step is a
  `start_remedy` feed item `{action: "answer", by: "user", choice}`: the answer's id, never what a prompt asked for.
  When the node typed nothing (the question was answered at the computer, or gone by itself), the step is
  `{action: "answer_not_typed", by: "user", choice}` instead: the task's history and the supervising assistant never
  read the owner's answer as the one that took effect.
- **The web** shows the question card (`views/ShellQuestionCard.tsx`, loaded only for such a failure) on the failed
  row, the task panel and the to-do page while the tab is kept and the hub lists the feature, beside Retry, which stays.
  Apple and Android offer Retry only, so the failure's words (`shell_waiting`, also the assistant's notice and 督办
  detail) offer the answers only "where Persona lists them" and always the way at the computer: answer there, then
  start again.

## To-do titles

To-dos created by `task_plan` and `agent_start` (#2775), and by `agent_send` with `task` and `agent_supervise` (#3020), formerly used the prompt's first line as title, often starting with instructions to the Agent ("ultrathink ultracode 主人 11-05 19:47 的反馈，已授权直接开工：…", meaning feedback from the owner, authorized to start; "秘书派活（主人授权过…）", meaning assistant dispatch, owner already authorized), obscuring the task itself. Now two steps (`assistant/todo_titles.go`):

1. **On creation**, synchronously supply a cleaned title: remove leading keywords such as ultrathink / ultracode / think hard, provenance/timestamps such as "主人 11-05 19:47 的反馈" (owner's feedback), parenthetical notes such as "秘书派活（…）" (assistant dispatch) / "【…】", and "已授权直接开工" (authorized to start); truncate to 20 Chinese characters (20 Japanese, 40 characters for other languages). No model call, no delay to task launch.
2. **In background**, the small-task model (**To-do Title** `todo.title` in model configuration, inheriting the knowledge-organization category, through `models.complete` like chat titles `assistant.title`) reads the prompt and produces a short title explaining the task, replacing step 1. Keep step 1 if model unavailable, errors or empty result. Before replacement, verify title is still step 1's (conditional `UPDATE … WHERE title = old title` in database); never overwrite an intervening user edit. Prompts: `prompts/todo/title.md`, `title_input.md`.

Assistant-supplied titles in `task_plan`, `agent_send`'s `task.title` and `agent_supervise`'s `title`: if within the limit and without those prefixes, use as-is without a model; only first-line, overlong or prefixed titles use the two steps. Without a title, `agent_send` names the task from its text when the task still has a `done_when` or `expect_minutes` (with neither it is a plain reply and makes no to-do, #3386); `agent_supervise`, which has no instruction, keeps the session's title (else its label).

**Batch retitle existing to-dos**: `POST /api/v1/todos/retitle` selects only task-created to-dos (nonempty `origin`) whose title is still the prompt's first line truncated at dispatch: over the limit and a prefix of `notes` (truncated, with or without "…"). Short titles merely resembling prompts ("【紧急】修登录", "[Urgent] fix login"; "11/05 反馈：修登录", "11/05 feedback: fix login") count as user-created and stay untouched (to-dos do not record who named them; this is the most conservative possible judgment). Use model for each (4 concurrent), or step 1 cleanup without a model; again verify title unchanged before writing.

```sh
curl -X POST '<hub address>/api/v1/todos/retitle?dry_run=1' -H 'Authorization: Bearer <token>'   # Preview changes first
curl -X POST '<hub address>/api/v1/todos/retitle' -H 'Authorization: Bearer <token>'             # Then apply
```

## Automatic completion

Tasks dispatched from assistant chats (to-dos created by `task_plan`, nonempty `origin`) are automatically marked done by assistant, without individual user taps (except tasks supervised by main chat: completion judgment moves to "Pending review", and supervisor must accept with `task_review`, `done_by = review`, see `docs/assistant/unified-entry.md`, "Supervision"). Manually created to-dos (empty `origin`) never auto-complete; only user marking done counts.

With Agent tasks on (#3617, off by default; `docs/assistant/unified-entry.md` "Agent tasks"), an Agent started from an app's New Agent or by `agent_start` from any chat is on a quiet, supervised to-do with a nonempty `origin`, so it is judged here like the main chat's own tasks: an app's Agent gets its to-do at the first turn end that did work, and that stop is the first one judged. A manually created to-do an Agent is linked to gets a supervisor then, but still never auto-completes.

**When judged**: all task Agents stop (none working, waiting for user or carrying pending cards), at the same point assistant sends the done receipt to chat (`taskTurnEnded` in `assistant/tasks_follow.go`; one receipt and one judgment per stretch of work). The receipt's `done` is the end of that stretch, not of the task: the apps draw it "<task> stopped, not done yet" while the to-do is open and as done once it is, and the "Today" card lists as finished only to-dos that are done (#6153).

**By session and turn** (#5718, `server/internal/assistant/task_turns.go`): the receipt, the judgment and the supervision signal belong to the turn the runtime closed, not to whichever event told of it. The runtime's end of a turn in the transcript names it: the turn id of Codex's `task_complete`, else the id of the item that ends it (Claude Code's `turn_duration`, the interrupted notice of a user's stop). Each open task has one row in the `assistant.task_turns` setting: the session and turn taken up last, the stretch of work it closed, the judgment written for it and whether its signal was told.

- **Idempotency key**: (to-do id, machine id, session id, turn key). The receipt's feed id is a hash of it, so the receipt is written once whichever path writes it and whichever manager process (the `assistant_feed` primary key). The receipt's body names the run too (`machine_id`, `session_id`, #10465; the hash is unchanged), so a reader of the to-do's history can give each receipt to its run; `machine` is that run's computer's name, a label only. Receipts written before carry only the name, which on a turn ended by one of two Agents on two computers could be the other's; failed starts, which have no run, carry neither. A turn taken up again gets no second judgment: the one on the row is put back without a model call when a start was heard since (a stale `working` row after the end takes the check and the review wait off), or made now when a manager stopped between the receipt and the judgment. Its signal is told once: the row keeps the signal's kind and key and when a supervision message carried it, and a manager started again tells what was not told and does not repeat what was.
- **No working needed**: for a supervised task the supervision sweep (every 30 seconds, below) reads the last turn of the task's last Agent when all its Agents look stopped (`done`, `idle`, or `unknown`) and that row moved since it last looked. A closed turn the row does not have is taken up through the end's own checks: only when none of them refuses or puts off the end, and the transcript, read once more, still shows the turn closed, is the start nobody heard taken (what a `working` list would have done), then the receipt, the judgment and the signal as usual. An end that is not taken therefore leaves the task's stage, check and review wait as they were. An `unknown` status counts as stopped only for the row whose transcript showed the turn closed; a row is the same row while its status and its transcript's size (`rev`) are (its time counts only where it has no `rev`: a node's later list can carry a later time for a transcript that did not change). So a node that never lists a runtime as working, a manager that was down or disconnected when the turn ended, and lists that arrive out of order all end in the same one receipt, one judgment and one message.
- **Bound**: a turn that ended unheard gets its receipt within one sweep tick (30 seconds) plus two transcript reads (the sweep's and the end's own, 20 seconds at most each) of the node listing the end; with more than four such tasks at once, four looks go at a time and the rest follow on the next ticks. The judgment follows within its own limit (90 seconds, with one retry 3 seconds after a failure); one that does not land (the task's work changed while it was judged) is asked again on the next tick, then one and two minutes later, and when the third does not land either the supervisor is told `unjudged` at once. When the judge could not answer, the `unjudged` message says why: `判定模型未配置` when no model is set up for the judge (Settings › Model configuration; it is not asked again), `判定模型出错` when the judge's call or reply failed (#10435). The supervision message then goes out on the usual schedule (15 seconds to gather, at most one message per 2 minutes for a stop, per 10 minutes for a review; queued behind a running main chat turn).
- **A look that cannot finish** (the node does not answer the read, an Agent works or waits again, another look is at the same end, the judgment does not land) is tried again on the next tick, then 1, 2, 4 and 8 minutes later and every 10 minutes after that, while the row stays as it is and its node's connection is the same one. A row that moved, or a node that connected again, is looked at on the next tick whatever came before. Some states are not looked at at all, because looking cannot help:
  - **A usage limit that is waited out** (the CLI or the manager goes on after the reset): nothing is read and no start is taken until the wait is over; the turn that did not go on after all is taken up then.
  - **A computer that is not connected**: its rows are the manager's copy of its last list; nothing is asked until it is back.
  - **An end the task refuses as it stands** (a cancelled task that is still open, an Agent let go, a meeting's turn): recorded as seen after one read, not read again while the row stays, and not taken up if the task changes later.
  - **A turn stopped between its tools and its answer**: no receipt, as on the edge; left until its transcript is written to.
- **What it costs**: no call to a node unless an open supervised task's Agents all look stopped and the last one's row moved; then one `session.items` read of one turn, and a second one when the turn is taken up. Stopped sessions that belong to no open supervised task cost nothing, and after a manager start each open supervised task is read at most once.
- **A stop right after a reconnect**: a node that started over (an ssh node whose link dropped) can list a turn that still runs as stopped in the first list of its new connection. A working → stopped edge seen in that list is taken as the turn's end only once the session's transcript, read then, shows the turn closed; otherwise the row is kept as `unknown`, so its next `working` is the same turn, and the next working → stopped edge (or, for a supervised task, the sweep above) takes up its end.
- **Not recovered**: a turn of a task nobody supervises (it keeps the working → stopped edge), and a turn of a closed task (a turn found in a transcript does not reopen it). A turn that ended before the ledger was first kept, before its Agent was linked or before the to-do was reopened is recorded as seen and nothing is made of it. A turn whose transcript never gets an end record (an older runtime, a runtime that died before writing it) has no key: it is handled from the edge alone, as before.
- **A turn handled before it had a name**: the node can say an Agent stopped before the runtime has written the turn's end record (Claude Code writes it after its Stop hook; Codex in a pane is listed from the screen, not from the rollout), and the read at the end can fail. Such a turn is kept with the item that opens it (its prompt) and whether its receipt went out. Found later with its end record, it is that turn (the same opening item; where none was read, it began before the row was taken): it gets its name, and no second receipt, judgment or message.
- **Size and writers**: the setting holds one row per open task that had a turn; rows of closed tasks are taken off on each tick. A row is small (under 1 KiB usually, about 11 KiB at most: the judge's reason is 40 characters, a task has at most 6 criteria of 200 characters with 300 characters of evidence each, an error is cut at 300), and nothing caps the number of open tasks. The document is read once by a manager process and rewritten whole on a change, as the to-do stages are: a manager is one process at a time (a planned stop or switch waits for it to exit; its own service holds a lock). Where two overlap for a moment (a hub that was killed leaves its child running until it sees its input closed), an update of one can be lost to the other. The receipt is still written once (its id); the turn can be judged a second time, and its message is then held back by the 30-minute deduplication when the Agent's last words are the same.
- **Locks**: the ledger's mutex is held across its database reads and writes, so it is never taken while the task lock (`s.tasks.mu`, used all over the manager: starting tasks, routing messages, cards, stages) is held, nor the other way round. The one thing both sides need, the mark that a turn's end is being handled right now, is in memory under a small lock of its own that is held across nothing. A ledger write that does not come back (a full pool, a Postgres restart) therefore keeps the ledger's own callers waiting, up to that write's deadline, and nothing else (`turnsState` in `server/internal/assistant/task_turns.go`; `task_turns_lock_test.go`).
- **A dropped link at the wrong moment**: the stretch's receipt is reserved before the task's Agents are asked a second time whether they stopped. When that second look fails (the node does not answer, or one works again), the reservation is given back and the turn end is looked at once more 30 seconds later, so a link that dropped for a moment no longer leaves the stretch without a receipt and a judgment.

Normal receipts are written before judgment for both supervised and unsupervised tasks. At receipt time, the latest open to-do with a supervision ledger adds `review: {"state":"awaiting","criteria":N}` (the number of `done_when` entries, including zero), unless its effective supervision state is `needs_user`. This names Persona's next follow-up: `superviseJudged` signals review for finished work or idle for unfinished work; `needs_user` means the task is already waiting on the user. An accepted task that was reopened, or a cancelled task the user explicitly reopened, has an ongoing effective state and qualifies again. The receipt does not wait for the model or change the order of supervision signals. Failed / interrupted receipts carry no review. The web keeps the neutral stopped title for an open task and adds "Waiting for Persona's review", with a positive criterion count; completing the to-do hides this historical hint. Older receipts and clients remain compatible (#4893).

**How judged**: stopped is not finished; "not all changes done…" or "waiting for review" must not close. Assistant's judgment model (through hub model configuration, `app.call models.json`; **AI Twin Judge** `inbox.judge`, i.e. `inbox.judge_ai` in the manager's `manager.json`, inheriting `ai` if unset) sees three things: task title, dispatch requirements (to-do `notes`), each active Agent's latest turn (read via `session.items`: user's message and last complete reply; fallback truncated `last_text` in session list if unreadable). Later new requirements from user override original ones (already handled in earlier turns); if later messages merely confirm/answer a question ("OK", "👌", "Use A"), original dispatch requirements still apply (#1116). Model chooses one of five:

| Verdict | Meaning | Auto-complete |
| --- | --- | --- |
| `done` | Requested work finished, reply gives results, user need do nothing more, no waiting for others | Yes |
| `not_done` | Partial, failed, blocked, or only reporting progress/plan | No |
| `waiting` | Awaiting an external result (review, CI, someone else's reply, release queue), or no model is configured for the completion judge and the hub writes its own localized reason | No |
| `needs_user` | User must decide, supply information, approve, act manually or accept | No |
| `unsure` | Cannot tell | No |

- Caveats do not prevent completion: platforms without screenshots, unmeasured environments and reminders to user are not unfinished work. Routine waits after delivery (TestFlight external-group Beta review, CI rerun) do not count as waiting either; addressing App Store / Mac App Store review feedback then awaiting review outcome does count as `waiting`.
- Prefer leaving open: unavailable model, timeout, invalid JSON or verdict other than `done` leave the to-do open and log; receipt still sends. A verdict is kept as the to-do's `check` (below).
- No judgment for a turn interrupted by model service (#1516): if an Agent stops on an API error (`turn_error`: Claude Code's last message such as "API Error: …", Codex reported by node from this turn's error, #2185), receipt has `state: "interrupted"` (summary "Model-service error interrupted the task", original error in `error`); no judgment-model call or closing to-do. `done-check` directly returns `not_done` when the last reply is such an error.
- No judgment for a turn with no output either (#2349): latest stopped Agent's turn (node `session.items`, `turns: 1`) contains no assistant text, tool calls or images and no `turn_error` (model service returns 200 with empty content; Claude Code adds an invisible "no visible output" notice, retries, then ends silently). Receipt is `interrupted` (error "这一轮没有任何输出：…", "This turn had no output: …"), notification uses interrupted, no judgment or to-do close. Unreadable items (node unreachable/no items) or user pressing Esc ("已中断" notice, "Interrupted") do not count.
  The Agent's row says so too (#10187): the hub keeps the verdict for that turn (on the turns ledger, in the same write that takes the turn up, so a restarted manager still has it) and its session lists give the stopped row `turn_error` (the same sentence, in the user's language) with `turn_error_kind` `no_output`, so the task reads Interrupted (rule 2.5) on every client and in the snapshot, never "done, not seen". The verdict is made against the row re-read after the transcript (a row that moved during the read is looked at again) and holds while that row does: the same `rev`, or without one the same time (at most 2 seconds later) and last words. It ends when the Agent starts a turn or its transcript moves. Session Triage leaves such a row alone (no model-error card, no automatic Continue); `agents_list` names it "中断了，没做完" and lists it with what needs the owner (`state=needs_you`, not `unread` or `done`), as the snapshot's Agents do. A row cut off by a model API error keeps its old label there. "Continue" holds its guard (through reads that get no answer) until the verdict no longer holds for the row, by the verdict's own row whatever row it was picked at, and checks the turn again once it holds the claim.
- A turn Persona's own Stop interrupted is stopped, not failed (#10187): stopping a reporting conversation (`stopReporting`: the app's Stop, the plugin's `/stop`) interrupts its tasks' working Agents and notes each one with the task's stretch of work it ran in (taken back if the interrupt failed). The turn that stretch's Agent next ends, when the hub hears that end after the Stop and within 10 minutes of it, and it had no output, with or without the "已中断" notice, gets an interrupted receipt with `cause` `stopped` (summary "Stopped along with its conversation", not a model-service error), no notice or report (the stopped conversation hears nothing until the owner talks in it again), and its row `turn_error_kind` `stopped`: Interrupted with "Continue" on the clients, "stopped" in the snapshot and `agents_list` ("被停下了，没做完"). Its push, if any, carries no ⚠️; a voice run reports it stopped, not failed. A turn that ended before the Stop was sent, a later turn, and a turn whose end only the sweep found (no end heard) read `no_output`; so does such a turn whose Stop was sent before a manager restart and lost with it before the turn was classified (Stops are kept in memory only; a `stopped` verdict already made comes back from the ledger, and a Stop sent after the restart counts as usual). A look that takes up a Stop's turn end spends that Stop only, never a newer one. Verdicts and Stops are let go after their time (14 days, 1 hour) on lookup, by the sweep (the apps are told the rows that lose one) and on a restart, and with a session its computer's own list no longer has.
- Known limitations of the above (#10187):
  - Stop attribution and pairing a verdict with the transcript it read are best effort: the node gives no turn identity, so an Agent that ends its turn by itself just before the Esc reaches it, or a next turn written before the computer's next list, can still be taken for the interrupted or the read turn. A follow-up would return a turn id with `session.items` and with the interrupt's answer.
  - A crash between taking the turn up on the ledger and appending its interrupted receipt (any cause) can lose that receipt: the ledger recognises the replayed end as the same turn and writes none.
  - The finished push and Session Triage (a `WorkDone` from the turn's last words) can act on such a turn before its verdict exists, and a voice run can end before it arrives.
  - The agent lists' `is:error` filters (Rust core, web, Android, iOS) still count a turn Persona's Stop ended as an error.
- Cheap signals: final reply has a GitHub PR link and mentions merging (merged / 已合并 / 合入, the latter two meaning merged), or mentions TestFlight plus a build number. Assistant includes these as hints only, never enough alone for completion.
- Prompts: `server/internal/prompts/assistant/task_done.md`, `task_done_input.md` (`docs/assistant/prompts.md`).

**The check on the to-do** (#3180): every automatic judgment, supervised tasks included (before `superviseJudged`), writes `check: {"verdict", "reason", "at", "work_since"}` on the to-do, so an open task can say why it is not done: `verdict` as judged (a made-up one becomes `unsure`; with Delivery on, `undelivered` too), `reason` the judge's line, `at` when it was judged, `work_since` the start of the stretch of work it judged. It is written only while the judgment is still current (`taskCompletionCurrent`, and no new turn since under `completionMu`), so one overtaken by new work writes nothing; a reopen and an Agent's new turn clear it. Having no configured model writes a hub-generated `waiting` check with the same localized explanation shown in model settings; a model error still writes nothing.
- **Language**: the judge writes `reason` in the user's language (`{{if .Language}}` in `task_done.md`) without internal ids. The hub's own reasons (no reply read, a cut-off turn, a side-conversation reply with no evidence for this task) and the `done_reason` fallback for an empty reason come from the hub's i18n (`assistant-tasks.*`).
- **Storage**: next to `delivery` in the `assistant.todo_stages` setting (`task_check.go`, `reports.go`), no migration. It is additive: no field changes meaning, `task_cards` is unchanged, and clients that don't know it show the to-do as before.
- **Clients**: web `ProgressTaskRow` and Android `trayProgress` say "Stopped, not done yet · <reason>" for a task neither working nor done whose current check is not `done` / `unsure` (`docs/assistant/unified-entry.md` "Progress tray"). iOS doesn't draw it yet (#2879).

**Visible and reversible**: auto-completion writes `done_at`, `done_by = "auto"`, `done_reason`. iOS / Mac / web list/detail show **Auto-completed** beside Done; detail shows reason. **Reopen**, like manual completion, returns to unfinished, clears `done_by`/`done_reason`, records `reopened_at`. Before it clears them, a reopen is recorded as a `todo_reopened` work event, so the work stats can count the judge's closes reopened within 24 hours (`docs/assistant/agent-work.md`, "Evaluation").

**After reopening**: same stretch of work cannot auto-close again; only when an Agent begins a new turn after `reopened_at` (user sends again, Agent resumes) is completion judged again. After assistant restart the turn's start time is unknown; reopened to-dos are not judged then (prefer leaving open). Database write rechecks (`done_at IS NULL`, `reopened_at` before work start); user completion/reopen during judgment wins.

**After completion**: same path as user marking done: sessions lose to-do field, node reconciliation clears `persona_todo` / `persona_todo_ref`, whole-project linking/spawn following stop, Inbox AI twin no longer associates messages with it; assistant live snapshot marks task "Done (automatically closed after hub judged complete)", omitted after 24 hours.

**Diagnosis**: `POST /api/v1/todos/{id}/done-check` judges the same inputs, returns verdict only without database writes, `check` included (read-only role 403):

```jsonc
{"verdict": "waiting", "reason": "Waiting for App review", "would_close": false, "skip": "", "replies": 1, "signals": {"merged_pr": false, "build": false}}
```

Nonempty `skip` means automatic flow would not judge this to-do (`not_a_task` manual, `done` completed, `reopened` no new work after reopen), but API still returns model verdict for inspection.

**Re-check applies** (#4867): with the body `{"apply": true}`, which the web's Re-check sends, the check writes what it finds, as the end of a turn would.
This catches up after a turn end the hub missed, such as a restart mid-turn, and after a verdict that was only shown.
It runs only when the automatic flow would judge the to-do (no `skip`) and its agents are not working.

1. It reads the agents' last replies and moves the stage and delivery from them through the deploy check ("Deployed needs evidence" in `docs/assistant/todo-status-sop.md`). Deployed work is asked to be verified.
2. It judges, keeps the verdict as the to-do's `check`, and moves the task on: a supervised task found done waits for its supervisor's review, and the supervisor is told; an unsupervised one is closed.

The answer adds `applied` (whether it wrote) and `stage`. Without `apply` nothing changes.
With **Delivery** enabled (next section), response also has `delivery`; `verdict` may be hub's own `undelivered`.

### Judged against the brief (#3822)

The judge's input names the task's brief (`docs/assistant/unified-entry.md`, "Briefs") when it has one: the owner's
message that led to the work, verbatim with its day, and the criteria as logged scope changes left them, with the
dropped ones listed as no longer required. A take-over's notes are a hand-over prompt; the request and the criteria
are what the work is judged against. When the judge closes a task itself (spot-check reviews), the brief's `result`
records each criterion as it did for the supervisor's review.

## Delivery

(#3306, #12034, lessons in `docs/lessons/delivery.md`) Assistant setting `delivery_gate` (`assistant.delivery_gate` in `persona_settings`, `PUT /api/v1/assistant` with `{"delivery_gate": "off" | "merged" | "live"}`, and Web Settings › Assistant › Agent follow-up) controls the three-tier delivery closeout gate, while keeping full backward compatibility with the legacy boolean `assistant.done_needs_delivery` (`true` maps to `live`, explicit `false` maps to `off`, both unset defaults to `merged`):

- **`merged` (default)**: for supervised tasks with linked PR(s) (`pr_url`, review `link`, or saved repository `pull_request` links) and/or linked repository `issue` links, `task_review accepted` verifies that every PR is merged and every linked issue is closed before closing the to-do. Otherwise it refuses premature acceptance and instructs the supervisor to `park` the task (`waiting_on: "external_event"` with `evidence.kind: "external_event"`, `url`, `pr_event: "terminal"`, or `waiting_on: "someone_else"` with `evidence.kind: "merge_review"`) until merge and issue closure—so `sweepPRStatuses` / `parked_due` wakes the supervisor for final verification and closeout. `outcome: "cannot"`, non-PR/non-issue tasks, read-only tasks, and tasks whose brief/criteria explicitly opt into PR-only/draft-only scope are not held. Uncheckable/rate-limited GitHub checks return a temporary verification error without marking work unfinished; unreadable non-GitHub hosts add a reply note and do not block.
- **`off`**: closes strictly on `done_when` with no PR/issue or deploy delivery gate.
- **`live` (legacy `done_needs_delivery: true`)**: a code-change task is "done" only when live and tested, not when a PR is opened or merged. Judging only whether an Agent says finished leaves many tasks at "PR opened", "merged but off by default" or "not deployed" while showing Done. Enable via `assistant.delivery_gate` = `"live"` or legacy `assistant.done_needs_delivery` = `true` (`PUT /api/v1/assistant` with `{"delivery_gate": "live"}` or `{"done_needs_delivery": true}`); effective from the next judgment and next dispatched task. When `live` is active:

- **State criteria at dispatch**: for non-read-only tasks created by `task_plan`, hub appends delivery criteria to the Agent's first message (dispatch prompt, `prompts/assistant/task_delivery.md`): done = live and tested, with measurements;
  if rules permit self-merge/deploy/enable, finish the whole path; if current user approval is required (merging a repo not owned by user, production deploy, enabling an off-by-default feature, outbound messaging), stop one step before approval and state what needs approval;
  first try to resolve CI/other-person/environment blocks yourself; if impossible, state where and who can unblock. Fixed last line: `交付：<已上线并实测 | 停在 PR | 已合未上线 | 默认关待启用 | 不涉及上线>；卡点：…；谁来解：…` ("Delivery: <live and tested | at PR | merged, not live | off by default, awaiting enablement | no deployment involved>; blocker: …; who can resolve: …"). Read-only tasks omit it. While the triage's `closeout` switch is on the prompt also asks for a closeout, and the line is then the one just before that block instead of the last (`docs/assistant/agent-work.md`, "Closeout"); the line is read wherever it stands in the reply.
- **Judge one more thing**: the "Automatic completion" model also returns `delivery` (`live` / `pr` / `merged` / `off` / `none`), `gate` (blocking gate), `unblock` (`user` / `agent` / `other`), taking the Agent's line as authoritative unless contradicted by the body.
  If model omits it, use Agent's line; if neither exists, `none`. If `live` (or not judged) but reply mentions a PR without deployment or TestFlight build-number wording, treat as `pr` / `merged`, unless the Agent's line says live.
- **`live` needs evidence** (#3205): a `live` the judge (or the Agent's line) gives is checked against the running hub; the hub's commit not containing the PR's merge commit (or the check failing) makes it `merged` with the gate "等部署…" / "等确认部署…" (`docs/assistant/todo-status-sop.md` "Deployed needs evidence").
- **Only `live` and `none` auto-complete**: if `verdict` is `done` but delivery incomplete, change to `undelivered` and keep to-do open.
  Main-chat-supervised tasks (#3124, already not closed by hub) do not enter pending review; supervision message says "Finished but not live yet: …(at PR, blocked on '…')", for main chat to follow up or ask user approval.
- **A supervisor's `accepted` is held to the active delivery gate** (#6428, #12034, `assistant/supervise_review_delivery.go`): under `merged` (default), `task_review accepted` refuses while any linked PR is unmerged or any linked repository issue is still open (guiding the supervisor to `park` until merge/closure); under `live` (`done_needs_delivery: true`), it additionally requires the PR to be contained in the running hub (not merged, merged but not in the running hub, not named by its deployed-commits file, or check failing; where the running hub cannot be checked against, the PR still has to be merged, and PR-only criteria do not override `live`). Under `off`, no delivery gate runs. `outcome: cannot` and tasks with no linked PR or issue are never held.
- **A bare `accepted` is refused when the result does not settle the task** (#12026, `assistant/supervise_accept_guard.go`): nothing is written and the error names the fix when the review's note/reason/checks or the Agent's last reply show a closeout whose status is not done, a blocker only the owner can clear (missing owner-only information), or an inconclusive / ineffective / partly-done result. The supervisor must instead send `needs_user` (`why_owner: only_owner_knows` for missing owner information), `accepted` with `user_check: true` so the to-do stays in Needs you until the owner passes it (the intended path for read-only research and evaluations), or hand out a linked follow-up to-do first. `user_check` and `outcome: cannot` are deliberate closures the guard lets through; a question written only in chat text never reaches Needs you.
- **To-do shows the blocker**: judgment results except `not_done` are recorded in to-do `delivery` (`{"state", "gate", "unblock", "at"}`, settings `assistant.todo_stages` alongside stage strip, no new table); delivery replaces unconfirmed reply-keyword guesses (PR → review, merged → merge, off by default/live → deploy), but never rolls stored progress back or caps a deployment confirmed by the deploy gate. Explicit verification is recorded only after an acceptance is saved; a supervisor's `accepted` alone does not verify a high-priority task still awaiting its owner. All stage writes are forward-only except an explicit review withdrawing verification (`unverified`) from `verify`; rework, `cannot` and a requested user check do not count as verification.
  Web to-do rows add "At PR · Blocked on '…' · Needs your approval" while open and `state` is `pr` / `merged` / `off`; Android to-do rows (when the Agent is neither working nor waiting for you) and details show the same line (`Todo.hold` in `core:domain`); iOS / Mac do not render it yet (optional field, old clients unaffected).
- **The delivery hold follows the current wait**: the to-do and briefing combine the recorded delivery with current supervision and forge observations. An external park supplies its reason and puts the next step with someone else. A pending owner decision supplies its question. An answer, rework review or acceptance supersedes the previous approval, and a requested owner check remains available on its verification card. A ready PR resolves its draft approval, and a merge advances a PR hold to the deployment stage of work still to do. An independent owner decision stays actionable. The deploy check still uses the recorded delivery as evidence.
- **Batch user approvals**: assistant live snapshot lists delivery blockers after each task; open tasks with `unblock = user` get a separate "Waiting for user approval to go live" group (oldest ten).
  Assistant CLAUDE.md tells it to present these together in one message; after user approves in one reply, use `agent_send` to notify the corresponding Agents separately, rather than asking anew for every item.

## Spot-check reviews

(#3128, `assistant/supervise_sample.go`.) Every finished supervised task waits for the main conversation's `task_review`; with many tasks that makes the main conversation the bottleneck. The assistant setting `review_sample_percent` (0–100) lets the done judge close the tasks it can verify and sends only a share of them to the main conversation.

- **Default 100**: nothing changes. The judge is not asked for anything more and every finished task waits for `task_review`.
- **Turning it on**: tell the assistant (`assistant.review_sample_percent` in `persona_settings`, confirmation card on the phone), or `PUT /api/v1/assistant` with `{"review_sample_percent": 20}`; `GET /api/v1/assistant` reports the share in effect. It applies from the next judgment.
- **The judge's check**: below 100, the "Automatic completion" model of a supervised task with `done_when` also returns `checks` (per criterion, in order: `checkable`, `met`, `evidence`) and `delivery` (as in "Delivery", whether or not `done_needs_delivery` is on; it is not written to the to-do unless that setting is on). The hub matches the checks to the ledger's criteria by position. A task **passes** when every criterion is checkable (a command's output, CI, a link, a live reading — not a matter of taste or something only the user can confirm), met, with evidence, and the delivery is `live`. A task without `done_when` never passes.
- **Passed and not sampled**: the judge closes it as `task_review accepted` would: the ledger records an accepted review `by: "judge"` with the checks, the to-do closes (`done_reason` starts with 判官核对通过), the outcome goes to the project timeline, and the owner gets the usual conclusion card. The main conversation gets no supervision message for it.
- **Passed and sampled**: whether a task is sampled is a hash of the to-do id and the stretch of work, so the same work always gets the same answer; about `review_sample_percent` percent are. A sampled one waits for `task_review` as before, its supervision message starting with 抽查 so the main conversation knows the judge's check already passed.
- **Failed the check**: waits for `task_review` as before.
- **Never closed by the judge**: a rework round (the supervisor was promised the next review, and asked for more than `done_when` says), a task that was reopened or was ever accepted or cancelled before, and a task the supervisor reviewed while the judge was deciding. `live` counts only when the judge itself says so, never on the Agent's delivery line alone; checks that do not come one per criterion with each criterion copied in its place count as not met.
- When the independent review (`supervise_autoreview.go`) starts for a task, it runs first and its result waits for `task_review`; the judge's check does not close it.

## Close a task's tab after acceptance

When starting a new task from a plan, an owner API client can set `close_tab_on_accept: true` on that task in the
`tasks` array sent to `POST /api/v1/task-plans/{id}/start`. Omit it to keep the tab on acceptance. The plan shows the
recorded choice. To withdraw it, send `DELETE /api/v1/todos/{id}/terminal-cleanup`. The request returns
`{"terminal_cleanup":"skipped"}` until the manager has given the node its final authorization to close, including
while the node is still checking the tab. An authorized close returns 409. This is a per-task choice.

Only a supervisor or main conversation's `task_review` that saves `accepted` with outcome `done` uses that choice.
Tasks still waiting for the owner's verification keep their tabs. The original Claude Code or Codex tab must have
been created for this start on Herdr, with the same agent process still in its only pane. The node checks focus,
terminal viewers, drafts, queued input, interactions and work again. If there is no other tab in that workspace,
cleanup skips the close so the workspace remains open. Eligible cleanup uses the dispatch consent with no extra
phone card. The transcript, files and worktree remain available.

The `task_review` result and plan report `closed` when the node confirms the close, `skipped` when cleanup was
ineligible or could not be sent, and `pending` if the close may have been sent but its result is unknown. Repeating
the review reports the recorded result and does not send another close or conclusion. Ordinary archive-and-close
still asks for confirmation.

## Stop Agents of completed tasks

Completing a to-do stops Persona's automatic follow-ups for its linked Agents, including when a turn ends after
completion: no transient-error retry, usage-limit continuation, scheduled wake or new triage card. Triage may still
record the turn's work state. The check runs before scheduling and again before sending, including after a manager
restart. It applies to manually linked to-dos too, regardless of whether the Agent can be closed. Released or dismissed
links do not count, and an Agent linked to an open to-do can still receive follow-ups. Deleting a to-do leaves its Agents
unaffected. Direct chat messages and `agent_send` still work; a user-completed to-do stays done until explicitly reopened,
while a hub-completed task reopens on new work as described below.

After a task dispatched from assistant chat (nonempty `origin`) completes—manually or automatically—its Agent stops running (with Agent tasks on, `docs/assistant/unified-entry.md` "Agent tasks", that includes the Agents started from an app or another chat, whose to-dos have an `origin` too):
assistant checks every minute (`assistant/tasks_close.go`, reading hub's App-facing session list through `sessions.list`); once task completion and Agent inactivity both reach 3 minutes (`taskCloseIdle`, measured from the latest of completion time, last activity and when the pass first saw the Agent running), it asks node to stop it (`session.stop` with `retire`, `node/retire.go`):
the Agent process quits (Ctrl+C twice, up to three rounds, until the engine no longer shows the Agent in its pane) and **its terminal stays** (unless the owner turned on `close_ended_terminals`, #10355: then the same idle Agent is closed with `session.retire` and `close_terminal`, recording `task_completed`, as "Archive and close" closes it without archiving): the tab keeps the shell the Agent ran in, ending with Claude's "Resume this session with: …". Stopping never closes it (#4754); the node closes the terminal itself only once it has sat unchanged for the grace period (#10111, `docs/integrations/engines.md` "Agents run in a terminal"); an Agent that does not quit is reported (`not_stopped`) and left running, never closed to make it go.

**What stays**: to-do Agent record (machine, session id, directory) remains, not released; node's launch information (launcher, directory, model, hub `node_sessions`), transcripts and the terminal remain.
Results still read from transcripts (receipts, `agent_read`, chat page); Unread Agents may also stop.

**How to reuse**: a stopped Agent is read-only (#4754, `docs/integrations/engines.md` "Agents run in a terminal"): a message to it—`agent_send`, the task's card (`route`), the chat page—is refused (`agent_stopped`), nothing typed. The user brings it back with **Resume** on its terminal page, and the assistant with an explicit resume (below), both in the shell it left when that is still there (else a new tab), with its original launcher, directory and workspace:

| Agent | Resume method |
| --- | --- |
| Claude Code | `<launcher> --resume <id>`, with original permission mode, thinking effort and model |
| Codex | Launcher arguments (with original model substituted) `resume <id>`, through `personad codex-start` |
| Compatible Codex forks | `<launcher> resume <id>` |

**A resumed Agent stays** (#10311): an Agent of a completed task that the pass saw stopped (or stopped itself) and that runs again was brought back on purpose, by the owner's **Resume** or a message that resumed it. The finished-task rule leaves it running however old its last step is (a Resume adds none), and the idle rule below stops it once it has been still for `idle_close_hours`. When its task reopens and is completed again, the rule starts over. The pass keeps what it saw in memory, as the idle rule does: after a manager restart a running Agent counts from when it is first seen, so a resumed one is never stopped on the first pass. An Agent still launching when its task was completed (#2954) is not a resume.

**The assistant's resume** (#8099, `assistant/agent_resume.go`): `agent_send` with `resume: true` and `resume_why` resumes a stopped Agent through the node call the user's Resume makes (`session.start` with `resume_session_id` and `resume_automatic: true`, so the node fills in its launcher, directory, model and permission mode, and uses the shell it left), with the text as its first message. It is for follow-up work that depends on that Agent's context (it has just found the cause and should now fix it, rework of its own work, the owner asked for "the one with the context"); unrelated work or an Agent that went off track get a new Agent (`agent_start`, or `task_plan` with `continues`), and when unsure the assistant asks the owner to choose (`prompts/assistant/claude_md.md`). The resumed Agent is never unsupervised: it is on an open task of the calling conversation already, or the call gives `task` (main conversation) and becomes one as any `agent_send` hand-off, its card marked resumed (`wakeResumed`). The owner sees it: the phone's confirmation (when outbound confirmation is on) and a `routed` line on the task's card name the Agent and the reason (`assistant-tasks.resume_note`). It is refused, with nothing started or sent and "start a new Agent" as the suggestion, without a reason, without a task to be on, for another conversation's or the owner's own task, when its computer is offline, when its context is nearly full on a runtime Persona cannot compact (below), and when the node refuses the resume (its error is passed on). Persona's own follow-ups (rework, relayed answers, digests, channel messages) still never start a stopped Agent. Rework of a retired herdr leader is the task-scoped exception: it resumes the same session in the recorded task workspace (#4786).

**A nearly full context is compacted, not replaced** (#11137, `server/internal/node/compact_before_send.go`). A context at 85% of its window or more (`proto.ContextNearlyFull`, from `context_tokens` / `context_window`) is no reason to lose the Agent's work. The assistant's resume then starts the session without a first message and sends the text with `compact_if_full`; an `agent_send` to a running Agent the hub sees nearly full sends that flag too (with a 15-minute wait instead of the live send's). The node decides when the text would go in: a Claude Code or Codex Agent that is nearly full gets its own `/compact` first (a Codex on its app-server `thread/compact/start`), and the text goes in once the compaction is over. Over means the transcript has a compaction record written after the `/compact` (Claude Code's `compact_boundary`, a Codex rollout's `compacted` / `context_compacted`) and the Agent no longer works; there is no fixed wait. It failed when the Agent came back to rest without such a record, wrote an error, did not begin within 3 minutes, stopped, or wrote none within 10 minutes. Then nothing is sent and the refusal (`compact_failed`) gives the reason, and only then is a replacement suggested. An Agent mid-turn that is already nearly full keeps the message on its node instead of in the runtime's own queue: once the turn ends the node checks again, compacts if still needed, then sends (`compact_after_turn` in the answer). One that cannot go in then leaves the session waiting for the owner, with why. Below the threshold everything is as before. Codex counts in all three forms Persona reaches it in. In its terminal, `/compact` is typed once its TUI shows the input box: a Codex that `codex resume <id>` just brought back reads its whole rollout first, so the node waits for its screen to show the box, for at most 3 minutes. A thread nothing runs (`codex_history`) is resumed that way in a new tab. Codex can come up behind its own update offer, whose default `Update now` installs the update and quits Codex. Every resume skips it with Esc (`settleCodexStartup`), as a new start does (#11323). Before `/compact`, the offer is skipped again if it is still there; any other dialog with numbered options is never taken for the input box and refuses with its first line (#11316). A `/compact` that was typed but whose screen did not confirm it in time is not a failure: the transcript decides. An agent that quits meanwhile is reported with the step and its terminal's last lines. A Codex on its app-server gets `thread/compact/start`. For Codex, a transcript written to after the `/compact` keeps the wait going even when its status shows no work. A reply that sees at most 60% of the context from before the `/compact` also counts as the compaction. Other agents have no compaction Persona can run: the Codex App's chats (the App takes no `/compact` from Persona and compacts on its own), a Claude outside Persona's terminals (`claude_bg`, `claude_desktop`, `claude_cli`: their inbox runs no command), pi, agy, opencode, cursor, and runtimes such as Paseo. A running one gets the message as before. Resuming a nearly full one is refused, and the refusal says which of these it is.

**Stop provenance and recovery** (#8214): only `idle`, `task_completed`, `restart`, `resume_failed` and `compact_failed` stops permit this assistant path. The node persists the confirmed stop cause in existing session state; a user close (including a kept terminal or `/exit`) revokes eligibility, and observing a running session clears the old cause. A restart status, an old start timestamp or a lost connection alone cannot prove the cause: an unrecorded crash remains unknown and needs the owner's Resume. Since #11441, three non-user stops are recorded. `restart`: the node records when it last saw each Agent running (`ran_at`, written at most every 5 minutes); a session the restart cut off (`markInterrupted`) that was seen running within 10 minutes before this node started counts as stopped by the restart. That window is a trade-off: an Agent that quit by itself in the last minutes before a restart is counted as the restart's, and a machine that was off for longer leaves the cause unknown. `resume_failed`: the assistant's own resume (`resume_automatic`) refused with nothing run (`delivered: none`, no kept tab) and the Agent not running. Any other failed start stays unknown: a line typed into a shell, a stalled Agent or an unanswered call may still bring it up, and a second resume must not start it twice. `compact_failed`: an Agent that quits while the node compacts it before a message. Neither is the user's doing, and the earlier stop already permitted the resume, so the assistant may try again. A user close during the attempt still wins, since it takes the same recovery lock and writes `user` after. Legacy rows, unknown/future causes and missing provenance stay read-only to the assistant. User closure first reads its saved stop back through `state.load`; a resume similarly saves and verifies unknown provenance before starting, so an interrupted attempt cannot reuse the previous idle stop (a failed one is `resume_failed`, above). A failed or unsupported save returns `stop_not_saved` without touching the terminal. Monotonic `stop_cause_at` revisions keep late metadata writes from reviving an older cause. The node rechecks the cause under the same per-session recovery lock as user closures, so a cached eligible row cannot undo a later close. Resumable `codex_history` rows enter this path only with read/terminal capabilities and no subagent; other read-only sources stay refused. The owner's explicit Resume is unchanged. Both the node and the managers carrying its provenance must support this addition; a component that drops it fails closed, not open.

When every Agent of a task has stopped, the user's message on the task's card (`route`) or the task's **Retry** starts a new Agent for it instead (`assistant/tasks_successor.go`): on the computer, in the directory and with the launcher of its latest Agent, linked to the to-do, its first message the user's after who worked on the task before and that Agent's last reply; the `routed` feed line carries `new_agent`. Every `routed` line written since #10465 names the run it reached in `machine_id` / `session_id`: the owner's words, an answer the hub worded for them and Persona's own lines alike, the new Agent's for a message that started one (absent when its start named no session). A message on the card of a task the hub closed (`done_by` `auto` or an accepted `review`, not cancelled) reopens it once the new Agent started (or may have: the start's answer never came), so that Agent's work is the task's; a start that definitely failed (its computer unreachable, its launcher refused, or it never left the manager) leaves the task closed (#7539). Persona's own follow-ups (a supervisor's rework, relayed answers to decisions, acceptance or conclusions) start nothing and are refused (`route_agents_stopped`), and so is a bare `/exit` or `/quit`: what it would close is closed already (`route_agents_exited`). One new Agent per task at a time (#8272): a second message while it is still starting (a follow-up line, a bare `/exit`, or the same one sent again after the phone stopped waiting) waits for that start and is then sent to the new Agent. If the first start was definitely refused, the waiting message can start the Agent itself. If the first message may already have reached a new Agent, the manager keeps the task open and both callers are told to check its Agents before sending again (#11245). A start still going after its own bound plus a minute answers `route_starting` (nothing sent).

When a resumed Agent starts a turn, its completed to-do (a chat-dispatched task it still belongs to that the hub closed: `done_by` `auto`, or an accepted `review` whose conversation sent the Agent more after the acceptance, see "State calculation rules" above; user-completed and cancelled tasks stay completed) reopens, as **Reopen** does (`reopened_at` recorded): the task shows as in progress, the turn's end gets its interrupted or done receipt and notice as usual, and completion is judged again (#5892). If the to-do is completed again, the Agent stops again after 3 minutes idle.

A cancellation stays final whether the Agent receives a user message, an `agent_send`, or continues after a background job, before or after its idle stop. It produces no new task receipt, completion judgment, supervision signal or automatic triage follow-up while the to-do stays closed. This also applies to older cancellations stored as `done_by = review` with a `cancelled` supervision ledger. The user can still explicitly **Reopen** the task. Cancelling a task stops its Agents right away, working or not (`session.stop` without `retire`, `assistant/supervise_leader.go`), keeps their terminals and archives them; a session with no terminal (another tool's, an engine that runs Agents itself) is closed as before.

**A herdr leader task's workspace closes too** (#4786): the leader and its workers share one workspace named after the
leader task. Once that top-level task is accepted or cancelled and every Agent under it has retired, the same close pass
closes the exact workspace recorded for the task (`docs/integrations/engines.md` "Task workspaces"). Any shells left in
that task-owned workspace go with it; the Git checkouts and transcripts stay. User-opened workspaces and other tasks'
workspaces are never closed, and repeated close passes do nothing.

**Do not stop**: working, waiting for user (questions, plans, permissions, any dialog, pending cards), unknown engine state; queued messages, background shells, running sub-Agents, `/loop`, listening ports (development servers); linked to another unfinished to-do; assistant chats; sessions managed by other tools (external Codex app-server, runtime, daemon, pi) or by an engine that runs Agents without a terminal (Paseo, Cindy); not started by Persona (the user's own Agents are theirs to stop); Agents other than Claude Code, Codex and compatible Codex forks.
node rejects these (`not_retirable`), assistant records them and does not ask again for 10 minutes if Agent unchanged (`taskCloseRetry`, then retries because node may have upgraded). Old nodes not recognizing `session.stop` are likewise treated as refusals, so nothing is closed while the hub is updated first; after the node upgrade, stopping resumes within at most 10 minutes. A node since #4754 answers an older hub's `session.retire` the same way: it stops the Agent and keeps its terminal.
Agents linked to no task (user-created, `agent_start`, inspection sessions such as herdr-leader) are not managed by the finished-task rule; the idle rule below covers the ones Persona started.

**Idle Agents stop too** (`assistant/tasks_idle.go`, #2784): in the same minute loop, an Agent Persona started (including a stopped one a message resumed, `agent_send` or the chat) that has been still for `idle_close_hours` (assistant setting, default 12, `0` turns it off, `GET`/`PUT /api/v1/assistant`) is stopped like a finished task's, by the same checks and the same `session.stop`, and keeps its terminal. The idle time counts from the later of its last activity and when the hub first saw it running, so a freshly resumed Agent is not stopped at once (and after a hub restart the clock restarts). Besides the "Do not stop" list above, it is left running when its work state is blocked (on the user, another Agent, CI or a deploy) or has a wake due, and when it belongs to an open task, unless that task itself has had no update for three times the idle time (stalled or never accepted). Transcripts, launch state and the terminal stay; it is read-only from then on, and the user's Resume, or the assistant's explicit resume, brings it back.

**`/exit` from the assistant**: `agent_send` with only `/exit` or `/quit` stops a running Agent as `session.stop` does (its tab stays, holding the shell) instead of typing it in; to an Agent that is not running it does nothing, so a stopped Agent is not resumed in a new tab only to quit there.

**Terminals stay** (`node/personatab.go`): every tab Persona opens for an Agent carries the herdr pane token `persona_tab` (the session id when known). When its Agent exits, on its own (`/exit` typed by hand, an API error it gives up on, a launcher that quits) or stopped as above, the tab keeps its shell. Nothing closes it automatically: the ten-minute sweep of tabs left with a bare shell (#851) is gone (#4754). The user closes a terminal like any tab (on the computer, or a space's or tab's menu in the web's terminal list); the user's **Close** and **Archive and close** on a session still close its tab, and so does a finished review's reviewer, an internal helper (`assistant/supervise_autoreview.go`). Guards: `assistant/terminal_guard_test.go` pins the functions that ask a node to close, `node/terminal_guard_test.go` the functions that close a pane.

## Closed sessions archive themselves

#3618 (`assistant/agent_archive_auto.go`). A stopped or closed Agent stays in the lists as not running, so after a few weeks most of the list is finished tasks' sessions that no longer run and the Agents that matter are hard to find. Every five minutes, in the loop that stops Agents, the manager archives a session when all of these hold:

- it is **closed**: its Agent runs in no host (its terminal may still hold the shell it ran in, #4754): no `pane_id`, no `host`, and it is neither working nor starting. The status does not decide it. A closed session reads `offline`, but just as often `interrupted` with state `unknown`: a node that restarts marks the sessions it had running in a pane as interrupted so the apps offer **Continue**, the mark stays until a message resumes the session, and the unified state has no value for it. Some keep the `idle` or `unknown` their host last reported. A session another tool lists (`source_kind`) counts as closed only when that tool says `offline`;
- it has been **idle for `archive_closed_days`** (assistant setting, default 3, `0` turns the pass off, 0–3650, `GET` / `PUT /api/v1/assistant`), counted from the latest of its last step, the moment its latest to-do was done, and the last time its archive state changed (so a session the user restored is not taken straight back);
- it is **on no to-do, or every to-do it is on is done**.

It uses the archive the apps use ("Agent session archives" in `docs/protocol/protocol.md`): the session moves under Archived, nothing is deleted, the tool that owns it is asked to archive it too where it can, and new activity (the user's Resume) restores it for good. At most 20 sessions are archived per pass, so a long backlog clears over a few passes.

Never archived by this pass: a session still in a host (a pane or an engine host), including one whose state the host cannot tell (`unknown`); one working, starting, or with background commands, subagents, workflows, a `/loop` or a server running; one with a card waiting for the user or queued input; one the manager is to wake or continue, or that waits on something the manager follows (`work.phase` `blocked`, or `work.wake_at` set); one linked to an open to-do; one the owner filed under a current direction (#11515, `docs/assistant/unified-entry.md` "The direction tree": once its direction ends it may be archived again; the owner's own Archive still archives it, and a session this pass archived before #11515 stays archived until the owner restores it); an assistant conversation; a review's reviewer; a subagent's row; a session another tool owns (`source_kind` set: archiving it would also move it in that tool); a desktop app's session (`agent_surface` `desktop`): the node lists the Claude desktop app's sessions as its sidebar does, whatever their age (#3304), but sets `source_kind` only while the app has one open, so only an archive in the app or the user's Archive here takes one off; with no to-do, one whose last reply asks the user something nobody answered (`awaits_reply`). Computers that are not connected are skipped, nothing runs until the to-dos are loaded, since they say which sessions open tasks count on, and a pass archives nothing while the direction filing book cannot be read, since it says which sessions a direction holds. Each candidate is looked at again just before its archive is written, with the to-dos and the book read again.

## Nobody is working on this

#3618 (`assistant/tasks_orphan.go`). An open task can lose its Agent without anyone noticing: the Agent ended on a model error nothing retries and its tab was closed, the user closed the tab, or the computer went offline. The task then still reads as in progress. Once a minute the manager looks at every open to-do that has Agents; the to-do is **orphaned** when every active Agent on it is gone and nothing pending brings one back.

An Agent is gone when its computer is not connected, the computer no longer lists the session, or the session is closed in the sense of "Closed sessions archive themselves" (no pane and no host, not working or starting, whatever its status reads: `offline`, `interrupted`, `idle` or `unknown`). For 2 minutes after its computer's node connects again, none of that computer's Agents is gone: a node that started over (an ssh node whose link dropped) lists its Agents again only once it has found them. It is not gone, whatever its status, when it is an assistant conversation, is starting, has a card waiting or queued input, has a wake or continuation pending or waits on something the manager follows (`work.phase` `blocked`, or `work.wake_at` set), or waits out a subscription usage limit.

`GET /api/v1/todos` then carries `orphaned: {"reason", "since"}` on the to-do, and the apps are told to read the to-dos again (`{"type":"todos"}`) when it appears, changes reason or goes. `since` is when the manager first saw it so (it restarts with the manager). `reason` is the first that applies to any of its Agents:

| `reason` | Meaning |
| --- | --- |
| `error` | An Agent is closed and its last turn ended on a model error (`turn_error`) that nothing is set to retry |
| `offline` | An Agent's computer is not connected. Reported only after the computer has been away for 10 minutes, so a dropped link or a node restart flags nothing |
| `closed` | The Agents are not running: stopped by the finished-task or idle rule ("Stop Agents of completed tasks"; their terminals stay) or closed by the user, and nothing is set to wake them |

Not orphaned: a done to-do; one with no Agent yet (not started, or its start failed: "Remedying a start"); a supervised task waiting for its review or for the user's decision, which waits on them and not on an Agent. A to-do whose computer is connected but could not be asked this minute keeps what was found before.

The assistant's snapshot says it on the task's line, and a supervised task's supervisor gets the `orphaned` signal once (`docs/assistant/unified-entry.md`, "Supervision": the supervisor loop's signals). Clients that do not know the field show the to-do as before; showing it on the task card and row is each client's own work: the web (`docs/web/web.md`), Android (`docs/android/android.md`, "Closeout, decisions and tasks nobody works on") and the iOS app (`OrphanedLine`, `docs/apple/ios.md` "Closeout, orphaned tasks and answerable decisions (#3612, #3618, #3804)") do.

## Decision records

A standing authorization answer records an Agent decision naming the grant, original user words and source. It is
committed in the same transaction as the hook's resolved question or plan, before the answer is delivered. It is not
presented as a fresh user click. The grant itself is managed through the main conversation's `persona_settings` key
and the list/delete API in [Unified entry](unified-entry.md#standing-authorizations); established task decisions keep
their provenance even after that grant is revoked.

The owner's own decisions (`source` `card`, and the `manual` ones made by choosing a decision's option) are also what
a suggested rule is counted from: after the same go-ahead three times in 14 days, the next decision offers to make it a
standing authorization
([Unified entry](unified-entry.md#a-rule-after-the-same-answer-three-times-4929)).


The costliest long-task mistake is an Agent forgetting a decision already made: asking again or silently overturning it (#1618). Decisions scattered across Agent chats disappear when switching Agents or compacting, so collect them by to-do:

- **One decision** = question + choice + reason + time + provenance (asking Agent, answering card).
- **Automatic**: when user answers Claude Code's choice question in App (`question` card, `AskUserQuestion`) and the Agent is linked to an unfinished to-do, record each answered question (`source = "card"`; hub emits `interaction.resolved`, assistant records; nothing recorded if assistant disconnected). Do not record authorization, plan approvals, terminal dialogs or ignored cards; duplicate reports of a card record once.
- **Manual**: **Decisions › Record one** in to-do details.
- **From the Agent** (#5279): an Agent on an open to-do has two MCP tools of its own (`mcp/todo/`, `agentToolNames` in `assistant/agent_control.go`). `todo_decisions` gives the effective decisions with who made each (`by`: `user`, or `agent` for `agent` / `outcome`), to reread after compaction; `todo_decision_add {question, choice, reason?, supersedes_id?}` notes a call the Agent made (`source = "agent"`, its machine and session as provenance), at most 10 in 10 minutes per Agent; it may replace an Agent's decision, never the user's (it is told to ask them). The to-do is always the one the calling Agent works on (node passes its pane's session, as for `report_to_supervisor`; an Agent without the Persona MCP calls both through `personad tool` from its pane or Codex thread, resolved the same way, #12096); an Agent cannot read or write another to-do's decisions, and outside an open to-do both say there is none. A continuation's replacement reads the decisions the to-do kept; the Agent it replaced, released, has none left. Handoff context marks these as the Agent's, not the user's.
- **Supersession**: a new decision can **Replace** an earlier one (`supersedes_id`), keeping the old one struck through; only unsuperseded decisions are effective. PATCH can mark/undo later corrections. Only earlier decisions in the same to-do can be replaced, preventing cycles.
- **Hand to Agent**: when `POST /api/v1/sessions` `prompt` or `POST …/messages` `text` carries `todo_id` (all clients' handoff does), hub asks assistant (`assistant.todo_handoff`); assistant prepends effective decisions as `<persona-context kind="context" title="待办 · <title> · 已定的决策">` ("To-do · <title> · Established decisions", prompt `server/internal/prompts/todo/decisions.md`), no client change needed; send unchanged without decisions. For a take-over, the handoff also reads the effective decisions of its actual `continues` ancestors (never every to-do on the brief), oldest first, with their original question, choice, reason, time and provenance. Each to-do's effective records appear once; conflicting records on different to-dos remain separate history rather than superseding one another or creating an authorization. Missing, cross-brief or cyclic links stop the ancestor walk. On read failure (database error), still send and only log.
- Recording/superseding updates to-do `updated_at` and broadcasts `{"type":"todos"}` so clients refetch decisions.
- iOS / Mac (`apple/Persona/Views/Todos/TodoDecisionsSection.swift`, model `TodoDecisionsModel`, wire `apple/Shared/TodoDecisions.swift`): the same Decisions section in to-do details, under the notes: **Add** records one, **Revise** records one that replaces it, the row's ⋯ marks it as replacing an earlier one or undoes that, **Full History** shows the replaced ones struck through. Read again whenever the to-do's `updated_at` changes; hidden on a hub without the route (route-level 404).
- **How many show** (#6447, web `DecisionsSection` with `shownDecisions` in `web/src/lib/todos.ts`; iOS `TodoDecisionsLogic.shown`): the first five, oldest first, with **Show all N** under them and **Show the first 5** to go back; the header's fold-all button (the Agents title row's) folds the list away and **Expand all** shows it whole. The header's count is the decisions in effect, whatever is shown, and folding asks nothing of the hub. Nothing is stored: each to-do opens at the first five, and recording or revising one shows the whole list so it is in view.

- Android (`android/feature/agents/src/main/kotlin/persona/feature/agents/TodoDecisions.kt`, wire `TasksApi.todoDecisions` / `addTodoDecision`, source `TodoDecisionsSource` that `TasksStore` implements; #1853): the same Decisions section in to-do details, under the notes: **Add** records one, **Revise** records one that replaces it (its question filled in, the earlier choice kept struck through), **Full history** shows the replaced ones struck through, and each row says when and where it came from. Typed words are asked about before the form is dropped. Read again whenever the to-do's `updated_at` changes; hidden on a hub without the route (route-level 404). So a question nobody answered can be answered on Android too ("Questions nobody answered"). Not on Android yet: marking an existing decision as replacing an earlier one, or undoing that (the iOS row's ⋯, `PATCH …/decisions/{did}`).

## Concerns

Something the owner raises in the main conversation and wants an answer to is a **concern** (#3561, `docs/design/proposals/owner-at-a-glance.md` G5 and H2): a to-do with `kind = concern`, so it is a record with a status that nothing forgets (`server/internal/assistant/concerns.go`). It reuses the to-dos and their decisions, no store of its own.

- **Recorded** by the main conversation, `todo_create {title, notes?, kind: "concern"}` (only the main conversation may; `origin` is the main conversation, no agent needed, nothing to confirm), or by hand, `POST /api/v1/todos {"title", "kind": "concern"}`. It needs the hub's database (without it a concern could never be reported, so it is not recorded).
- **Closes only after its report**: the main conversation tells the owner the outcome in its reply and, in the same reply, calls `concern_report {id, report}` with the words it told them. That writes a decision of source `reported` (`question` the concern's title, `choice` the report) and closes the concern (`done_by = reported`, `done_reason` the report) in one transaction (`db.ReportConcern`): there is never a close without its report, nor a report on a concern left open. By hand: `POST /api/v1/todos/{id}/decisions {"choice", "source": "reported"}`.
- **Never closes on its own**: the hub's judge ("Automatic completion"), a review or cancellation, a failed start, `todo_complete` and `PATCH {"done": true}` (an app, an extension) all leave it open (the PATCH answers 409, the tool says to report instead). The store refuses each of them for `kind = concern`, and memory refuses a row that would close one without `done_by = reported`. Reopened (`PATCH {"done": false}`, `todo_reopen`), it needs another report; deleting it stays the owner's choice.
- **Extensions**: `todo.changed` carries `kind: "concern"` (created, reopened, closed by its report), and each report is a `todo.decision` with `source: "reported"`, so a work-log extension can keep the concern in its record and show its answer.
- `todo_list {kind: "concern"}` lists the open concerns; `todo_list` / `todo_get` mark them `concern`.
- Clients: `kind` is on the to-do's JSON (left out for others), `done_by` `reported` on a closed one; clients that do not know them show it as a to-do. The SOP rule (an open concern sits in Working while a task of it runs, else in Other open, labelled Concern and not folded) is on the hub (`todo_triage.go`: never shelvable, so a leader's stuck report and the counts see it right) and the web (`web/src/lib/todo-triage.ts`, `web/src/views/Todos.tsx`): the shared fixtures cover it, an open concern keeps a row of its own, and every concern row has the existing neutral tag. iOS and Android follow in their own PRs (#3582), and are not claimed here. The secretary's prompt (P1, #3609) has the main conversation record a concern whenever the owner raises one, and report it only after telling the owner the outcome.

## Questions nobody answered

(#1617, `assistant/ask_todo.go`.) When a card of the assistant's own `ask_user` **expires** unanswered (2 hours, `askUserWait`), the question becomes a to-do, so it waits where the owner looks and a late answer still reaches the conversation that asked. Only an expiry does this: a dismissed card, one withdrawn because the user wrote in the chat (`replied_in_chat`), an answered one and a conversation that stopped waiting behave as before. Agents' question cards keep their own paths.

- **How an expiry is told apart**: the manager's interaction queue ends the card (`await`, history status `expired`) and hands the question a dismiss; `askOnPhone` reads the history and marks that dismiss `reason: "expired"` (`proto.DismissedExpired`; a history that says nothing, or whose end was not written, counts when the card's time is up), which only the manager sets (the apps' answers have their `reason` dropped, `fleet_routes.go`). A hub that keeps the cards itself sends a bare dismiss; it counts as an expiry once the card's `expires_at` has passed.
- **The to-do**: id `todo_ask_<the card's id without ix_>`, so the same card never makes two (a second hand-over, a restarted assistant, two assistants on one store: the id is the primary key). If its record (below) can't be written, no to-do is made and the tool says the user did not answer, as before. Title: the first question. Notes, in the owner's language: when and in which conversation it was asked, each question's options with their descriptions as written (a "(Recommended)" in a label stays), and how to answer. No Agent and no `origin` (#1852, #1909): it is not a task of the asking conversation, which is kept in its record (below) instead, since an `origin` is what makes a to-do a task for the hub and every app. So no app lists it in that conversation's task dock or task board (where it would read "Starting the agent" and offer a **Message** that can't go anywhere), and `task_plan` can't reuse it as a `todo_id`. Handed to an Agent (**Hand to Agent**), it is like a to-do of the owner's own: the Agent works on it, but its turns post no receipt, no done judgment closes it, nothing reopens it or retires the Agent as a finished task's; only the owner's decision, closing or deleting ends the question. Question to-dos made before had the asking conversation as their `origin`; migration `0453_ask_todo_no_origin.sql` clears it, and the snapshot's task list skips question to-dos by id all the same. The live snapshot lists it on a line of its own ("asked with ask_user, nobody answered, waiting for the user's call": don't ask again, don't go ahead), not among the tasks; the next briefings list it under "Can wait" (`laterQueue`, the same queue Agents' non-urgent questions use) until it is closed or deleted, or for 7 days as that queue keeps anything. **Handled** on that row (the web app's `brief` item, the Lark briefing card) closes the to-do as `PATCH done: true` does ("Closed without a decision" below; #1854), so the snapshot stops holding the question back; a to-do that can't be read or closed makes the press fail (503, an error toast) and the row stays. It remains an origin-less question to-do, but now carries an open owner ask rather than reading as an Agent that has not started (#9731).
- **Needs you** (#9731, `server/internal/assistant/ask_todo_choices.go`): `GET /api/v1/todos[].ask` projects an unanswered question with `outcome: "decide"`, its original `asked_at` and `questions[]` (question, header, options with descriptions and recommendation, and multiple-selection flag). A single-choice question with an explicit, matching recommendation also supplies the existing legacy `options`/`recommend` row, recommended option first; the original `questions[]` order never changes. Without that evidence, legacy clients keep their manual-answer path instead of labeling an arbitrary first option as recommended. No Agent, task origin, supervisor or new decision queue is created. Closed, dropped, answered, and actively claimed records have no ask. New records retain structured questions in `assistant.ask_todos`; old records recover them only from their matching expired interaction history. If history is unavailable, the question stays answerable in free text without invented choices.
- **Answering inline**: the Web Needs you row reuses the question card, including one-tap single choices, multiple selections, paginated questions and Other text. It posts `POST /api/v1/todos/{id}/accept {asked_at, answers: {question: answer}}`; the existing single-choice `{option}` form works too. The complete original question set is required for this path; stale rounds return 409, malformed/incomplete answers 400 and a read-only device 403. An explicitly empty `answers` object is incomplete, never consent to the recommendation; omitted or null `answers` preserves the legacy single-choice path. A 409 refreshes the Web row and shows already-handled feedback, not Answer recorded, so a still-open question remains retryable. Inline acceptance commits the complete manual-decision set, the answered record, to-do completion and one durable late-answer relay in a single database transaction, never as Agent work. Delivery can start only after that commit; Answer recorded means the whole answer is durably accepted, even while the asking conversation is busy. Any failed decision insert, record/queue setting write or completion update rolls back the whole submission, sends nothing and leaves the complete form retryable. Decision events publish only after commit. The persisted relay retains the same once-id inputs across restart/retry, so recovery uses the existing relay delivery deduplication rather than creating another answer. A lost commit reply reloads the durable record before releasing its claim, never overwriting an answer that actually committed. Later defers only this browser's copy of the question round; closing or deleting remains the explicit drop path in its details.
- **Deadline state is not completion**: `DueAt` records deadline processing, not an answer. An irreversible question is only reminded and stays in Needs you until the owner decides. `ByDefault` explicitly reserves a reversible question for its recommendation, including delivery recovered after a restart; it offers no second owner answer even if its sending claim expires. A failed default clears that reservation and returns the question to the owner despite its nonzero `DueAt`.
- **Close during an inline answer**: once the answer is claimed, it owns the terminal message to the asking conversation. A concurrent close or delete must not abandon that answer or send an additional dropped notice; delivery preserves the already-closed or deleted to-do. Deletion also removes its decision ledger, but does not revoke an answer already claimed. If close or delete claims the drop first, the drop is the only terminal message and a concurrent inline answer returns 409.
- **The record**: what the message needs (the card, the asking machine and conversation, the original questions and structured choices, when) and whether it was told are kept in the assistant's settings (`assistant.ask_todos`), not on the to-do (no new column); records older than 30 days go (such a to-do is an ordinary one from then on). The record list is one setting, written whole: two assistants on one store dedupe the to-do by its id, but the last to write the list wins.
- **The answer goes back**: the first decision the owner records on the open to-do by hand (`POST /api/v1/todos/{id}/decisions`, the apps' decision form; `source = "manual"`) is claimed (written before it is sent, so it goes once; a claim not followed by the send within 5 minutes, say the assistant restarted in between, no longer holds, so the next decision goes) and sent to the asking conversation as one new message (`prompts/assistant/ask_answer.md`: "you asked … at MM-DD HH:MM; the user decided …"), through the queue `conversation_send` uses (now, or after its turn; kept across a restart; in the background, so the request that wrote the decision does not wait on the node); a conversation that is gone gives way to the main conversation of now. The to-do then closes. With several questions asked, the first decision goes and closes it; the message lists every question and says to ask again what the decision did not cover. A reply in the Lark topic the to-do is bound to is its decision too ("Replies in the thread"): the same message goes to the asking conversation (from the record, as the to-do has no `origin`) as the bot's own send (so the answer comes back into the topic), never to an Agent, and the to-do closes; if no send goes through, the claim is given back. A second decision (the to-do is closed by then) sends nothing.
- **Closed without a decision**: closing it (`PATCH done: true`, or **Handled** on its "Can wait" row) or deleting it tells the asking conversation once that the question was dropped (the same prompt, its "dropped" form). Reopening and closing it again says nothing more; a decision recorded after a reopen still goes back once.
- **The Lark card** of the expired question closes saying "Moved to to-dos" instead of "Ended".
- **Restart**: an `ask_user` waiting while the manager restarts is still cancelled (it lives in memory, #26): it makes no to-do.
- **Asked without waiting** (`wait: false`, #4928; `docs/assistant/assistant.md`, "Asking without holding the turn"): its card's expiry makes the same to-do with the same record, deadline handling and briefing row. Since no tool call is waiting to hear it, the asking conversation is told in a message that the question is now this to-do (or that its recommended options were taken by default); the owner's later decision, or closing the to-do, then reaches the conversation as above. Such a card survives a manager restart, and one whose time ran out while no manager ran becomes the to-do when the next one starts. One exception: when the owner wrote in the asking conversation while the card was up, its expiry makes no to-do and takes no default, since what they wrote may have been the answer; the conversation is told and asks again if it still needs one.

## Waiting for the owner

(#2056, `assistant/todo_ask.go`.) A to-do whose result waits for the owner carries that ask on itself, so the apps can show it in the to-do list and take it with one tap, not only the briefing and the Lark card.

- **`ask` on `GET /api/v1/todos`**: `{"outcome"?, "verdict", "recommend"?, "asked_at", "risk"?}` (a decision carries more, "Decisions the owner can answer" below), the same rows and words as a `brief` item's `accept[]` but for `risk`, which only the list carries (`docs/protocol/protocol.md`, "Tasks and the chat feed"), read from the same acceptance book: a deployed to-do's "Please verify" (no `outcome`), or a supervised task's conclusion (#1226: `outcome` `done`, `cannot` or `decide`). `verdict` is the verdict line as its Lark card says it, in the request's language (the reason is as the review wrote it); `recommend` only on a decision (`decide`) that recommends an option; `asked_at` the round, which `POST /api/v1/todos/{id}/accept` takes; `risk` how risky answering it is, `open` when it cannot be undone or other people will see it, else `safe` (#10465, `docs/assistant/todo-status-sop.md` "The hub's view"), absent from an older manager, which clients read as `open`. A to-do with nothing waiting has no `ask`: never asked, verified, taken, acknowledged, asked before its latest reopen, or a decision the review moved on from (rework, cancelled) or whose task closed. A client that does not know the field ignores it.
- **Taking it**: `POST /api/v1/todos/{id}/accept {"asked_at"}`, as the briefing's Accept button (or, while the hub lists `todo_asks`, the asks route of "Decisions the owner can answer" below): a decision's recommendation goes to the task's Agent and is recorded in its decisions (the same path as the Lark card's "Take the recommendation"), a conclusion that only tells is acknowledged, a deployed to-do is verified. An `asked_at` from an earlier round is 409 "already handled" and takes nothing. If no Agent can receive the recommendation, the hub still records it, answers the round, tells the supervisor to pass it on, and returns 200 `delivered:"none"`. Another delivery failure returns 502 `accept_not_taken` and takes nothing, unless the recommendation may have reached the Agent: 502 `send_in_doubt` then ("One route for every answer" below).
- **Direct completion of a decision** (#3038): the owner may end an open `needs_user` task without taking its recommendation. Use the existing `PATCH /api/v1/todos/{id}` with `{"done":true}` → `{"todo": Todo}` (200, `todo.done_at` set, `done_by` / `done_reason` cleared); carry its `manager` in `X-Persona-Manager` as for any to-do write. This is a completion-state edit, not a round-specific acceptance: no `asked_at` is required and no new endpoint is added. The decision disappears from `GET /api/v1/todos[].ask`, the briefing's pending `accept[]` and the board; historical feed cards remain history. A later Accept on that decision returns 409 and sends nothing. Completion itself never sends a recommendation or message to an Agent and never resumes a closed Agent. It keeps existing outcome recording and idle cleanup ("Stop Agents of completed tasks"): eligible task Agents stop, keeping their terminals, after both completion and inactivity reach 3 minutes; working or blocked Agents are not forcibly stopped. Later Agent activity does not reopen a user-completed task. Explicit `PATCH {"done":false}` reopens it but does not revive its earlier ask. Automatic rework and recommendation sends recheck completion/reopening after slow session/device lookups, before dispatch; ordinary user messages to an Agent retain their existing behavior.
- **Don't handle and Later (web, #4808)**: the Needs you row offers both actions beside the decision choices. Later hides only this browser session's copy of the current review. Don't handle persists a dismissal of the current review through `POST /api/v1/todos/{id}/decision-dismiss {review_at}`; it never completes the task, chooses an option or sends a message. The returned `dismissal_id` is the Undo receipt: `POST /api/v1/todos/{id}/decision-undo-dismiss {review_at, dismissal_id}` restores only that dismissal. `GET /api/v1/todos[].decision_review` carries `review_at` and an optional `dismissal_id`; a newer review naturally appears again. A dismissed decision is never taken by its deadline and is not reminded. It reads the same everywhere: the To-dos page does not file it under Needs you (it is not `owner_decides`, `todo_triage.go` / `todo-triage.ts`), its badge says Not handling, and the assistant's snapshot calls it "you chose not to handle this decision" instead of waiting on you. An answer given later (OK or an option on a card, an answer in the chat or on Lark, `task_decided`) is the owner handling it after all: it undoes the dismissal only once a valid answer is taken. Invalid or stale answers, failed acceptance saves and retryable delivery failures keep the dismissal. A choice that is recorded and handed to the supervisor because no Agent can receive it still counts as taken. Both writes require a full device role and the exact current review; stale rounds/receipts return 409. Old `needs_user` reviews without an `ask` initially remain visible with their original `reason` or `note` and these actions, not invented options or a fabricated acceptance timestamp; after the one `undecidable` hand-back they leave the owner queue until a fresh review. iOS and Android are unchanged in this web-only client fix.
- **The push**: a review's `needs_user` with a `recommend` (`task_review`) is pushed to the owner's devices once (not when it can wait: "Decisions that can wait" below), besides its Lark card and whether or not the bot is on: a `decide` notification (`notify.request` kind `decide`, `docs/protocol/protocol.md` "Bus") to the devices that take "needs you" pushes (quiet hours make it silent, like a card's), opening the conversation the task came from. Its APNs payload:

  ```jsonc
  {"aps": {"alert": {"title": "Conclusion: <task>", "subtitle": "Persona", "body": "🤔 Needs your decision: <reason>\nRecommended: <option>"},
           "sound": "default", "thread-id": "<origin conversation>", "category": "TODO_DECIDE", "interruption-level": "time-sensitive"},
   "machine_id": "<the assistant's machine>", "session_id": "<origin conversation>",
   "todo": {"id": "<to-do id>", "asked_at": "<RFC 3339, the round>", "recommend": "<option>", "manager": "<manager id>",
            "ask": "todo:decision@<asked_at>", "lockscreen": "answer", "options": ["<option>", "<option>"]}}
  ```

  `todo` is `TodoDecidePush` in `schema/wire/todo-view.schema.json`; the cases are in `spec/fixtures/todo-push`. From a manager that says how the push may answer it (#10465), `todo` also has `ask`, the decision's ask in the to-do's view, which an answer from the notification names, and `lockscreen`, the view's rule for that ask (`open_only` exactly when answering it is `open`: it cannot be undone or other people will see it, `docs/assistant/todo-status-sop.md` "The hub's view"). `open_only` (or a value the hub does not know, written `open_only`) sends category `TODO_DECIDE_OPEN`, which no app gives actions, so the notification has none and a tap opens the app, on older apps too, which lose Take Recommendation on such decisions; `answer` keeps `TODO_DECIDE` and adds `options` (the labels whole, no empty one or repeat, the recommended first, at most 4) with `aps.mutable-content: 1`, so a newer app's notification service extension can offer them as actions. A push too big for APNs or the relay's sealed limit has its alert shortened first, down to 500 characters; if it still does not fit, the hub drops `options` and `mutable-content` and fits the full alert again, never the category, `lockscreen` or `ask`, so Take Recommendation is then its one action. A push from an older manager has none of the three and is sent as before, byte for byte; the rule also needs a hub from #10465 on, since an older hub sends every decision as `TODO_DECIDE`.

  `todo.manager` is the manager whose to-do it is (`assistant` for the assistant the hub starts), as the merged list stamps each item's `manager`; OK names it in `X-Persona-Manager`, so it reaches that manager whichever one is the default. All rounds of one to-do share an `apns-collapse-id`, so a later round's push takes the earlier one's place. Through the push relay `category` and `todo` are sealed with the rest (`docs/operations/push-relay.md` "Encryption"). On the WebSocket (`ws_notify`) it is a `notify` of kind `assistant` with the same `todo`, so a client that does not know decisions shows a plain notification. The app's OK action on `TODO_DECIDE` calls the accept route with `todo.asked_at`. No push for a decision without a recommendation (nothing for OK to take), for a task from a health conversation (the lock screen says nothing of those) or a muted conversation; a deployed to-do's "Please verify" and conclusions that only tell are not pushed either.
- **The supervisor** is told what went out. With a Lark card, as before (don't ask again), plus that a push with OK went too. With the bot off it still asks the owner as before (the hub taking a push says neither that a device got it nor that its app shows OK), and is told that OK on the push may take the recommendation first.
- **Clients**: the web shows the ask on the to-do's row, its page, the main chat's task card and the task panel, with the one button that takes it (`docs/web/web.md`, "Waiting for you"); a stopped to-do with an open ask sorts with Awaiting review. iOS shows the ask in the Needs You tray and on the task board ("iOS" below) and offers Take Recommendation on a `TODO_DECIDE` push, none on `TODO_DECIDE_OPEN`; the push's `options` are not actions yet, and the watch has none of it; Android shows the ask in the Needs you tray and on the task's page (`docs/android/android.md`, "Closeout, decisions and tasks nobody works on").
- Not done here: the push is not withdrawn when the decision is taken elsewhere (an OK on it then answers 409, "already handled"); the watch's answer-only credential can neither read `/api/v1/todos` nor call the accept route.

## Decisions the owner can answer

(#3804, `assistant/decision.go`.) A supervised task reviewed `needs_user` used to reach the owner as a title and "waiting for your decision", often for a task they had not started themselves. Now only a decision reaches them, it stands on its own, and it never rots.

- **A decision or nothing**: `task_review` with `needs_user` is refused unless it carries `why_owner` (`irreversible`, `visible_to_others`, `priority`, `acceptance` or `only_owner_knows`: why only the owner can decide), `reason` (one sentence: what is to be decided), `recommend`, `options` (2 to 4 of `{label, leads_to}`, the recommended one first; the hub moves it first if the review did not) and `cost_of_waiting` (one sentence). The refusal names everything missing and says what to do when nothing needs the owner: decide it and send the Agent on, send the work back, or close the task. A task that only waits for something is not a decision. A third `rework` is refused the same way unless it carries these fields, in which case it becomes the decision. The ledger's review keeps the fields (`supervision.reviews[]`), with the decision's `deadline` and `reversible` as the review gave them (absent when it gave none, and on reviews from before they were kept), so they can still be read once the decision is made.
- **Self-contained**: the hub, not the model, adds where the task came from and where it stands, read when the decision is asked. `from`: the origin conversation (`main` for the main chat, else its `title` when it has a name of its own), the to-do's creation time, and the owner's message that led to the work: the one the task's brief froze at dispatch (`request`, with its time; `docs/assistant/unified-entry.md` "Briefs"), else, for a task whose brief does not know, the first message the owner typed to the task (the first `routed` chat-activity entry with neither `from` nor `relay`, from before the task's first review). A to-do with no such message is `by_assistant` (with `started_by` when its brief says who: `assistant`, `leader`, `routine`, `hub`) and names that actual origin: the assistant, a leader conversation, a routine, or Persona itself; an unknown non-owner origin keeps the assistant fallback rather than guessing an owner message. `stands`: the latest Agent's closeout when it wrote one (what it did, else what is missing, what it waits for, what it verified), else its work line. Both are on the to-do's `ask`, in the decision push and on the Lark card, next to each option with what it leads to and the cost of waiting.
- **A default and a date**: a decision whose `why_owner` is not `irreversible` or `visible_to_others` gets a 24-hour deadline with `reversible: true` unless the review sets its own, and "Decision deadlines" below then takes the recommendation. `irreversible` and `visible_to_others` are never taken by default (a review that says `reversible: true` for one is refused). A current decision with an explicit non-reversible deadline is only reminded; once its facts are stale, only a fresh supervisor review raises it to the owner again.
- **Old decisions are checked first**: a decision that has waited 24 hours goes back to its supervisor once as supervision signal `recheck`, with the decision as it was asked: confirm the facts still hold and re-issue it, or close it. The hand-back is kept on both the ask and the review (`recheck_at`), so a restart does not repeat it and a recheck persisted by an older release gets the same projection. While that review is current, the old round leaves `GET /api/v1/todos[].ask`, Needs you, the owner board and the decision digest; its bare `needs_user` fallback is hidden too. Its option, fixed-response, free-text answer, automatic default, card retry and push paths all refuse the old round instead of acting on stale facts. A fresh `task_review needs_user` starts a clean round and restores those paths. There is no grace-period re-push of the unrefreshed round.
- **The backlog**: an open task in `needs_user` with nothing the owner can answer (no ask, or one that recommends nothing) goes back to its supervisor once as signal `undecidable`: restate it as a decision, or close it. Kept on the review (`restate_at`). It waits ten minutes after the review or after an answer, so an ask being written or an answer on its way to the Agent is not mistaken for one. After that hand-back the old no-question row and any no-recommendation fallback ask leave the same owner queues and cannot be answered until a fresh review. A `restate_at` belonging to an actual fixed response does not hide the round: `explain_first` intentionally keeps it answerable while the supervisor prepares the background.
- **"I can't answer this"**: besides its options every decision takes three fixed answers through the accept route (`{"response"}`), and none is ever a default: `decide_yourself` ("You decide"), `not_what_i_asked` ("This isn't what I asked for") and `explain_first` ("Tell me the background first"). Nothing is taken; the task's supervisor gets signal `owner_cannot_answer` once, with the answer and the decision, because the answer says the supervisor was not aligned with the owner.
  - `decide_yourself`: the task stops waiting for the owner and the supervisor decides, telling the Agent and stating its assumption. Asking the same question again is refused. When `why_owner` was `irreversible` or `visible_to_others` the step is not the supervisor's to take: the task stays `needs_user` and the only review accepted is the same decision restated as a plain approval with exactly two options.
  - `not_what_i_asked`: the task stops waiting for the owner and its Agent gets no automatic follow-up (continue, wake, CI follow-up; `workGuard`) until the supervisor reviews the task again (re-scoped with `rework`, `cancelled`, or the link to the owner's request explained in a new decision) or sends its Agent on.
  - `explain_first`: the decision stays as it is, no longer taken by default, and the supervisor re-issues it with a short background.
  - Counted: each is a work event `owner_cannot_answer` and `GET /api/v1/agents/work/stats` sums them per supervisor conversation (`docs/assistant/agent-work.md`, "Evaluation").
- **Choosing an option**: `POST /api/v1/todos/{id}/accept {"asked_at", "option"}` with the recommended label is the plain OK; another option goes to the task's Agent as the owner's choice with what it leads to, is recorded in the to-do's decisions and ends the decision. A decision a linked schedule's progress check raised is the exception: either option goes to the task's supervising conversation, not its Agent (`docs/assistant/assistant.md`, "Scheduled tasks", #11587). With no Agent to receive either kind, the choice is still recorded, the decision ends, and the supervisor gets one `decision_not_delivered` signal for that round; the response is 200 `delivered:"none"`. The Lark card has a button per option and one per fixed answer. The manager's `decide` notification also names the options (the labels, the recommended first) and `responses`; the push carries the options only where the owner may answer from the lock screen (`lockscreen: answer`, "Waiting for the owner" above, #10465), and never the fixed answers, so an app can offer the options from the notification; its body lists the background, the options and the cost of waiting.
- **Answered in the chat** (#6470, `assistant/task_decided.go`): the owner often answers in their own words in the main chat instead of on the card. The main conversation, or the task's supervisor, records that answer with the assistant tool `task_decided` (`todo_id`, `option`: one of the waiting decision's labels, `said`: the owner's words, `told_agent`). Without `told_agent` the option is taken exactly as the accept route takes it (sent to the task's Agent, then recorded). With `told_agent: true` (the answer already went to the Agent with `agent_send`) nothing is sent again. A decision a linked schedule's progress check raised goes to the task's supervisor either way, told whether the Agent already has the answer, and the tool's reply says so (`docs/assistant/assistant.md`, "Scheduled tasks"). Either way the decision ends as a card answer ends it: the ask is answered and leaves Needs you, its deadline default and daily raise stop, the supervision leaves `needs_user`, the to-do's decisions get a `manual` row with the conversation as its source and the owner's words as its reason, and an `owner_decided` event is written. An option that is none of the decision's, a conversation that is neither the main one nor the supervisor, and a decision no longer waiting are refused. Relaying the answer with `agent_send` alone used to leave the decision waiting.
- **Owner message in the task's Agent chat** (#9370, `assistant/decision_agent_reply.go`): a message to an active task Agent while its `needs_user` decision waits pauses that round's automatic default. The pause and source conversation are kept with the ask in Postgres, so they survive a manager restart. A person's own authenticated app also supplies the message text privately to the assistant manager. A single letter (`A`, `B`, etc., case-insensitive) selects by displayed option order; a complete option label matches after removing whitespace and punctuation, without case-folding the label. A unique exact match immediately records and ends the decision through the same record-only path as `task_decided` with `told_agent: true`, using the Agent conversation as the source and preserving the owner's words. Nothing is sent to the Agent again; a linked check's decision also goes to its supervisor, told that the Agent already has the answer (#11747). Conflicting letter/label matches, duplicate normalized labels and prose are not guessed. An exact answer can also settle a decision paused by an earlier unclear message.
- **Unclear Agent replies get supervisor attention**: an unmatched reply pauses the default and unanswered-owner reminders. Its `decision_reply` signal asks the supervisor to read the original conversation and confirm with `task_decided`, or clarify. If that turn ends with a structured `done` closeout, the ask leaves Needs you and any posted card says it was handled in the original conversation. The supervisor receives the owner's words and the closeout and still verifies the open task. No option is selected or sent. A validated notice can interject into an already-running supervisor turn on supported runtimes, and failed delivery stays recoverable. Terminal hooks carry no prompt text. Only `UserPromptSubmit` marked `prompt_source=user` pauses the decision, and replays from before the ask do not count.
- **Replies before an ask**: when `task_review needs_user` raises an Agent's existing question, the manager checks the current Agent's recent transcript for the question and a later owner reply. It matches `reason` or an optional verbatim `question_quote` when the reason paraphrases the question. A reply in that round goes to the supervisor for review without publishing an ask. A unique full option label is also recorded. A bare letter typed before the decision card cannot select by its unpublished option order.
- **Answered in words on Lark, not delivered** (#7911, `assistant/acceptance_reply.go`): a reply in words to a decision's Lark card is recorded in the to-do's decisions and then relayed to the task's Agent. When the relay fails (a dialog open in the Agent's terminal, its computer away), the decision is still made: the supervision leaves `needs_user`, the ask is answered, and the task's supervisor gets an `idle` signal naming the owner's answer and why it did not reach the Agent, to pass it on itself. The hub never resends it, so the Agent cannot get the same answer twice; the reply tells the owner it is recorded and will be passed on. Explicit options and recommendations use the same recorded-but-undelivered outcome when no Agent can receive them; other delivery failures still take nothing.
- **One route for every answer** (#10465, `assistant/todo_asks_routes.go`, hello feature `todo_asks`): `POST /api/v1/todos/{id}/asks/{ask}/answer` answers any of a to-do's own asks by the id its `view` lists (`todo:decision@<asked_at>`, `todo:retry@<done_at>`, `step:<step>/<id>` for a step's ask on its parent's row) and maps the answer onto the paths above: an `option` (the recommended one is the plain OK), a fixed `response`, the owner's `text`, or an `outcome` (`later`, which writes nothing; `decline`, Don't handle; `undo`, with the decline's receipt); an empty answer starts a failed start again or acknowledges a conclusion that says the work cannot be done, never a decision's recommendation. The id carries the round, so an answer from a screen that is behind is 409 `ask_stale` with the row as it is now, and the first answer anywhere wins. An answer to a round handed back to its supervisor ("Old decisions are checked first", "The backlog") is `ask_stale` too: the route reads the same rounds the view lists. It names no conversation: words for a to-do no conversation opened go to its Agent the way the hub's other relays to it go, where the conversation route refuses another conversation's task (its guard stays for that route), and words no Agent can receive are recorded and handed to the supervisor (`delivered: "none"`), as a chosen option is. A run's ask is answered at its card (409 `answer_in_session`). The reply carries the row with its view, which says whether the ask still waits (`explain_first` answers `answered` and leaves it waiting while the supervisor explains), and the hub keeps an operation receipt for it, so a notification action or a phone that lost the reply asks again with the same `X-Persona-Op-Id` and gets the first reply; one cut off while the manager had it is in doubt (502 `assistant_in_doubt`), never "nothing reached it". Every refusal says what reached the Agent (`delivered`), so the hub's receipt and its `todo_send_state` say failed only for an answer that typed nothing: words or an option whose send may have reached the Agent (its answer never came, or the node is not sure) are 502 `send_in_doubt` with `delivered: "unknown"`, and words the Agent took before the decision could be recorded (or before the to-do was deleted) 502 `send_in_doubt` with `"yes"`, in words that say to look at the to-do before answering again. The accept route answers its sends the same way (502 `send_in_doubt`, `accept_not_taken` and 423 with `delivered`; its 400, 409 and 503 come before anything is sent and say nothing of delivery, and it keeps no receipt), and so do the Lark card's button and an "OK" reply, in their own words; the conversation route says `delivered` on every refusal, 409 for all but a bad body (400) and a read-only device (403). An owner's answer in doubt also keeps its decision's deadline handled, so no default at the deadline sends the recommendation a second time. The routes above stay for clients without the feature. Cases: `spec/fixtures/todo-asks`, and what each failure says in `spec/fixtures/todo-writes`.
- **A decision is not replaced by "Please verify"**: while a decision waits, a turn of the task's Agent that says "deployed" (or a held deploy landing) no longer starts a "Please verify" round in its place; and a review that arrives while such a round is still being written keeps its decision, the round giving way. Before, either order left a `needs_user` task with no `ask`, passed by the supervising assistant as if it were a deployed task.
- **iOS** (`DecisionRow`, `docs/apple/ios.md` "Closeout, orphaned tasks and answerable decisions (#3612, #3618, #3804)"): the same row as the web's in the Needs You tray and on the task board, answered through the accept route with `option` or `response`; an option of an `irreversible` or `visible_to_others` decision takes two taps. The `TODO_DECIDE` push's one action is Take Recommendation, which calls the accept route with `todo.asked_at`; a `TODO_DECIDE_OPEN` push has none, and the push's `options` are not actions in the app yet.
- Not done here: offering the options from the decision push on Android (its notification opens the conversation) and on iOS. A task that only waits is parked: "Parked tasks" below.

### Decisions raised outside a supervisor

(#8235, `assistant/outside_decisions.go`.) An authorized extension, or a script on a connected computer through `personad decision`, can raise a rich owner decision without holding an Agent session or a model turn open. It supplies the same question, why it is the owner's call, 2–4 options and outcomes, recommendation and cost of waiting, plus the background and whether the action is reversible. The manager derives the displayed source from the authenticated extension or computer, never from text the caller supplies. That source and the background appear in the existing decision background, so web, iOS and Android need no new field.

- **Its own backing row**: every outside decision has a durable `odc_…` caller id and a separate `todo_od_…` row carrying the ordinary Needs-you ask. An optional `todo_id` associates the backing row with an existing open to-do through `part_of`; it never replaces an ask already on that to-do. Without `todo_id` the decision stands alone and its push opens the main chat, respecting that chat's mute and health-conversation rules. The existing option buttons, one-tap recommendation, three fixed answers, text answers and decision push all answer this backing ask. The backing row is deliberately not quiet: standalone or attached, it is in the same Needs-you list, count and badges as a supervisor's decision. Its `part_of` association never rolls the ask onto the parent, so the backing row stays the request's one answer home and a quiet parent cannot hide its count. Its `NoCard` flag only stops the Lark retry from adding another card; it does not hide the ask or its explicit decision push. While it is pending, an ordinary close or delete of the backing row is refused (`outside_decision_pending`); only an answer or withdrawal ends it, so the caller cannot be left polling a decision that silently lost its card.
- **Polling, not a second answer channel**: the caller polls its decision and gets `pending`, `answered` or `withdrawn`, the answer and its `answered_by` (`owner` or `default`). Only the authenticated caller that raised it can read or withdraw it; another caller gets the same 404 as an unknown id. A caller-stable optional `ref` makes a lost raise response safe to retry: the identical normalized request returns the original id without another card or push, while the same ref with different content is 409 `decision_ref_conflict`.
- **No answer by Persona**: an option, fixed answer or owner's words is recorded for the caller and never sent to an Agent or supervisor. `decide_yourself` therefore means the caller should decide, not that Persona may choose for the owner; it invokes no model. The assistant's `task_decided` tool refuses these backing rows too, so a model cannot settle one through the ordinary chat-decision shortcut. `explain_first` records that response but leaves the decision pending and stops its automatic default, so the owner can answer after the caller supplies an explanation. A final answer or withdrawal closes the backing row and removes it from Needs you.
- **Default and withdrawal**: a reversible decision defaults to its recommendation after 24 hours, like a supervisor's reversible decision, unless `allow_default: false` disables that deadline for this decision. Irreversible and visible-to-others decisions never default. Disabling the default does not make a reversible answer require extra confirmation. Withdrawal is idempotent; withdrawing an answered decision is 409 `decision_closed`, and an answer after withdrawal is refused. Outside decisions do not use the supervisor's 24-hour stale-fact recheck.
- **Durability**: the owner-facing ask and caller polling record are saved together before the initial push. They survive a manager restart; a push transport failure does not roll back the durable decision. The CLI and HTTP contracts are in `docs/integrations/script-cli.md` and `docs/protocol/protocol.md` ("Decisions raised outside a supervisor").

## Decisions that can wait

(#4930, `assistant/decision_wait.go`; `docs/design/proposals/main-chat-availability.md` section 4b.) A decision nobody needs today used to ring the owner's phone the moment it was raised. A supervisor may now say that it can wait, and it arrives with the next briefing instead.

**The default, in one sentence**: a decision is pushed the moment it is raised, unless its supervisor marked it as able to wait and a daily briefing will bring it to the owner in time. Without a daily routine with `facts` nothing changes. With one, turning `facts` off on the routine (or the routine off) brings back "every decision is pushed"; there is no switch of its own.

- **The field**: `task_review` with `needs_user` takes an optional `can_wait: true`, set by the supervisor when nothing is due within 12 hours and waiting costs little. `cost_of_waiting` stays the sentence the owner reads; `can_wait` is a boolean beside it (as `user_check` and `reversible` are) because the hub only has to know push now or not, and a sentence cannot be tested. Absent or `false`: pushed as before. On any other verdict it is refused.
- **Held**: a decision that can wait gets no `decide` push and no Lark card when it is raised. It is the to-do's `ask` at once, so Needs you in the apps and the board show it, with its options and fixed answers as any decision; its `ask` says `for_briefing: true` while nothing was pushed for it. The ask is kept with `for_briefing` and `no_card` in `assistant.acceptance`; a hold that cannot be written is not kept in memory only, the decision is pushed at once.
- **Always pushed**: `can_wait` is ignored, and `task_review`'s answer says why, when `why_owner` is `irreversible` or `visible_to_others`, when the review's own deadline says `reversible: false`, when the deadline is less than 12 hours away, and when no briefing comes in time. In time means: the next run of an enabled daily routine with `facts` (the routines "Questions that can wait" count on, `docs/extensions/bots.md`) is within 24 hours and at least 12 hours before the decision's deadline. The deadline is counted from when the decision is raised, as for any decision, so with the default of 24 hours a decision is held when a briefing is due within 12 hours; a review that can wait longer gives a longer `deadline`.
- **In the briefing**: a run of a routine with `facts` lists it under "To verify" with its recommendation and **Take the recommendation**, where every open decision already is (`docs/extensions/bots.md`, "Morning and evening briefings"). The hold ends (`for_briefing` cleared, for the round the run listed) once that briefing reached the owner: the run ended normally and its finished push with the counts was sent (the run's `brief` item lists every row), or its Lark card went out with the decision's row on it. A run that was only sent, failed, or whose card had no room for the row does not end it. A decision a briefing brought to the owner stays card-less: the briefing and the to-do are where it is answered.
- **Never lost**: a held decision is pushed after all as soon as one of three things is true: no such routine is on any more, 24 hours passed since it was raised, or its deadline is 11 hours away (an hour after the latest briefing it could count on, so the owner has at least 11 hours to answer before a default is taken). Checked once a minute with the deadlines. The hold ends when the hub took the push; a push it did not take is tried again a minute later. The decision's Lark card is then due as when a decision is raised: posted on the next tick of the card retry (within 10 minutes), and tried again for 45 minutes from the push. One the owner hid in the apps (Don't handle) is not pushed.
- **A leader's or the background supervisor's held decision** is not sent to the main conversation when it is raised (`escalated`, `docs/assistant/unified-entry.md` "Leader conversations", "Background supervisor"): nothing went to the owner, and the main conversation is not woken for what can wait. It is sent when the decision is pushed after all; one a briefing brought to the owner is not sent at all. The held decision keeps who raised it (`raised_by` in `assistant.accept`, cleared with the hold), because a background supervisor's task names the main conversation in its ledger; one held by a manager from before that is sent when its task is a leader's.
- **Unchanged**: the 24-hour default of a reversible decision, a deadline the review gives, the `recheck` after 24 hours, `undecidable` and `owner_cannot_answer`. The owner can answer a held decision at any time from Needs you.
- **The supervisor** is told that nothing went out and not to ask the owner itself; when `can_wait` was ignored it is told why and the answer goes on as for any decision.
- Not done here: the briefing lists it among "To verify", where decisions already are, not in a block of its own; the Android app marks a held decision on its card and on its To-dos row (#5802, `docs/android/android.md` "Rule suggestions, held decisions, recommended setup and purpose descriptions") and the Apple apps mark it "Comes with your next briefing" on its row and card (#5803, `docs/apple/ios.md` "Suggested standing rule and held decisions"); the web marks it on the decision's card in Needs you and on the to-do's ask line (#5803, `docs/web/web.md` "Decisions held for the briefing"); nothing counts how many decisions were held; and there is no switch of its own in Settings (above). A hub rolled back to a build from before #4930 drops `for_briefing` on its next write of the asks, and such a decision is then neither pushed nor carded by either build: it is still in Needs you and in the briefing.

## Confirmed handoffs between active to-dos

The supervisor of a stopped to-do can ask an Agent on another open supervised to-do to check a candidate. Use
`agent_send` with `handoff` naming both to-dos, the full candidate commit, the requested check and a deadline. This
uses the existing Agent session. A node acknowledgement, including acceptance into its queue, records the wait on
the originating to-do. A refused send or one with an unknown outcome leaves its state unchanged.

The originating to-do shows the receiving task, requested check and deadline in Waiting. The receiving Agent gets a
receipt ID in the message. It uses `report_to_supervisor` with `handoff_receipt`, the head it checked and its evidence.
A receipt from the bound Agent must match the active handoff ID, originating to-do, commit and check. Only that
originating to-do returns to its supervisor for review. The result and the return to review are stored together.
The supervision sweep recovers a result that has yet to be delivered after a restart.

A failed check, a cancelled receiving to-do or a missed deadline returns the originating to-do to its supervisor
with the reason. A receiving Agent stopping by itself leaves the wait in place. New work and later reviews of the
originating to-do end the old wait. Owner decisions and acceptance keep their existing handling.

## Parked tasks

**External PR events (#9775).** On an `external_event` park, set `evidence.pr_event` to `terminal` when merge or
closure ends the wait, or to `terminal_or_review` when a new submitted review also ends it. Set `evidence.url`
to that GitHub PR. A PR link used as context for another dependency keeps its timed recheck. Existing records
without `pr_event` can opt in when the supervisor confirms the condition and records a new park.

The existing minute PR pass can add this exact source to its bounded sample even for a task with no stage PR.
It uses the ten-minute attempt/fact throttle. Terminal state can be confirmed on the first fresh read.
A review must name the current head and have a provider ID and submission time after the current park.
Approvals, requests for changes and comments submitted as reviews are read from the existing bounded review page.
The manager rechecks the task, captured park and latest observation before committing `external_pr` and
`pending_review` together. The review signal goes to the current supervisor, who still checks the task criteria.
Failed writes can be retried. The watch recovers a committed wake after a restart, with one delivery per park.
The existing ready `merge_review` path still gates terminal wakes on the task's sampled PRs.

(#3804, `assistant/parked.go`, `assistant/park_evidence.go`.) Parking is for an evidenced external wait, not a way to defer work or ask the owner a question. A new park must say what is awaited and include source-backed evidence.

- **New parks**: `task_review` with `parked` requires a one-sentence `reason`, `waiting_on` (`someone_else`, `external_event` or `date`), and typed `evidence` with nonblank `kind`, `target` and `wake`. A new owner decision is `needs_user` with its complete decision fields; `owner_priority` is refused for new parks. Legacy `owner_priority` reviews remain readable; the existing supervision watch reconciles their open, current parks into `needs_user` rather than leaving an owner choice hidden in the waiting-only digest.
- **Evidence**: `person_reply` and `merge_review` require `contact` with `channel`, `url`, `sender`, `sent_at`, `request` and `status: "sent"`; this records an already-sent request and its receipt, not a draft or unknown send. `merge_review` also requires `ready: true` and a PR/MR `url`. `external_event` requires the observable object's `url`. On an `external_event`, optional `interaction_id` names the task worker's existing pending owner interaction, obtained by exact ID (for example from `agents_list`), never inferred from the target or URL. Admission refuses unknown, resolved, wrong-worker, dismissed and failed-start references before any mutation; a released worker's still-pending request remains eligible. Projection checks the exact pending card again on every read and exposes it as the existing run `OwnerAsk`, including when the worker is idle or released. A worker shared by several to-dos keeps the existing one-home routing: the session's tied to-do wins, else the first listing; the others keep their ordinary park. Once the exact card resolves or disappears, a stale session `needs_you` with that same `work.interaction_id` does not synthesize another ask; a different current card is still real owner input. The ordinary park and its fallback remain, and resolving the interaction does not itself accept or wake the task. `date` requires an explicit RFC 3339 `until` (not a duration or default). Other waits may use a duration or RFC 3339 `until`, default 24 hours; all `until` deadlines must be 1 minute to 30 days ahead.
- **Named-person topic reply** (#9601, `assistant/park_reply.go`): an optional `evidence.reply` binds a `person_reply` to `source: "larkcli"`, `brand` (`feishu` or `lark`), `app_id`, `account_open_id`, `person_open_id`, `chat_id`, `thread_id` and `request_message_id`. These are source identities, never inferred from the displayed target or Inbox task linking. `contact.url` must be the actual sent request's HTTPS provider topic AppLink, with matching `open_chat_id` and `open_thread_id`. The configured reader independently reads back that request and a human reply from exactly that person in exactly that topic, under the same app/account identity before and after the read. The request must have been sent by that account or the bound app, and its source link/time must agree with the contact. No third-party reply enters the owner-only decision route.
- **Reply time and recovery**: source timestamps retain their precision as intervals, including the CLI's local minute-only format. The entire request interval must precede the current park, and the reply interval must provably follow that park and request and precede the observation. No ordering inside an ambiguous minute is guessed. With the same park still current and the task open, the manager commits a small source receipt to that review's `reply` and changes the ledger to `pending_review` in one write, then queues existing `review` for the current supervisor. Failed writes leave it parked and retryable from the source after restart; replay cannot end a later park. This is not owner consent, task acceptance, direct Agent delivery or execution.
- **Reply reader limits**: the existing minute source pass attempts up to four bound waits, longest unattempted first, with an eight-second per-wait deadline and thirty-second pass budget; each topic read is bounded to four pages of fifty messages. There is no push subscription or complete-history/latency guarantee. Missing request/reply metadata, source/account mismatch, unreadable history or an unavailable/unconfigured lark-cli reader leaves the task parked. Only explicit bindings opt in; no setting or external message is changed/sent, and the reader does not mark messages read. Unbound/legacy waits, the Lark gateway and other providers are unchanged; generic delivery remains separate (#6206).
- **Provenance boundary**: the supervisor must inspect the actual source receipt before supplying evidence. The tool validates and persists the supplied source-backed account; admission itself does not contact providers or independently verify a receipt. Automatic observation is limited to the explicit supported bindings described here, not arbitrary wake prose or URLs. It does not forward events or send an Agent instruction. `recorded_by` is server-authored for the current conversation and is output only. Legacy parks with no `evidence` mean evidence was not recorded, not that a contact or wait was verified.
- **Mechanical waits**: a mechanical wait without source evidence is no longer automatically parked; its signal remains visible to the supervisor for ordinary review. This does not change native future-wake deferral or merged-delivery advancement. Outside the supported typed bindings, the recorded wake condition is descriptive, not an event adapter. No UI, status-only, outbox or supervision-authority behavior is added here.
- **What parked means**: the to-do stays open with `supervision.state: "parked"` and `supervision.parked: {reason, until, waiting_on, count, evidence?}`. It is not a new owner question: no `ask`, push or conclusion card, and it is not filed under Waiting on you just because it is parked. The exception is an `external_event` with a verified `interaction_id`: its already-pending interaction appears once in the usual Needs you flow while it remains actionable, without creating a new ask or changing the park ledger. While parked, its supervisor gets no `stalled`, `no_progress`, `idle`, `unjudged`, `orphaned`, `overdue`, `undecidable` or no-progress `check` signal, and the manager does not send the Agent its own follow-up. At `until`, one `parked_due` message returns the task and its recorded decisions to its supervisor; the task remains parked until the supervisor acts.
- **Leaving**: any Agent turn ends the parking, drops a still-pending `parked_due`, and returns the task to in progress (or `rework` when rounds were used). There is no status-only exception in this change. Any other review ends parking; a closed to-do is not parked.
- **Owner decision wake** (#8044): an owner's recorded decision ends a park waiting on `someone_else`, and still ends a legacy `owner_priority` park or its reconciled `needs_user` wait, even without an Agent turn. The supervisor receives one `park_decided` with the decision so it can resume, review or close. A decision before a later park does not end that newer park. The decision is stored before the ledger is touched, so a failed ledger write does not fail the decision request; it is logged and the watch recovers within 30 seconds. A later review or re-park does not drop an already queued `park_decided`; only `accepted` or `cancelled` does, and a decision from before a newer park does not end it. The ledger records the decision and whether supervision carried it across restarts. Agent notes, routed-card answers by the supervisor, deadline defaults and outcome records are not the owner's decision; decisions do not end `external_event` or `date` parks.
- **Not a place to forget things**: `count` is consecutive parks without an Agent turn; three re-parks are allowed, and the next is refused. An Agent turn or an owner's decision that ends the park resets the count.
- **Legacy owner visibility**: the watch moves an open, current `owner_priority` park to the existing `needs_user` state, so Needs you includes it before its old `until`. It preserves the actual review, reason, timestamps, history, supervisor and independent owner-wait record; it creates no question, recommendation, option, deadline, consent or Agent instruction. The existing `undecidable` signal asks the current supervisor once to restate a complete question, without the modern question-write settle delay or treating an older Ask as the current question. Fresh `task_review needs_user` admission remains strict. A real owner decision stored after that park wins over reconciliation and is retried after a failed write; a failed decision lookup postpones migration rather than guessing that nothing was answered. Older decision cards are stale while the latest review is that legacy park: neither clicking an old recommendation nor its automatic default can answer the new owner wait. Deadline reminders are also skipped without changing the old Ask. This lasts until a real newer review replaces the legacy marker; non-decision verification asks remain unaffected. Other external/date parks, closed tasks and newer reviews are untouched; no historical card or decision is replayed.
- **Kept on the review**: `reviews[]` carries `reason`, `until`, `waiting_on`, `parks`, `evidence` when recorded, and the existing `due_at`, `decided` and `decided_told` fields. `supervision.parked` is read from the latest review while the state is `parked`; no new column is added. A legacy review without evidence stays without it.
- **Web wait display**: use the lazy `TaskWaitInfo` display and the `ParkedTaskRow` API independently of the grouping implementation on the Parked tray, To-dos, All board and task details. It renders recorded wait, source and wake information; callers retain existing membership, owner-decision and live-work eligibility. It adds no grouping rule or lifecycle/status change. iOS and Android continue to show supervised tasks as in progress.
- **Web wait source names** (#9730): source links name the recorded PR, issue or comment instead of an ordinal. An explicit park uses its own evidence URL; unrelated task PR facts do not become evidence for that wait. Without explicit evidence, the existing multi-PR merge fallback remains. A recorded Lark topic title is used only when its chat and thread IDs match the source AppLink; a recorded contact keeps its channel name. Missing names stay an honest Lark conversation label, missing or unsafe URLs produce no source placeholder, and full URLs remain inspectable without another request.
- **Wait count and age**: `Parked.count` is the consecutive parks in the current streak without an Agent turn; wait age is the earliest known request or review time in that matching streak, never `todo.updated_at` or a PR check time. Match the same wait kind, target and object (for `person_reply`, the same channel), scanning only the trailing `count` parked reviews; an Agent turn resets the streak. For each matching park, a valid sent contact's `sent_at` takes precedence over that review's `at`. A valid sent-contact start reads **Waiting**; a review-time fallback reads **Parked**. Sort wait slots oldest known first, unknown starts last, with a stable to-do-ID tie-break (`web/src/lib/task-wait.ts`, `waitStart`, `compareWaitAge`).
- **Contact and provenance**: show a last request only when its contact is complete, `status: "sent"`, its URL is a non-root HTTP(S) source without credentials, and `sent_at` is no later than now (`sentWaitContact` in `web/src/lib/task-wait.ts`; display projection `taskWait` in `web/src/lib/task-wait-info.ts`). Review evidence also requires `ready: true` and a PR/MR object URL. `recorded_by` identifies the recording conversation, not the contact or sender. Evidence is the supervisor's source-backed account; the hub does not fetch or independently verify that source. A legacy park with no evidence has unknown contact, source and wake; an implicit PR wait keeps its known PR link but has unknown contact, wake and start time. Do not invent missing values. Only waits that can record a sent request say when none is recorded (`person_reply`, `merge_review`, a legacy park, an implicit PR wait); `external_event` and `date` evidence never carries a contact, so their display shows the target, source, wake and fallback time with no request line (#10527). A target that describes a prompt to the owner is shown as written: it is not read as a sent request, a pending owner decision or consent. Only the optional, hub-verified `interaction_id` on `external_event` evidence links an existing owner request. While that exact card remains pending, the web shows it once under Needs you through its normal interaction route, not as a contact receipt or a second decision card; explicit defer and its schedule stay on the interaction. After resolution, or when no valid link was recorded, the task keeps its ordinary external-event presentation and fallback (`web/src/lib/assistant-entries.ts`, `web/src/lib/todos.ts`, and the manager's `todo/projection`).
- **Due and reminder draft**: a passed `until` or a valid last contact older than 24 hours (`person_reply`) or 72 hours (`merge_review`) reads as due for follow-up. Only the last-contact threshold enables the editable reminder draft; Copy copies it locally and Open channel follows the recorded contact. Successful copy dismisses the editor; failed copying or an edit made while clipboard permission is pending keeps the draft. No external message is sent, no event is watched, no park is automatically ended, and no round is incremented. A minute clock refreshes displayed age/due text only. At `until`, `parked_due` is for the supervisor and the task remains parked until the supervisor acts.

## Decision deadlines

(#3127, `assistant/decision_deadline.go`.) A decision that waits for the owner can carry a recommended default and a deadline, so work does not stop just because nobody answered. Without a deadline nothing changes.

- **Who sets it**: `task_review` with `needs_user` (`deadline`, `reversible`, with its `recommend`) and `ask_user` (`deadline`, `reversible`, and a `recommend` on every question naming one of its options). `deadline` is a duration (`4h`) or an RFC 3339 time, 1 minute to 30 days ahead; a deadline without `reversible`, or without a recommendation, is refused. `reversible: false` is for what cannot be undone: deleting, sending anything to other people, spending money and production changes.
- **Where it is kept**: a task's on its decision in the acceptance book (`acceptAsk.deadline`, `reversible`, `due_at`, `by_default`); a question's in its arguments (as a time) and, once it became a to-do, on its record (`assistant.ask_todos`). The card waits no longer than the deadline. The Lark card and the decision push add a line with the deadline and what it does; on the phone card the recommended option's description says so.
- **At the deadline** (`acceptLoop` looks every minute):
  - **Reversible**: the recommendation is taken the way the owner's OK takes it. A task's goes to its Agent (the message says it was taken by default and can still change) and the task stops waiting for the user; a question still waiting gets the recommended options as the tool's answer, and one that became a to-do earlier has them sent to the asking conversation as a new message and closes. Either way a decision is recorded on the to-do: the question, the option, the reason "taken by default: no answer by MM-DD HH:MM", with `source = "agent"` because it is not the owner's own call.
  - **Not reversible**: nothing is taken. The owner is reminded once (the decision push again, and the Lark card again when there was one; a question's to-do gets a push), and it keeps waiting; the owner can still answer at any time.
- An answer from the owner before the deadline wins as before; a deadline that passes while the hub is down is handled on the next sweep.

## Chat thread

(#5279, step 2: the binding itself) A to-do can be bound to a chat thread, a topic in a group chat or a conversation, so that the thread and the to-do are known to belong together. The binding itself writes nothing to any channel. What the user says in the thread comes back to the to-do ("Replies in the thread" below), and what happens to the to-do is told in the thread ("Posting into the thread" below). `todo.*` events come in a later step.

- **The binding**: `thread` on the to-do, `{channel, chat_id, thread_id, title}` (the first three name the thread, the title is a label). `channel` is a channel id as `internal/channel` names them (`channel.Feishu` = `"feishu"`); it is trimmed and lower-cased before it is kept, so `Feishu` and `feishu` are one channel. For `feishu`, `chat_id` is the chat's id (`oc_…`) and `thread_id` is the `thread_id` the message events carry (`omt_…`), not the thread's root message id (`om_…`). The server does not check them against the channel (it cannot know a thread exists), so the caller must pass the real ones. At most one thread per to-do and one to-do per thread: binding a thread another to-do holds is refused (409, from memory first, finally by the unique index, so a second assistant on the same database cannot slip past it). Binding again replaces the thread; the old one is free for another to-do. A done to-do can be bound or unbound too (it may be reopened, and the user's tidying should not depend on its state).
- **API**: `PUT` / `DELETE /api/v1/todos/{id}/thread` (full role only), "API overview" above. Both move the to-do's `updated_at` and broadcast `{"type":"todos"}`, unless nothing changed (unbinding a to-do that has no thread, or binding exactly what it already has: nothing is written); `GET /api/v1/todos` returns `thread` with each to-do that has one. Editing a to-do leaves its thread alone.
- **Reverse lookup** for the next step (a reply in a thread finds its to-do): in memory, every `Todo` carries `Thread` and `sameThread(a, b)` (`assistant/todo_thread.go`) compares two bindings; from the store, `DB.TodoOfThread(channel, chat_id, thread_id)` (`internal/db/todo_thread.go`).
- **From the Agent**: an Agent on an open to-do has `todo_bind_thread {channel, chat_id, thread_id, title?, todo_id?}` (`mcp/todo/`, with the decision tools; the node resolves its caller the same way, `callerTools`). It binds the to-do the Agent works on and no other: `todo_id`, if given, must be that to-do's own id. A to-do that already has another thread keeps it (changing it is the user's call, the tool says to ask them); the same thread again only updates its title. Outside an open to-do it says there is none.
- Web (`views/Todos.tsx` `ThreadSection`, `lib/todo-thread.ts`): the to-do's page has a **Topic** section under the notes: one line "Lark topic · <title, or the thread id shortened>" (any other channel: "Topic (<channel>)") and **Unbind**, which asks first and then `DELETE`s the thread; the list row of a bound to-do has a small chat mark. No link to the topic is drawn: the binding holds no message id, and the repo has no verified Lark link that opens a topic by `thread_id`. Binding is not on the web: it would need the bot's recent topics, which the hub has no route for, so an unbound to-do says that a topic started in a `/topics` group opens and binds a new to-do, and that an Agent can bind it (the note does not name the tool). The web is always a full-role device, so Unbind is always there. A hub with no thread route (a route-level 404 on the unbind, as `isLegacySpacesRouteError` reads it) loses the section without a word.

### Replies in the thread

(#5279, step 3.) A message from a group chat (the bot event's `chat_type` is anything but `p2p`) never takes the bot's private-chat road: no commands (a text starting with `/` is a word like any other), no answering the question card or the "Please verify" card, never the chat's current target. It goes by its topic alone (`assistant/feishu_thread.go`). The hub hands the assistant only the owner's messages in a topic of a group chat the owner opted in (`docs/extensions/bots.md` ("Topic group chats")); the assistant's own rule here is the second line of defense.

**Using it in Lark**: (1) in the Open Platform console give the bot `im:message.group_at_msg:readonly` (every message then has to @ the bot) or `im:message.group_msg` (all messages in the group, needs the admin's review), and add the bot to a group chat with you; (2) send `/topics` in that group, the bot answers that it is on; (3) start a topic in the group for a to-do and bind the to-do to it (the to-do's `thread`: `chat_id` of the group, `thread_id` of the topic, "The binding" above); (4) what you write in the topic is a decision of the to-do and goes to its Agent, and the answer, the progress card and the Agent's questions and permission requests come back into the same topic, where the buttons (Stop included) work for you alone. `/topics off` turns the group off.

- **Only the owner**: the message must come from a user whose open_id is the paired owner's, else it is dropped without a word (the hub checks it too, "docs/extensions/bots.md" ("Topic group chats"); the words go to an Agent that acts on them, so this is not left to one line of defense).
- **Lookup**: the to-do whose `thread` is `{feishu, chat_id, thread_id}` of the message, in memory (`sameThread`). A message outside a topic (no `thread_id`) is left alone.
- **No open to-do** (the topic is bound to nothing, or to a to-do that is done): one short hint in the topic (`assistant-feishu.thread_unbound` / `thread_done`), at most once per topic in 10 minutes; nothing is recorded or sent, unless the message asks for a to-do (["Opening a to-do from a topic"](#opening-a-to-do-from-a-topic) below). A done to-do is not reopened by a reply.
- **Open to-do**: the words are written as a decision, `source = "thread"`, `source_message = "feishu-<message_id>"`, question "Reply in the Lark topic" (like a reply to the "Please verify" card, which records "Review feedback"), choice the text as said (trimmed, clipped as every decision is). The same message again writes nothing and is not sent on again (the unique index on `(todo_id, source_message, question)`; the bot also takes each message id once). Without the database nothing is recorded and the words still go on.
- **Who gets it**, settled before anything is written: the Agent on the to-do that most needs it (`pickTaskAgent`, among the ones running: a closed Agent, offline or interrupted, is not counted), else the conversation that opened it (`origin`, when it still exists; for a question's to-do, which has none, the conversation that asked, from its record: "Questions nobody answered"), else the main conversation; one the bot's switches do not allow (`agents` for an Agent, `main` for a conversation) is left out. It is sent as the bot's own send (`botSendIn`), so the run follows it like any message of the bot; when a send fails (the machine is gone, the node refuses) the next one is tried. With no one left, or all of them failing, the words are still recorded and the topic is told "noted on the to-do, but not passed to anyone" (just "couldn't send it" when nothing was recorded). The text is one line, "To-do "X": the user's new decision in the topic" (the title escaped like a decision's text), then what was said (`prompts/todo/thread_reply.md`); the line says it was recorded as a decision only when it was (not for a message of only a picture, with no database, or when the write failed). A Persona conversation also gets the note that it was said in a topic (`bot/message.md`). A quoted message and a merged forward are not read in (what others said there is not the owner's words); a merged forward gets "can't read this kind of message". Handoff context shows these decisions as "said by the user in the Lark topic".
- **The answer stays in the topic**: the run keeps the chat and thread in its channel values (`ext.chat`, `ext.thread`, kept with the run), and its progress card, answer cards and notes are sent with `chat_id` and `in_thread: true` (`feishu.post` / `feishu.text`, #5903), and so are the question, plan, permission and terminal-dialog cards of the conversation the run follows (`postInteractionCard`: the card is a reply to the run's message, in the topic; with a private run on the same conversation it goes to the owner's DM instead and the topic is told so in a line, and it goes to the DM when the topic refuses it outright). It makes no agent message (`feishu.cot_create` only knows the owner's private chat), and its cards are not bound as reply targets of the private chat. A topic's run and a private chat's run on the same conversation are not folded into one answer. A private chat's run keeps neither field and behaves as ever.
- **Not posted back**: a decision with `source = "thread"` is never posted into the thread (`postable`): it is already there, and the bot's own post must not come back as a reply. The posts below ask `postable`; and a bot's own message is not the owner's (`sender_type` is not `user`), so both the hub and `threadMessage` drop it before anything is recorded.

### Posting into the thread

(#5279, step 4.) A to-do bound to a Lark topic tells the topic, in one short line with a link back to the to-do (`/todos?id=…` on the hub's `public_url`; none when the hub has no address), when:

- **a decision is noted**: from the app, a card answer, an Agent (`todo_decision_add`) or the outcome on completion. Not one the user said in the thread, and not the words the user wrote in the private chat as the answer to a "Please verify" card (`postable`): what is said in the private chat stays in it.
- **an Agent working on it finishes a turn or needs the user**: the same two events the phone's pushes are made of (`notifyFinished`, after its push decision; `tell`, for a card that is not muted), so what is not pushed (a turn the user saw, a muted conversation, a turn asked in the bot and answered there) is not posted either. A card the topic already knows about gets no line: it went into this topic (its run was asked there: same chat and same thread), or a line there says it went to the DM (a private run of the conversation wins, `interactionPlace`). Otherwise the line says where the card is: in the DM, it only says so ("Agent X needs you, the card is in your private chat"; what an approval asks is not for a group); in another topic, only that the Agent needs the user; with no card at all (the cards switch is off, or the chat does not drive that Agent), the line is the notice and carries what is asked, except for a permission (a command or a path is not for a group): then it only says the Agent needs the user. An Agent with no name is "an agent".
- **the to-do is accepted** on its "Please verify" card (or from the Accept button of a briefing, when the ask has no card), **done** (by the user, or by the hub's judge, with its reason), or **closed because its Agent never started** (with the error). Accepted and done together are one line, the done one.

The line is "New decision: …", "3 new decisions: …", "An agent finished a turn: …", "Agent X needs you: …", "The to-do is done", joined with the others of the same minute (`assistant-feishu.thread_post_*`, in the bot's language). Decisions are quoted as "question → choice", at most three, the rest counted.

- **At most one line a minute per to-do.** The first thing of a quiet to-do waits 3 seconds (`threadPostSettle`), so what comes right behind it (the rows of one outcome, a decision and the closing) is one line; what happens after a line goes out waits for the minute (`threadPostEvery`) to be over and is then one line, "N new decisions: …". The clock and the timer are the poster's own (`threadPoster.now` / `after`), which the tests replace. A restart forgets what waits: it is a notice, not a record. A post that fails is lost, not tried again. An outcome decision that arrives more than the 3 seconds after the closing (the model is slow) is a line of its own, after the minute.
- **Every line has its own key** (`uuid` of `feishu.text`, cut to 50 characters; `feishu.post` takes it too, for a reply as well as a send into the chat, cut to 46; only letters, digits, `:`, `_` and `-` are taken, any other key is ignored as if none was given). Without it the hub keys a reply by its parent and words, so two lines that read the same under one anchor (two finished turns) would be one to Feishu, and the second silently dropped. Calls that pass no `uuid` keep the key they had.
- **Only into a chat the bot may send into.** Before a line goes out the assistant reads `feishu.status` and posts only when the thread's `chat_id` is in `chats`: the hub's own rule for `feishu.post` / `feishu.text` (the owner's private chat and the group chats the owner opted in, `docs/extensions/bots.md` ("Topic group chats")). Otherwise nothing is sent and the todo's id is logged. This closes the gap that `todo_bind_thread` lets an Agent write any `chat_id` into a binding: what an Agent binds is never a place the assistant writes to unless the owner opted that chat in. (The hub refuses the send anyway; this is the check before it.)
- **Where it goes**: `feishu.text` with `chat_id` and `in_thread: true`, as a reply to the latest message the owner said in that topic. The binding keeps only the `thread_id`, and Feishu replies into a thread by a message in it, so the assistant remembers that message (`bots.feishu.state`, `topics`, per chat and thread, 30 days, at most 200) each time a message of the topic reaches it, bound or not. With none known (nobody has written in the topic since the assistant has had this state) nothing is sent and the todo's id is logged; the first message the owner writes there fixes it. If the anchor was withdrawn or deleted the line is not turned into a message in the group: the assistant's call carries `no_detour` (the hub's option on `feishu.post` / `feishu.text`: a reply to a gone parent fails with `feishubot.MessageGone`), and it forgets that anchor, the line is lost, and the owner's next message in the topic is the new one.
- **Nothing for a to-do with no thread**, none for one unbound while the line waited. Not sent: the log says why.
- **Private chat as before**: the reports and pushes (`reports`, `feishuAgentDone`, the cards) go out as ever; a bound to-do's topic is told in addition. Whether a bound to-do should be told in the topic only is left for later.

### Telling the extensions

(#5279, step 5.) The extensions are told of the to-dos too, through two events (`todo.changed`, `todo.decision`; [extensions.md](../extensions/extensions.md) "To-do events"): the ones that subscribed and were granted `todos.read` (the read scope that already lets them call `GET /api/v1/todos`), so a connector extension can post into a thread it owns as the user. Nothing needs a binding: they go for every to-do. `assistant/todo_events.go`.

- **`todo.decision`** is sent from `insertDecision`, the one place every decision is written through, so every source is told (the thread's own too, with `source: "thread"`).
- **`todo.changed`** is not hung on the writers. Whenever the to-dos change (`todosChanged`, what tells the apps) a timer of one second starts; at its end the to-dos are compared with what the extensions were last told of (title, done or failed to start, bound thread), and a to-do created, deleted or different is told once. A new way to change a to-do cannot forget it, and several changes inside the second are one event. The baseline is taken when the to-dos are loaded, so nothing is told of the ones found there.

### Opening a to-do from a topic

(#5279, step 5.) In a registered group chat, a new topic opens a to-do by itself and hands it to the main conversation: the same as a bot that auto-starts a session on a new topic, but the session is the to-do (`assistant/feishu_thread_open.go`). The hub's gate and registration decide which groups get this far; the assistant opens only for the owner's own messages (see "Replies in the thread").

- **Shared path**: the to-do, the binding and the hand-over are `openTodoIn`; a request from another chat ("Where it came from" below) comes in through it too, with the first message posted by the bot.
- **When**: the message starts its topic (`isTopicRoot`: it has a `thread_id`, and `root_id` is empty or its own `message_id`), or it is "/ai" (or the full-width "／ai", any case) followed by a space or the end, in a topic bound to nothing. The command is taken off, and what is left is the first words. In a topic whose to-do is open "/ai" is a word like any other (a reply, a decision); in one whose to-do is done it is answered "reopen it in the app" every time (the 10-minute limit of the hint does not apply to a command), and no second to-do is made. A reply that is not "/ai" in a topic bound to nothing gets the hint, which now says to send "/ai" and a line. Checked on a real topic group with the message API (not the event push; the two carry the same fields): the first message has an empty `root_id` and `parent_id` and a `thread_id`, a reply has both set.
- **What is made**: a to-do titled after the first meaningful words. In a Lark topic, the initial confirmation skips leading attachment markers, bare URLs and the bot mention. A rich document link supplies its display title. A bare link alone or a request such as “have a look” uses the localized “New to-do” until the model names it from the original message. The opening message supplies its `notes`. The main conversation is its `origin` and supervisor (`superviseTodo`). The to-do is bound to the topic, and its task card appears in the main conversation’s feed. Creating it records no decision. Only a text or a rich-text message has words (`openingWords`): the bot's @ at the start is taken off (in a group where the bot only gets what @s it every message starts with one), an @ further in is the person's name when the message's mentions give it, and the placeholders of other types (`[语音消息]`, a shared group or card, a location, an unknown type) are not words. A message with no words (a picture, a merged forward, a voice message, a rich text of only pictures, or only "/ai") makes nothing and is answered "say it in a line of text".
- **Whom it goes to is settled first**: the main conversation must be allowed by the bot's `main` switch and exist; with no one to take it nothing is made and the topic is told why. The binding is made right after the to-do; if another to-do holds the topic by then (`ErrThreadTaken`) the to-do just made is deleted (`removeTodo`, the DELETE route's own code) and the topic is told.
- **The reply**: one line in the topic, as a reply with `chat_id` and `in_thread` — "To-do "X" opened and handed to the main conversation", with the to-do's web link when the hub has an http(s) address (as the bot's cards' links) — then the hand-over: the first words, quoted line by line (so that a many-line message cannot pass for the instructions around it), and the to-do's id (`prompts/todo/thread_open.md`), sent as the bot's own send (`botSendIn`) so the run answers into the topic. A hand-over that fails leaves the to-do (bound, so a later reply goes to the main conversation) and says so in the topic.
- **Running an Agent on it**: the hand-over tells the main conversation to give `task_plan` the to-do's id as the task's `todo_id`. That reuses the to-do rather than making one: it must be one the plan's conversation opened or supervises, not done (a failed start is not done: see below), with no live Agent on it (an Agent let go or dismissed does not count, and since #6427 neither does one whose session is listed stopped or archived, or whose computer the hub no longer knows; an unreachable computer's Agent still counts) and not held by another plan that has started and not yet linked its Agent. When the task starts, the stopped Agents still linked are let go (`released_at` only, so they stay in the to-do's history) before the new one links. It is checked when the plan is made (an error says why, nothing is made) and again when it starts (the task gets the reason as its `error`). The to-do keeps its title and notes, and no second task card is added. A reused to-do has no `plan_id`; its failed start is retried all the same (`POST …/retry` and `task_retry` find the plan that binds it, #8770), and the apps offer **Retry** on it. A failed start (`done_at` with its `start_error`, not cancelled: `Todo.failedStart`) may itself be given as `todo_id` (#10365): when the task starts, the to-do is reopened as a Retry reopens it (`start_error` cleared, `reopened_at` set) and the new plan binds it; one whose start is being remedied in a kept tab is refused (`task_retry` is the way there), and a cancelled one is closed for good. A plan taking a to-do over holds the to-do's one start on its way (the claim a Retry, `task_retry` and a Continue take too) from the moment it takes it until its Agent is linked or the start failed, so a Retry of the same failed start and a waiting `todo_id` plan's Start never both start an Agent: whichever comes first starts, the plan's task gets "starting again already" as its `error` (also at plan time while a Retry is on its way), and a Retry meanwhile starts nothing. One whose reopen finds another assistant sharing the store reopened it first starts nothing either. Before, it was refused as "already done", so the assistant fell back on `continues`, which made a new plan and so a new checkout on the same `task/<todo id>` branch.
- **After that** a reply in the topic goes the way those of a bound topic go: the running Agent, else the main conversation (the origin).
- **Risks**: a registered group used as a notebook gets a to-do per topic; and a group another bot works in is answered twice (`docs/extensions/bots.md`).

### Where it came from

(#6146) A to-do opened for a request made in another chat (`openFromElsewhere`, `docs/extensions/bots.md` ("Asking from any group")) records that chat and message as its `source`, and tells the outcome there once it is done or accepted. `GET /api/v1/todos` returns `source`; nothing writes it but the opening.

- **One way in, whoever received the request.** `openFromElsewhere(ctx, Source{Channel, ChatID, MessageID, Text, Quote})` (`assistant/feishu_elsewhere.go`) posts the topic's first message in the home topic group, then runs the same path as a topic the owner started (`openTodoIn`: to-do, binding, main conversation) and records the source. The Lark bot's gate calls it first. **With no home topic group** it does not turn the request away (Lark is one channel, not the shape of Persona): the first message goes into the owner's private chat with the bot, the to-do is made by the same `openTodoIn` but bound to no topic, and the source gets an `anchor`, the id of that first message (`openInOwnerChat`). The hand-over to the main conversation says so (`NoTopic` in `todo/thread_open.md`: the answer goes to the private chat, and what the owner says there later is not recorded as a decision). The text of a message the request replied to is someone else's: it goes into the notes under a label that says so, and to the main conversation as an escaped context block of its own titled as written by someone else, never in the quotation of the user's words. Another channel (say an extension that sees the owner's own chats) calls it the same way, and tells the outcome back itself: it is added to `sourceChannels` and `sendSourceReport` (`assistant/todo_source.go`); a request from a channel that is not there is refused before anything is posted.
- **When it is planned.** When the to-do becomes done (the user, the judge or the supervisor), when its Agent never started, or when the user accepts it on its "Please verify" card or from a briefing's Accept button, whichever comes first. A done to-do waits for its outcome (`todo_outcome.go` reads the Agents' last replies and asks a model): the report is planned the moment the recording is through, or after `sourceReportWait` (3 minutes) with what there is; a start that failed waits a moment (`threadPostSettle`) only. Only a to-do that is done (not reopened since) and was done within the last 7 days is reported. Reopening and closing again makes no second report.
- **What is told.** The default is the first line of the latest outcome note (`#o` in `todo_outcome.go`), cleaned of links, code, paths, markup and mentions and limited to 600 characters. It says "Done." when there is no usable outcome and "Couldn't get this done." when the task failed to start. When the owner enables full replies, Persona uses the completed answer of the most recently linked Agent with a matching turn in the current task round. A task handled directly in the main conversation uses only the answer to its original handoff (`source.handoff`, or the existing private-chat anchor). It reads truncated transcript items in full and takes the assistant's final text after the tools. If it cannot match a complete answer, it reports that the answer is unavailable. The text uses literal rich-text elements so an answer cannot activate mentions. Long answers go as text attachments (requires the bot's file upload permission, `im:resource`).
- **Preview and delivery.** A positive wait sends the owner the planned text in the task's topic or private chat before planning the original reply. A zero wait skips the preview. The stored report keeps the exact text, format and deadline through restarts and delay changes. Turning off full replies prevents a pending full answer from going out while the setting is off. Reopening before the claim clears the plan. Unbinding the task from its topic prevents delivery unless the task has a private-chat anchor. The sender claims the stored plan, so a stale in-memory copy cannot supply an earlier time, different text, or different format.
- **Once, and retried only if it may pass.** `source.reported_at` is written before the send (a conditional update, so two assistants on one store cannot both win) and the send carries a key made of the to-do and the message, so Feishu drops a repeat. A look at every to-do with a report to make runs when the todos are loaded and every 10 minutes (`sweepSourceReports`): it plans what is not planned, tells what is due, and retries a try that failed for a reason that may pass (no answer from Feishu, a rate limit, a server error): the claim is given back, and the hub allows a source two replies, so a report has two tries in all (`source.attempts`). A report that can never go (the hub refuses the chat, the original was withdrawn or deleted, Feishu says no) or has used its tries keeps its claim, is not tried again, and the topic is told "Couldn't post the outcome where it was asked: <why>". One that could not be told because the bot was not ready claims nothing and is found by the next sweep. A to-do reopened between the plan and the time cancels it (the text and the time are dropped, `ClearTodoSourcePlan`); closed again, the text is worked out afresh, a new reply is planned with the current delay and, if the delay is positive, a new preview.
- **Don't report back.** "/noreply" (also the full-width slash, any case, and nothing else in the message besides the bot's own @, which a group that only sends what @s the bot starts every message with) said in the topic sets `source.no_report`; sent before delivery it cancels the report. A reply configured to go out immediately has no preview window. Decided by the text alone, never by a model; recorded as a `source = "thread"` decision of the to-do ("Don't report back to where it was asked"); not passed to any Agent; works while the to-do is done and not yet told. After the report went out it says so. On a to-do with no source it says there is nothing to stop. The topic's first message says it. A to-do with an `anchor` has no topic to say it in: the owner replies `/noreply` to the anchor (the bot's first message in the private chat), to the notice, or to any answer under them (the reply's `root_id` or `parent_id` is the anchor); it is recorded as a `source = "manual"` decision ("Reply in the Lark chat") and not passed on. A `/noreply` in the private chat that replies to none of those is an ordinary message.

## Record conclusions on completion

Step 3 of the three-loop process (#2820): Agent conclusions automatically settle into the to-do/knowledge base, without user opening Agent; next dispatch for the same project includes them (`server/internal/assistant/todo_outcome.go`).

- **When**: main-chat-dispatched task (nonempty `origin`) becomes done: main-chat acceptance (`accepted` in `task_review`, `reviewDoneTodo`; all main-chat tasks are supervised, awaiting acceptance rather than self-closing), automatic completion (`autoDoneTodo`, unsupervised tasks), or user marks done (`done: true` in `PATCH /api/v1/todos/{id}`). Excludes manual to-dos, tasks ended by launch failure and review-cancelled tasks (`cancelled`). Runs in background, not slowing completion.
- **Extract**: read last-turn replies from all still-linked Agents (fallback session-list `last_text`; ignore model-service-interrupted turns), use model (`kb.project`, prompts `server/internal/prompts/todo/outcome.md`, `outcome_input.md`) to extract one-sentence conclusion (at most 120 characters), PR/deploy links (at most 3), decisions and lessons (at most 5 each); invent nothing not in replies. Reply reads get at most 1 minute, model 90 seconds, decision/timeline writes another 45 seconds, so a slow model does not delay writes.
  Without model (unconfigured, quota, unparsable reply), conclusion falls back to receipt text (latest Agent reply compressed to one line, at most 120 characters), links only GitHub PRs from replies, no extracted decisions/lessons.
- **Decision section**: record conclusion ("Completion conclusion" + conclusion/links), each decision (question/choice/reason), each lesson ("Lessons learned") separately, `source = "outcome"`, provenance latest Agent (`source_machine` / `source_session`).
  Once per completion: `source_message` is `outcome:<to-do id>:<completion time>#<index>`; duplicate triggers (two paths together, again after hub restart) check database first. Write conclusion first; only successful writer proceeds with decisions, lessons and timeline (one wins with two assistants sharing database); deleted to-do gets no writes. Reopen then complete is a new occurrence. The Decisions view labels a previous completion summary “Earlier phase outcome”; the tools distinguish it from the current completion using the time in the recorded key, even if its write arrived late. The result and its source session stay in the record. Web provenance says "Recorded when Agent finished"; handoff includes these in established decisions, marked "Recorded when Agent finished, not decided by user".
- **Knowledge base**: the to-do's own project when it has one ("Project" below); otherwise (or when that project is gone) the project for each Agent working directory (`kb.Engine.ProjectsForWork`: first registered code `dirs`; if none match, match directory name to projects with no registered code dirs by name/slug/alias, never name-match projects with registered dirs),
  append `结论：<conclusion> <at most two links>` ("Conclusion: …") to `log.md` (at most 200 characters per line: keep links whole, truncate conclusion to remaining space), source `待办 · <title>` ("To-do · <title>", remove ` · ` from title, at most 60 characters), one line per project. Not limited by `kb.agent_turn`'s one-per-Agent-per-30-minutes rule. If knowledge base not open, retry once after 30 seconds; otherwise only record decisions. A to-do that may hold the health space's words gets no line, and one whose conversations cannot be told yet gets it only once they are told outside the space (#10941, `docs/extensions/extensions.md` "Never shown to extensions").
- **Project context at dispatch**: for a new Agent, ownership is the to-do's live explicit `Project`, then the live project of its unique current direction through `Supervision.Supervisor` (unwrapping a task leader with `leaderAbove`), and only then the target directory's projects as above. `task_spawn` carries the same `TodoID`, explicit `Project` and raw supervisor source into its child, so a child working in another project's directory still reads and writes its assigned direction. Work-trust machines receive none of this personal context.
  With usable `memory.jsonl`, the first prompt has three fixed sections (`server/internal/prompts/todo/project_memory.md`): bounded `summary.md` (1500 runes for a short project, 2500 for a long direction; `OneLine` only when the summary is absent or empty), the latest 5 outcome records, then the latest 5 effective decisions with reasons and at most 3 pitfalls. Newest-first selection is per kind, not one shared JSONL tail limit. Only explicit `supersedes_id` removes an old decision; different IDs with contradictory choices all remain with their timestamps. `agent_reported` records are visibly marked as not supervisor-accepted; legacy M1 outcome rows with an inline decision remain readable without inventing a timestamp. Extension `project_context` blocks follow the pitfalls.
  Without a usable `memory.jsonl`, the old project keeps the existing `OneLine` plus latest 5 `待办 ·` conclusions from `log.md` and the original `server/internal/prompts/todo/project.md` rendering; dispatch does not create or migrate the file. At most two project blocks appear. Extension contributions are enough to render a block, as before. Send unchanged without project, nothing to say, or knowledge base closed.
  - Assistant `task_plan` (`startTaskAgent`, retry includes decisions too), `agent_start`: prepend directly; tab names still use original title/prompt.
  - App **Hand to Agent → New** through hub: `POST /api/v1/sessions` with `todo_id`/`prompt` asks assistant (`assistant.todo_handoff` with `new: true`, `machine_id`, `cwd`; expand `~/` and empty cwd using that computer's home), project context before decisions.
    Clients' Claude starts in background then sends first message (`async`, empty prompt): hub remembers "session newly created for this to-do" (memory, 15 minutes), treats its first message as new Agent's first input with context/decisions; recognizes iOS / Android first messages even without `todo_id`. Forget only after successful send; failed sends (rejected/nothing entered) retain context on retry; answer-only devices do not count. If hub restarted between, send unchanged.
  - Handoff to an existing Agent (message) includes decisions only, not project context.

Not yet: manual editing/undo of conclusions (currently **Replace** in decisions), Lark reporting (#2768), iOS / Android decision lists.

## Lessons from accepted tasks

A task the supervisor accepts after corrections teaches the next Agents of its project what to do better (#12295,
`server/internal/assistant/task_lessons.go`). It is a short retrospective written in the background. It asks which
mistakes came back, what background the owner had to add, which steps wasted time and what would make this kind of task
go better. The answers become lessons that new tasks of the same project get by themselves, so nobody has to remember
them.

- **Switch**: "Learn from finished tasks" (Settings › Persona; `task_lessons` in `GET/PUT /api/v1/assistant`;
  `persona_settings` key `assistant.task_lessons`, approved on the phone), **off by default**. Off, nothing here runs: no
  model call, no lesson written, and every first prompt is byte for byte what it was. Lessons learned before stay on
  their projects' pages, where they can still be edited or deleted.
- **When**: a supervised task (one with a supervision ledger) is accepted (`task_review` `accepted`, in `reviewDoneTodo`
  beside the outcome and the learned estimate). It runs in the background, so the acceptance answer never waits for it.
  A rework round triggers nothing by itself: its review is read when the task is accepted. Cancelled tasks, failed
  starts, to-dos without a ledger, and to-dos whose history may hold the health space's words or cannot be told yet
  (`todoVerdicts`) teach nothing.
- **Only after friction**: the model is called only when the stretch of work the acceptance closes had something to
  learn from. That means a rework round or a needs_user review, a criterion a review found not met, a scope change in
  the brief's log, an answer the owner gave on the to-do (a question card, a note on it, its chat thread), or at least
  twice the estimate. A continued to-do counts only the reviews, changes and answers since its earlier acceptance. A task
  accepted at once and in time makes no call.
- **Who writes it, from what**: one call of the Information processing model (`kb.project`, the purpose that writes the
  outcome; prompts `server/internal/prompts/todo/lessons.md`, `lessons_input.md`). It reads the title, the owner's
  request, goal and criteria from the brief, the scope changes, each review of the stretch (verdict, round, note, the
  criteria not met with what was found), the owner's answers, how each criterion ended, the estimate against the time
  taken, the newest Agent's last reply (2,000 characters), the project's 12 newest lessons, and, as a separate "deleted,
  never learn again" list, its 12 newest deleted lessons with their tombstones' IDs (each text once). The supervisor's
  instructions and `task_review` are unchanged.
- **What it answers**: at most 3 lessons, each `{kind, text, same_as}`. `kind` is `repeated_mistake`, `missing_context`,
  `wasted_step` or `improvement`, and `text` is one sentence of at most 200 characters in the owner's language that says
  what to do next time. `same_as` names a lesson of the project the new one repeats, and a lesson that repeats a deleted
  one, even in other words, is left out. Nothing is invented, and an empty list is the usual answer. A lesson of another
  kind, an empty one, or one that the shared-transcript scrub (`transcript.SanitizeShareText`) would redact (a key, a
  token, a password, a secret in a link) is dropped. Without a model nothing is learned.
- **Where**: typed `lesson` records in the project's `memory.jsonl` ([knowledge.md](knowledge.md)), under the ownership
  worker outcomes use (`projectsForTask`: the to-do's live project, then its direction's project, then the projects of
  its last Agent's directory). Without a project nothing is learned. A record keeps `kind`, the text in `conclusion`,
  the to-do (`todo_id`), `verification` (`accepted`, or `owner` once corrected), `seen`, `first_seen_at`,
  `last_seen_at`, `recorded_at` and up to 5 `sources`. Lessons never go into the direction's notes, which stay the
  owner's own text. A manager from before lessons skips these records, and the outcome, decision and pitfall records
  and their prompt are unchanged.
- **Merging, deleting, aging**: records are never changed in place. A lesson the project already has (the one the model
  named, else one with the same letters and digits, `kb.LessonKey`) is taught again: a record that supersedes it, with
  `seen` up, the to-do added to its sources and its text kept (the owner may have corrected it). A to-do already among
  its sources does not count again, and a completion is learned from once (its record IDs start with a key of the to-do
  and its completion time). A deleted lesson leaves a `lesson_retired` tombstone that keeps its last text, and it is
  never learned again (#12393): a lesson with the text of any of its versions is dropped (so its first words stay
  deleted when the owner corrected it before deleting it), and so is one whose `same_as` names its tombstone or any of
  its versions. Other words are for the model to recognize, as when merging: it is shown the deleted lessons and leaves
  out one that repeats them. All writes go through `kb.Engine.UpdateProjectLessons`, which decides from the lessons as
  they are under the store's lock, so a merge, an edit and a delete never supersede the same version twice. A lessons
  read goes through at most the last 8 MiB of the file.
- **Handed to new Agents**: every new Agent of the project gets, after the project's own block (`todo/project.md` or
  `todo/project_memory.md`, both unchanged), a block of its own (`server/internal/prompts/todo/project_lessons.md`). It
  holds the fresh lessons, the most repeated first and then the most recently taught. At most 2 of one kind, 5 in all and
  1,200 characters, each with its kind, `seen` and last date. A lesson not taught again for 90 days is left out. The block
  says the lessons were learned from accepted tasks and that the task's own instructions win where they differ. The
  starts are the same as for the project context ("Record conclusions on completion" above), and work machines get none.
- **Seen and changed by the owner**: the project's page in Knowledge on the web lists them, with the kind, the text,
  how many times, the last time, the newest source task and whether it is still handed out, and offers Edit and Delete
  (Delete asks first). Its routes are in `docs/protocol/protocol.md` "Project lessons", for the owner's apps only.
- **Cost**: at most one model call per accepted task that had friction, none otherwise; no call at dispatch, which reads
  a bounded tail of the file.
- **Checks**: `server/internal/kb/project_lessons_test.go` (chains, tombstones and every version of a deleted lesson,
  stale writes, the read's bound, dispatch memory unchanged); `server/internal/assistant/task_lessons_test.go` (an
  accepted rework learned end to end and handed to the next Agent, off by default and byte-identical, no call for a
  smooth acceptance, nothing without a model, merges and deletions, the deleted list the model reads, selection bounds,
  friction, the routes); `server/internal/assistant/task_lessons_deleted_test.go` (a deleted lesson taught again in
  other words, named in `same_as`, or in its first words after the owner corrected it); goldens `todo_lessons.*`,
  `todo_lessons_input.*`, `todo_project_lessons.*` in `server/internal/hub/testdata/prompts`; web
  `web/src/views/knowledge/ProjectLessons.test.tsx` and
  `web/src/views/settings/AssistantSettings.task-lessons.test.tsx`.
- **Not yet**: the iOS, Android and HarmonyOS project pages and switches; ranking lessons by how well they match the new
  task's words; promoting a lesson into the direction's notes; showing lessons to the supervisor or leader as it plans;
  measuring rework rounds and owner corrections per accepted task before and after (the evaluation #8231 asks for).

## Due date, reminder, priority

#1683. A to-do can be due at a moment (`due_at`) or on a day (`due_date`, read in the user's time zone: due by the end of it), have a reminder (`remind_at`) and a priority. The assistant's `remindLoop` (`todo_plan.go`) sleeps until the next reminder (at most a minute, woken when the to-dos change) and pushes each one once when it is due:

- It claims the reminder in the store first (`reminded_at` set only while `remind_at` is still that moment, not yet pushed and the to-do not done), then pushes it like `notify_user`: to every device (opening the main conversation) and to the Feishu bot and the channels with pushes on. A claimed push that is lost is not retried; a reminder is never pushed twice, by a restart or a second manager.
- The push's title is the to-do's, its body the due date (or "was due" once it has passed), the first line of the notes, and when it went out more than two minutes late (the manager was down), the time it was for.
- A done to-do is not reminded; changing `remind_at` re-arms it; a mesh member on standby leaves it to the center, as with scheduled tasks.

## Restores and Someday

#10226 (`assistant/todo_marks.go`), from stage 1 of the To-dos redesign (`docs/design/proposals/todos-redesign.md`,
sections 6.1 and 6.3). Two of the owner's marks live on the to-do, on the hub, so every device can agree on them, as
they already do on seen (`docs/assistant/todo-status-sop.md` "Seen"):

- **Restore** (`PUT /api/v1/todos/{id}/restored`): the owner brought an inactive to-do back. `restored_at` is the moment,
  meant to count as activity for the to-do's status only (inactive again after another 48 hours without a move), as a
  device's own restore does today.
- **Someday** (`PUT` / `DELETE /api/v1/todos/{id}/someday`): the owner's own "not now". Only an open to-do is put off (a
  failed start counts as open: it waits on the owner to retry or close it); a closed one is refused with 409. Taking it
  out works on any to-do. `someday_until` is when it comes back, no later than `9999-12-31T00:00:00Z`; Someday with no
  date is stored as that time, so that "put off until" is the one rule for both. A to-do is in Someday only while
  `someday_until` is ahead: the field stays after the time passes, and the status the hub works out decides, never a
  client reading the raw field. Closing the to-do keeps the mark; reopening it, or retrying a failed start, takes it out
  of Someday, since the owner is on it again.
- Neither is an edit: `updated_at` stays, as with seen. Both send the settled `{"type":"todos"}`.
- The manager's `view` on every row of `GET /api/v1/todos` reads both (the redesign's status projection, the
  proposal's section 6.3, rows 12 and 13; `docs/assistant/todo-status-sop.md` "The hub's view"), but no client reads
  `view` before stage 2. The hub's triage (`todo_triage.go`) still places every to-do with no restore, and the web,
  iOS / Mac and Android keep their restores on the device (`docs/assistant/todo-status-sop.md` "Shelving") until they
  read the view, from stage 2.
- Clients use both routes only while the hub's features list `todo_view` (a manager capability, listed while every
  manager has it; the proposal's section 7.3, "Writes"); without it they keep the restore on the device and offer no
  Someday. An older hub or manager answers 404 `not_found`, which a client can't tell from a to-do that is gone except
  by the code: these routes answer an unknown to-do with `todo_not_found`.

## Imported from Reminders

#4009 (`assistant/todo_imports.go`). The iPhone can import the user's Reminders as to-dos, one way. The phone reads the
lists the user picked (Settings › Phone data › Reminders) and sends their incomplete reminders to
`POST /api/v1/todos/import/reminders`; the manager matches each by its `external_id` (`todo_imports`):

- **New**: a reminder never seen becomes a to-do with its title, notes and due date (a moment, or a day for an all-day
  reminder). One without a title is skipped.
- **Changed**: only the fields that changed in Reminders since the last import are written, so a title the user changed
  in Persona stays until the reminder's title changes too. A due date removed in Reminders is removed here.
- **Left alone**: completing or deleting a reminder does nothing to its to-do, and nothing is ever written back to
  Reminders. A to-do deleted in Persona stays deleted: its reminder is skipped from then on.
- One batch at a time per manager; when two managers import the same new reminder, the second removes its copy.

The import runs only while the app does (launch, return to the foreground, a change in the Reminders database while it
is in front), since only the phone can read Reminders; it is not real time. There is no background refresh yet, which
keeps it out of the battery budget (#1633). A batch the hub already took (same hash, same hub) is not sent again
(`apple/Persona/PhoneTools/RemindersImport.swift`). A request takes at most 1000 reminders; the phone sends more in
several requests, in a stable order, and counts the set as sent only once every request was taken.

## Calendar

#2029. The to-dos page switches between the list and a calendar (List | Calendar at its top, kept per device; the calendar's Day | Week | Month too). The calendar shows the to-dos that have a due date, from the same list the page already has: `GET /api/v1/todos` returns them all, so switching needs no request and works offline from the cache.

- **Where a to-do goes**: due at a moment (`due_at`) on the time axis of the day and the week, the block's top edge at that moment. A due moment is not a span, so every block is the same height (about 50 minutes, a tap target). Due on a day (`due_date`, a day in the user's time zone) in the All Day row above the axis, on that day on every device. Blocks that would overlap sit side by side; on an iPhone's week, whose columns are a few characters wide, they become one block that says how many and opens their day (Android keeps them side by side there too, narrower, so each can still be dragged; #4200).
- **The month**: each day shows up to three lines (all-day first, then by time), or two and "+N" (phone) / "N more" (iPad, Mac). Tapping a day opens it in the day view; on Android a sheet lists that day's to-dos first (state, when, flag and bell; a tap on one opens it, as the month did before the day and week), with Show Day to open the day view.
- **Looks as in the list**: the bar and the dot are the state's color (needs you, working, done unread, not started); overdue is red, before the state; done is faded and struck through (Show Done, in the calendar's options, hides them, per device); a flag for high priority and a bell while a reminder is still to be pushed, as on the row. A reminder is not drawn on its own: it is not something to do, and would show the to-do twice. The moment is a red line on today.
- **Without a due date**: not on the calendar; a bar under it says how many and goes back to the list.
- **Moving around**: Today, previous / next, and on iOS and Android a sideways swipe; the day view has the week's strip (a dot for each open to-do, a few) to pick a day; a day of the week, or of the month, opens that day.
- **Where a week starts**: on the system's or browser's first day of the week, the same for the day's strip, the week and the month. Apple: the first weekday the user chose (Language & Region), else Monday in Simplified Chinese or on the Chinese mainland (Apple's data still says Sunday there; current CLDR and the browsers say Monday), else the region's (`TodoCalendar.userCalendar`). ## Requests in pieces

When one thing the owner asked for is split into several pieces of work, the pieces say so on the to-dos themselves (`assistant/todo_pieces.go`): `part_of` is the to-do that stands for the request (its root, usually the owner's words as a to-do), and `after` the pieces of the same request a piece waits for. The web's To-dos page draws them as a graph under **By request** (`docs/web/web.md` "Todos").

- **Who writes them**: the assistant through `todo_create` / `todo_update` and each `task_plan` task's `part_of` / `after`, the apps through `PATCH /api/v1/todos/{id}`. The graph is advisory by default; owners can opt into enforcement below.
- **The manager's checks**, whenever they are written: the to-dos named exist; a to-do names neither itself nor a to-do that is itself a piece (one level: a request's root is no piece, and a to-do with pieces cannot become one); `after` names pieces of the same request only, needs `part_of`, and closes no cycle; repeats and blanks are dropped. Changing `part_of` without giving `after` empties `after`. The same-request rule holds from both ends: a piece another piece waits for keeps its `part_of` (moving it to another request or clearing it is refused, naming the pieces that wait) until it is taken out of their `after`; Persona does not take it out for them, since that would let them start early without anyone deciding so. A refusal says what is wrong (a tool error, or 400). The write checks them once more while holding the to-dos' write lock (`todoBook.writing`, taken by every link write: `editTodo`, `insertTodo`), so two writes at once that each pass against the graph the other is changing (A after B, B after A) can't both be stored: the later one is refused (#8556 review).
- **A piece that waits** is a to-do with no Agent. Made with `todo_create` and `part_of` by a conversation that may hand out tasks, it is that conversation's (`origin`, as a leader's pieces are, but not supervised until an Agent works on it), so when its turn comes `task_plan` with its `todo_id` runs an Agent on that same to-do: its id, and every `after` naming it, stay. From an Agent's session it is a plain to-do.
- **`task_plan`** checks a task's links when the plan is made and writes them when the task starts. For advisory requests, a stale link is logged and left out rather than stopping an approved start. The apps' edits of a plan card do not change links.
- **Deleting** a to-do leaves its id in other to-dos' `part_of` / `after`. The graph cannot draw edges to missing nodes; enforced starts stay blocked until their references are repaired.
- `todo_list` / `todo_get` show a piece as `(piece of todo_…, after todo_…)`.
- **The request's own row** (web, #11858): its status line says its steps as the hub counts them on its view (`view.steps`, closed of all; iOS's "Steps 2/5"): with no Agent of its own, "Steps 1/3" in place of Not started and nothing about handing it over, and once every step is closed "3/3 steps done · Next step not arranged yet"; with one, "· Steps 1/2" after its Agent count. Its page says the same. A row without the view (an older manager) reads as before; its section is unchanged.

### Enforce prerequisites at launch

An owner can set `{"require_accepted_after":true}` on the root to-do with `POST /api/v1/todos` (alongside `title`) or `PATCH /api/v1/todos/{id}`. It defaults to `false`. Use the existing `part_of` and `after` fields to relate pieces; there is no separate editor or assistant tool for the switch. This gate applies to manager task plans, not to standalone agents launched outside a plan.

1. Create the pieces, then use `task_plan` with each piece's `todo_id`. To change a recorded piece's links, edit that to-do rather than putting new links on the plan. A plan for a new piece can instead supply `part_of` and `after` directly, but stale links must be fixed before that plan can start.
2. Approve the plan on its card. A piece with prerequisites requires explicit approval even if other policies would let it start immediately. Independent pieces can start without waiting for one another. Blocked pieces list the outstanding to-do IDs in their queue status and do not take a machine slot.
3. A prerequisite clears on an accepted task review, not when its agent merely finishes a turn or when its to-do is marked Done. If the review asks the owner to verify it, the gate also waits for their Pass. A reopened, cancelled, deleted, or unaccepted prerequisite stays blocking; the **By request** graph uses `prerequisite_blockers` from the to-do list to show the manager's state.

An approved start is remembered across manager restarts and rechecked by the task queue (normally within a minute). After it clears prerequisites, normal capacity checks still apply. A waiting start checks the prerequisites it was approved with as well as any new links; removing a link or turning enforcement off does not waive that approval's prerequisites. To release work with revised prerequisites, cancel the old start and approve a new plan. If the manager loses confirmation of a launch, it does not send it a second time automatically: check the computer. This version does not support direct Retry or a `continues` handoff for gated starts; after a definitive failure, make a new plan on the same to-do and approve it.

## The assistant's todo tools

#1683. The assistant has the user's to-dos as MCP tools (`todo_tools.go`, descriptions in `prompts/mcp/todo/`), so it can note what the user asks it to, or a batch of deadlines from a mail, without a hub token:

| Tool | What it does | Confirmed on the phone |
| --- | --- | --- |
| `todo_list` | Open to-dos and failed starts by default, earliest due first (none last), filtered by state, due before / after, overdue, with or without agents, project, words | — |
| `todo_get` | One in full: notes, agents, the task it is, decisions in force | — |
| `todo_create` | `title`, `notes`, `due` (a day, a moment in the user's time zone or RFC 3339, `2h` / `3d`), `remind` (a moment, not past), `priority`, `project`, `part_of`, `after` ("Requests in pieces"); an open to-do with the same title and due date is returned instead of made twice | No |

With the advanced manager setting `assistant.complete_agentless_todos` enabled (default `false`), the supervising conversation can complete its own memo without a confirmation card when no Agent is attached. A memo originating in that conversation and having no supervision ledger also qualifies. Another conversation, a planned task (with or without an attached Agent), every reopen, and health-space outbound confirmation keep their existing behavior. This is visibility only: a personal to-do stays the user's own and is not automatically supervised or dispatched to an Agent. Questions created by `ask_user` keep their dedicated snapshot section.

The background supervisor's snapshot leaves out the main conversation's plan cards waiting for Start, the owner's unread chats and the iPhone line, which only the main conversation acts on (`assistant/context.go` `backgroundSnapshot`, #7315). The total of open to-dos and the `todo_list` entrance stay (#8666, `assistant/context.go` `scopeSnapshot`). The sources are still read once for all conversations.

## Design trade-offs and reasons

1. **Not another Lark Tasks or Reminders**: Persona to-dos drive and track Agent workflows, focusing on which Agents share one task and their progress, not complex subtasks, deadlines, priority trees, calendar reminders or multi-party collaboration. The Reminders import (#4009) keeps to that: one way, title, notes and due date only, so a to-do started in Reminders can be handed to an Agent without retyping it; lists, subtasks, sharing and completion stay in Reminders.
2. **No stored state**: overall state derives entirely from linked Agents' live runtime states (questioning, working, finished unread, etc.). Agent state changes frequently; derivation avoids dual-write consistency problems and large synchronization overhead.
3. **One active to-do**: `UNIQUE (machine_id, session_id) WHERE released_at IS NULL` ensures each Agent serves only one current to-do at a time. Assigning other work automatically marks the previous task "Previously involved", keeping context and execution goal clear.
4. **Automatic completion only for chat-dispatched tasks, judged by model**: these have explicit requirements (dispatch prompt) and deliverables (Agent's final reply), so requiring individual user completion taps is a burden; manual to-dos often represent the user's own plans, whose completion hub cannot know. Stopped is not finished, so do not close by state alone; judgment model decides, leaving open when uncertain. Wrong auto-close (user thinks finished) costs much more than missed close (one extra tap), hence reversible, reasoned, and not reclosed by the same work after reopening.
5. **A continuation is the same task**: `continues` reuses the original to-do and its immutable brief. At Start, stop and release prior Agents and reopen the to-do in place if closed; planning does not mutate a running Agent or closed task. A failed or unauthorized takeover must not create another to-do; an unreachable prior Agent and legacy open successor duplicates are refused. Plain `todo_id` remains limited to an open to-do without live Agents.

   Reuse the existing `task_plan` fields instead of adding an API: `agent_send` is enough for a plain follow-up to a live Agent when no permission change is wanted. To move from investigation to implementation, use `continues: "<original to-do id>"`, `continues_why`, `readonly: false`, a new implementation prompt, and an explicit writable `permission` (for example `bypassPermissions` for Codex). A fresh writable process removes Codex's launch-time plan/read-only sandbox instead of attempting to mutate it in place. The original brief and `out_of_bounds` remain unchanged; use `task_scope` for an authorized scope change.

`continues` is an explicit task handoff, separate from automatic task closure. It stops prior Agents only when the
plan starts, keeps their terminals and released links in the task history, and reopens the original to-do if needed.
The new Agent's work is a new round of the to-do's supervision, and a plain `todo_id` takeover is too (#11553). The
earlier round's accepted or cancelled review stays in the ledger's history. The ledger's state goes back to going on
and its rework count to 0, so no client shows the earlier acceptance on the new work (`docs/assistant/todo-status-sop.md`,
"Accepted tasks").
The waiting plan card leaves Agents and task completion unchanged. A refused stop fails the handoff without making
a new to-do. Existing historical successor chains are still guarded against duplicate continuation.

## Known limitations

1. **Direct renames inside herdr**: renaming workspace in herdr terminal rather than hub API acts as a new project; previously linked Agents remain, but later Agents in that workspace will not auto-link.
2. **Marker overwrite across multi-hub groups**: a computer's persistent node serves only one long-lived connection at a time. If independent hubs in different linked-hub groups connect alternately to one node, later hub's expected markers overwrite earlier hub's.
3. **Empty-workspace rename does not migrate**: when renaming through hub with no active sessions, hub cannot resolve old workspace name; `todo_spaces` does not automatically migrate, like pin/mute.
4. **`/clear` recreates session**: Agent `/clear` creates a new session uuid underneath; new session does not auto-link to old to-do, and original session row stays listed.
5. **Assistant disconnected**: to-do APIs and create/send with `todo_id` return 503; workspace renames through hub do not migrate and answered cards are not recorded as decisions ("Who owns what").

## Repository associations

Repository associations are optional metadata for ordinary to-dos and existing
single-repository tasks. They do not create or remove directories, change the
workspace mode, or advance task progress. Legacy `new` / `existing` / `none`,
Engine-created workspaces, reused directories and cleanup retain their existing
behavior. The existing `pr_url` and delivery judgment stay independent: multiple
linked PRs never imply that a task is complete.

The Web to-do creation dialog and detail use the optional **Repositories and
work** group. The detail is read-only by default: it draws the saved
repositories as rows with their issues and pull requests as links, so the
associations the agent maintains are visible without opening an editor. Each
repository row carries its provider's own mark and its project address on one
line; a link shows its retained full title as the hyperlink, falling back to the
localized type and number when no title is known. A provider extension's
repository has the extension mark and its source's name after the address (the
`provider_name` saved with it, else "Another source", never the `ext:` id); its
links open at their stored addresses, numbered `#N`, with the extension's own
`link_kinds` words for issue and pull request. While its `provider_state` is
`off` or `missing` the row shows an **Unavailable** pill and a note, and adding a
link to it is turned off. The association store holds no
physical workspace path, so a row shows no filesystem path; directory aliases
are not paths, and physical paths belong to the workspace preparation service.
Opening the editor holds the draft and the revision it began from: a to-do
version change while it is open never replaces them, and the newest store is
read again when the dialog closes. Source options are disclosed per repository.
No alias or base branch is required: an empty alias means no directory override
and a missing ref means the remote default branch. This feature does no Git or
remote issue lookup for GitHub and GitLab; a new link of a provider extension's
repository is asked of that extension (`repo.link`) before the save, never while
reading or opening a to-do.
An issue/PR URL must belong to the saved provider, instance and target repository;
links retain numeric string IDs, including IDs beyond JavaScript's integer range.
When a provider extension is switched off, not running or uninstalled, its rows
and links still read and open from what was stored (`provider_state` `off` or
`missing` on reads), saves keep the links already there without asking it, and
only a new link for it fails with `task_repositories_provider_off` or
`task_repositories_no_provider`. Right after a restart, before the extensions
have listed their providers, a new link on a host no built-in owns waits for
them within the save's budget and, if they are still starting, fails with
`task_repositories_providers_starting` (409), never `task_repositories_no_provider`.

| Method | Route | Contract |
| --- | --- | --- |
| GET | `/api/v1/todos/{id}/repositories` | Returns `schema_version`, `manager`, `todo_id`, `revision` and `repositories` |
| PUT | `/api/v1/todos/{id}/repositories` | `{expected_revision, expected_catalog_revision, repositories}` replaces business associations atomically; `[]` clears them |
| PUT | `/api/v1/todos/{id}/repositories/{repo_id}/links` | `{expected_revision, links}` replaces one repository's links; `[]` clears them |

`POST /api/v1/todos` also accepts optional `repository_bindings` containing
`catalog_revision` and `repositories`. The Todo and associations commit in one
transaction. Older requests omitting it retain existing behavior; ordinary PATCH
operations never touch association storage. The catalog response and
`repositories_list` include `catalog_revision`. Writes require exact revisions;
conflicts preserve the client draft and require reconciliation. Read failures
never masquerade as an empty set.

`todo_repositories_get`, `todo_repositories_set`, `todo_repository_links_set` and
`todo_repository_links_add` expose the same manager-owned store. `todo_get` includes
its canonical associations. The additive tool accepts `{id, links: [{url, title}]}`
with full source titles, or legacy `{id, urls}` (one to 50 exact issue/PR URLs in
total), infers repository groups offline (an address on a host a provider
extension claims is read by that extension) and needs no preconfigured catalog.
Creation and replacement tool schemas leave `requested_ref` optional. When
present, it requires `kind`: `default` omits `value`, while `branch`, `tag`,
`commit` and `ref` require a nonempty string value. The manager still validates
Git ref syntax and commit hashes; its older omitted-ref default is unchanged.
Each repository has at most 50 links, and structured link numbers are decimal
strings matching `^[1-9][0-9]{0,19}$` across creation and replacement tools.
Titles are optional plain text, limited to 1,024 UTF-8 bytes after trimming; control
characters are rejected. The tool schemas describe this byte limit explicitly;
their `maxLength` is only a character ceiling, not a UTF-8 byte validator.
A nonempty title updates a retained link and increments
the association revision. Omitted or empty titles in URL-only reports or older
editors preserve known titles; removing a link removes its title. Agents obtain
titles from the related work and maintain them through the same tool. The app
shows a localized type and number until a title is available; it never guesses
titles or performs a remote metadata request when opening a to-do.
It preserves source snapshots, aliases and requested refs. Assistant conversations
can manage their manager's to-dos; task Agents can read or edit only their actively
linked open to-do, with its ID available through `todo_decisions`; the node names
the calling Agent's session for them from its pane, as for the decision tools
(`callerTools`, #9089). Empty ordinary
to-dos need no catalog read. `todo_create` accepts the optional creation object; a matching
existing Todo with supplied bindings is explicitly refused so callers can read
and edit that Todo without silently discarding associations. Writes retain the
existing outbound confirmation rule for health conversations.

Existing `pr_url` / `prs` references are imported once before the first interactive
association read or edit. During a meeting turn, `todo_get` and
`todo_repositories_get` read only saved associations: they never import links or
write association data, revisions or receipts. An ordinary user turn retains the
historical import behavior. New Agent reports append every supported PR URL to this same store,
including self-hosted instances; old stage and delivery fields retain their existing
judgment semantics. A stored receipt prevents historical imports and repeated reports
from restoring links removed by the user. An explicit additive call can restore them.
Imports and interactive edits lock the same Todo and commit atomically; changes
broadcast the existing `todos` event even when stage and legacy PR stay unchanged.
Metadata import errors are logged without blocking the legacy progress path; explicit
tool and HTTP failures remain errors. Link-derived repositories absent from the
catalog have `catalog_state: "unlisted"`; recording a GitHub or GitLab URL performs
no repository verification, remote lookup or catalog mutation. In a report, a
provider extension's URL that is new is read by that extension in the background,
and not again on that to-do for 5 minutes once it has answered (an attempt that
failed or found it unavailable is tried on the next reply). That covers every address on its hosts in
an Agent's reply, even one that is then not kept (a file page, an issue, another repository),
so the extension learns the addresses you and your Agents mention in a to-do's work,
as its install permission says. Reports skip such addresses while the extension is
unavailable, and the one-time import of older `pr_url` / `prs` references never
asks an extension.

Task repository storage uses manager migration `0516_todo_repositories.sql`.
Earlier branch builds recorded it as `0513` or `0514`; the existing migration
renumbering moves either record before applying the search migration that now
owns that number. Existing association data is kept.

Shared Go types and validators: `server/internal/assistant/repository/task.go`.
Web types/helpers: `web/src/lib/task-repositories.ts`. Fixed consumer fixture:
`spec/fixtures/task-repositories/contract.json`. Directory aliases use one ASCII
rule, case-insensitive uniqueness, reserved-device-name rejection and an optional
empty override. Explicit `root` layout maps one selected repository to `.`;
`container` layout uses a validated nonempty effective directory name. This
opt-in mapping never changes legacy cwd inference.

Each association saves identity and credential-free transport by value. Catalog
names are independent. A removed or identity-changed catalog entry is reported
without replacing the saved source. Catalog clients omitting `clone_url` preserve
its previous value when identity is unchanged; a changed identity gets its own
canonical fallback. Adopting a new source requires removing and reselecting the
association in separate saves. A repository row a new link adds clones from the
catalog entry's `clone_url` when there is one (`transport_origin: "catalog"`),
else from the clone address a provider extension answered for its repository
(`"provider"`), else from its canonical URL (`"canonical_default"`).

Preparation consumers use `repositorystore.ReadTodoRepositoriesTx` with the expected revision,
select repository IDs through `repository.Snapshot`, and persist that value with
their operation in the same transaction. The reader locks the Todo, including an
empty set. Digests exclude links and association revision. Consumers retain the
operation's snapshot for retries; no permanent business-association seal or
legacy-start hook exists. Physical records, paths, resolved commits and cleanup
belong to the workspace preparation service.


## Backend workspace naming

People configuring coding tasks can open **Workspace naming** inside Assistant
settings’ **Starting tasks** group after choosing **New workspaces**.
The entry waits for the matching assistant’s confirmed preference; other, missing
or unknown preferences hide it without deleting saved rules. A to-do’s details
keep an independent naming entry. Template help appears beneath each field by
default; preview options open on request. Labels and fields form compact desktop
rows and stack on narrow screens. Unset inputs are blank, with localized
placeholders showing the system default (Assistant settings) or the effective
Assistant default (task overrides). Clearing and saving removes that override;
there are no inheritance status labels or reset buttons. A preview shows the task
folder once, then a labeled branch for a root repository or each repository's
folder-to-branch mapping for a container, without repeating the parent path. The
computer and layout selectors and the preview action form one compact row that
stacks on phones; a task's repository choices sit above it. Routine planning
time, time zone and disclaimer text are left out of the result.
It applies only to explicitly selected backend preparation. It does not change Engine creation, legacy `new`, `existing`
or `none`, existing preferences, task progress or cleanup.

The fields are `base_directory` (default `{home}/workspace`),
`task_directory_template` (`task-{task-id}`), and `branch_template`
(`persona/{task-id}`). Each field inherits task override → Assistant → product
default. Omitted patch fields preserve saved values; `null` removes an override;
empty strings are invalid on the wire. The Web editor converts a cleared field
to a null patch and uses the same fallback in preview and after reload. Assistant
writes still require the explicit manager.
Assistant GET and PUT responses keep `workspace_rules` as the saved partial
object (`{}` when unset or wholly reset); `effective_workspace_rules` separately
contains all resolved fields. Saving a value equal to a default still records
an explicit override. Reading defaults never materializes them in saved rules.
Task overrides have their own CAS revision, independent of legacy Todo edits.

Folder templates support `{task-id}`, `{task-slug}`, `{yyyy}` and `{mmdd}`.
Branches also support `{repo}`, `{branch}` and `{base-branch}`. The last two
require an explicit branch; default, tag, commit and arbitrary typed refs are
preserved without guessing a branch. Only a template using an unavailable field
fails. A root repository maps to `.`, while containers use each repository's
explicit alias or the shared repository-name default. Duplicate names fail.

| Route | Contract |
| --- | --- |
| `GET/PUT /api/v1/assistant` | `workspace_rules`, `effective_workspace_rules`, `workspace_naming_version` (`workspace-naming/v1`); PUT patches rules with explicit manager ownership. |
| `GET/PUT /api/v1/todos/{id}/workspace-rules` | `{todo_id, revision, workspace_rules}`; PUT requires `expected_revision` and a rule patch. |
| `POST /api/v1/assistant/workspace-naming/preview` | Clearly labeled sample, using selected computer and layout; optional draft rules. |
| `POST /api/v1/todos/{id}/workspace-naming/preview` | Trusted saved Todo/repositories, explicit `machine_id`, `layout` (`root` or `container`) and `selected_repo_ids`, optional draft rules. |
| `POST /api/v1/todos/{id}/workspace-naming/plans` | Same selection plus required stable `operation_id`, without draft rules; saves one immutable snapshot for this operation. |
| `GET /api/v1/todos/{id}/workspace-naming/plans/{operation_id}` | Reads a saved snapshot, including after a lost save response. |

Preview calls the selected computer's read-only `workspace.naming.resolve` RPC.
It supplies its own home and native path semantics; no browser-provided home or
resolved path is trusted. The pure resolver checks lexical paths; on Darwin it
compares components without case to conservatively reserve private state even
on case-sensitive volumes, while Linux comparisons remain case-sensitive.
The Node resolves existing symlink ancestors of the base, task root and every
repository's absolute path through its existing guarded walker, then rejects
credential paths and physical private state. Only a missing tail is accepted;
other resolution errors fail closed. This includes the private-state root itself:
the guarded walk returns its physical existing ancestors plus missing tail even
with `ErrNotExist`, and containment uses that returned path. It also validates local branch format.
No directory is created, no repository is
queried or fetched, and no Engine is opened. `.persona` and `.git` task path
segments and private state directories are unavailable; `{persona-home}` has no
registered public workspace subtree in this version and is unsupported.
Windows device and extended namespaces (`//?/`, `//./` and `/??/`, including
extended UNC paths) are rejected rather than stripped: they can name the same
private directory with a different lexical volume. A Windows Node with a
namespace-form home or state directory returns `context_invalid`; ordinary
drive and UNC paths retain their native case and separator semantics.
Task-directory components follow portable rules both when saving a template and
after expanding it on the Node. Windows device names (`CON`, `PRN`, `AUX`, `NUL`,
`COM1`–`COM9`, `LPT1`–`LPT9`, and their superscript-digit forms) are rejected in
every component, regardless of case or extension. The shared repository helper
checks only reserved names: task paths still allow Unicode, internal spaces and
components longer than a repository alias. Ordinary near-matches such as
`COM10` and `NUL-backup` remain valid. This is naming validation, not proof that
the target filesystem can create the path. Preparation must recheck physical
paths when it creates or reuses resources; preview does not freeze the filesystem.

The sole resolver and wire contract are in
`server/internal/workspacenaming/naming.go`, with an exact shared vector in
`spec/fixtures/workspace-naming/contract.json`. It freezes the instant, assistant
timezone (explicit UTC fallback), title slug, effective rules, T1 selected source
snapshot, paths and task branches. `digest` is SHA-256 of the Go JSON encoding
with its own digest cleared; repositories are ordered by repository ID.

The manager persists `todo_workspace_rules` and `workspace_naming_plans` in
PostgreSQL. Their schema migration is `20261118234802_workspace_naming.sql`. Earlier
branch builds recorded `0515_workspace_naming.sql`; the existing renumbering step
moves that record before applying pending migrations. Saved rules, revisions and
operation snapshots are kept, including when an older build left both records.
Snapshot saves check the current override revision and selected source
digest in the same Todo transaction. Link-only edits do not alter that source
digest. Retrying an existing operation returns its original snapshot without
rereading settings, title, clock or computer context. Changing input requires a
new operation; associations and overrides remain editable, including after a
snapshot. Operation IDs are global: reusing another Todo's ID returns a generic
conflict before calling the computer, while a read under the wrong Todo remains
not found. Concurrent saves preserve one immutable snapshot; incompatible input
returns a conflict rather than a database uniqueness error.
Preparation can call `repositorystore.ReadWorkspaceNamingPlanTx` in its own
transaction. This read does not permanently bind the Todo or attest readiness;
preparation owns cancellation, intent checks, physical ownership, Git source
resolution, recovery and existing cleanup semantics.

Web reuses `WorkspaceRulesEditor`, `WorkspaceNamingPreview`, settings inputs,
Group and Button. Saves confirm returned values; failures keep drafts and can
reload the saved baseline without discarding local edits. Reloading also removes
preview selections for repositories no longer associated with the task; existing
selections stay unchanged and newly associated repositories require selection.
Both entry points load the shared editor through `lazyPage` when rendered, keeping
its module out of the first screen's page-preload dependencies. The connection
context guard is shared with the repository editor. Both Assistant settings and
Todo details wrap naming in a local `PageBoundary`, retaining the existing
one-time chunk reload and recoverable error. A persistent import failure leaves
the other editors mounted and saveable.
Edits and computer or assistant changes invalidate pending preview responses.
These controls never select a creation mode or start an Agent.

## Backend workspace preparation

Backend creation is an explicit additional path for people preparing repository work on a computer.
It does not change legacy `new` / `existing` / `none`, engine-created workspaces, existing checkout
reuse, ordinary to-dos or their defaults. Associating repositories never creates a directory. A saved
naming plan selects the repositories to prepare, independently of later association edits. Root layout
uses one linked worktree at relative path `.`; container layout uses the selected subdirectories.

The Manager adopts the T1 repository snapshot and saved T2 naming plan in one transaction before
calling the Node. The shared repository contract lives in `server/internal/repositorywire`; the original
`server/internal/assistant/repository` import path retains aliases and forwarding helpers. This keeps
the Hub independent of Manager code while preserving the T1/T2 API. Naming and preparation persistence extend the Manager-owned `assistant/repositorystore` on the same database pool; no repository business storage is restored to shared `db`. New records are in manager migration `20261119163935_task_workspaces.sql`, separate from
legacy engine workspace IDs. Repository migration `0516_todo_repositories.sql` replaces its earlier
0513/0514 names through the existing renumbering mechanism; 0514 on main belongs to search. A Node
stores physical receipts and private bare repositories under its protected `task-workspaces` directory.
The bare repositories are private to the workspace, have no shared object dependencies, and survive
default cleanup so local branches and commits really remain available. `common_dir` reports their
actual locations. This separate Git storage also permits a root worktree to be removed while retaining
its branches. File APIs cannot edit the ownership receipts; shell access under the same OS account
is not a separate security boundary.

The HTTP operations are:

| Method and path | Behavior |
| --- | --- |
| `GET /api/v1/todos/{id}/backend-workspace` | Current persisted workspace or null; never prepares resources. |
| `GET /api/v1/todos/{id}/backend-workspace/operations/{operation_id}` | Persisted workspace plus a separate live Node observation or an unavailable error. |
| `POST /api/v1/todos/{id}/backend-workspace/prepare` | `operation_id`; first call also supplies `machine_id`, `layout` and `selected_repo_ids`. Saves or adopts a naming plan, then prepares. |
| `POST /api/v1/todos/{id}/backend-workspace/cancel` | `operation_id`; persists cancellation before contacting the Node. |
| `POST /api/v1/todos/{id}/backend-workspace/cleanup` | `operation_id`, optional `force` and `delete_branch` (both false by default). Returns per-repository removal and branch results plus retained Git paths. |

These routes require full credentials for extension access, like machine worktree inspection and
removal. The extension scopes for to-do metadata and naming plans do not grant physical worktree access.

The assistant's `todo_workspace` tool exposes inspect, prepare, cancel and cleanup with the same
contract. Preparation and cleanup never start an Agent or change task stage. Missing support returns
`unsupported`; it never falls back to engine creation. Errors carry code, stage, operation, repository,
path and available actions; partial results remain in the operation record. Raw Git stderr and embedded
credentials are not returned. Default refs are discovered from remote HEAD and fetched on the Node;
typed branch/tag/commit/ref input is preserved. A resolved base commit is checkpointed before the
worktree is added. Current HEAD and dirty state never replace that source fact.

Use the same operation for transient retry. After an unknown transport outcome, inspect it first.
A canceled operation remains canceled. To correct inputs, cancel, edit associations/rules and use a
new operation on the same to-do. Unchanged successful instances at the same root are reused; changes
that would replace successful work return `resource_conflict` and require explicit cleanup. Cleanup
keeps tombstones; preparing after removal uses a new operation/workspace identity. `node_operation_id` records the operation actually admitted by the Node, which may still be the
previous one after rejected corrections. Further corrections and cleanup target that physical owner,
including when cancellation happened before any Node effects. Business metadata stays editable and
does not invalidate a ready workspace.

Node locks cover each workspace and its root, including Git subprocesses. On Unix the subprocess
inherits both lock descriptors: a killed Node cannot make an ongoing command look stopped. A new
Node reconciles the Git registration after the command exits, preserving commits and dirty files. On
Windows an interrupted in-flight command remains `operation_unknown` because the current lock
implementation cannot prove its child stopped; normal completed-command restart recovery is supported.
No native Windows execution is claimed by a cross-build.

Cleanup uses the existing worktree rules: running Agents/use claims prevent removal, uncommitted
changes require force, and deleting an unmerged task branch requires force. New commits alone do
not prevent default cleanup because the task branch and its bare object store remain. The ancestry
check for non-force branch deletion uses the frozen source, the equivalent of the source checkout's
branch. It also protects branches whose worktrees were removed by an earlier partial cleanup or
reconciled after a lost receipt; a completed branch deletion can resume without recreating the branch. Unknown container files and additional Git registrations are preserved, including with force.
Cleanup results distinguish removed checkouts from retained branch storage; no retained branch is
claimed after its object store has been deleted.

### Starting an agent in a prepared workspace

For a to-do with a saved workspace naming plan, pass its `todo_id` and select
`"workspace":{"backend":{"operation_id":"op_example"}}` in the corresponding
`task_plan` item. The operation determines the computer, root and selected
repository paths. The named machine must match. Set `backend.host` to select
an enabled engine on that computer. The Manager prepares a missing checkout,
persists the all-ready result, claims the workspace and checks that the to-do
and operation still permit a start. A retry reuses the same ready checkout.

For an owner starting a to-do directly, including one created by hand, use
`POST /api/v1/todos/{id}/backend-workspace/start`. Send `operation_id`,
a stable `start_id` for this launch, and optional `host`, `launcher` and
`prompt`. The response contains the ordinary task plan. Repeat the same
request after a lost response to retrieve it. Changing the inputs under
the same start ID returns a conflict. A subsequent launch after a confirmed
stop uses a new start ID and the existing workspace operation.

The plan's `workspace_resolved` contains `backend_workspace_id`, `operation_id`,
`path` and the repository map. Git requests to the machine can carry
`backend_workspace_id` and `repo_id` in the query for reads or the JSON body for
writes. The Node verifies the worktree identity before running the usual Git
operation in its recorded path. This also works when the root is itself the
selected repository. Existing clients continue to pass `cwd`.

The Node opens the prepared root, records the session ID, and keeps the checkout
claimed while the agent runs. The Manager reconciles a lost reply against that
receipt. An uncertain dispatch retains the claim and offers inspection. A
confirmed stop allows another plan for the same operation to choose a different
supported engine and keep the files and commits. A failed plan item exposes
`workspace_error` with its stage, operation, path, repository when applicable
and recovery actions. Preparation details and per-repository results remain
available through the operation inspection endpoint above.

The engine's workspace ID still identifies its native container. Use the
backend cleanup endpoint for the prepared repositories and the engine’s
close action for its terminal. Adding a repository, issue or pull request
association leaves the task’s launch choice and delivery progress in place.
